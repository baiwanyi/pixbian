# 后续两轮：缩略图静默全灭（0x8001010E）+ 快速切换未响应，均已修复（用户确认正常）

## 缩略图全灭 → HRESULT 定案 RPC_E_WRONG_THREAD
- 症状：不冻了但骨架屏常驻；THUMBWAIT 正常完成而 THUMB 0 条产出——失败全静默黑盒
- 取证迭代：catch 全量记录异常类型 → COMException（Message 空）→ 加 HResult →
  **`0x8001010E`（RPC_E_WRONG_THREAD）**
- 根因：**第 20 轮 ConfigureAwait(false) 修复的回归**——编码段落线程池后
  `SynchronizationContext.Current` 变 null，`CreateBitmapAsync` 的 ConfigureAwait(true)
  切不回 UI 线程 → `new BitmapImage`/`SetSourceAsync` 在线程池 → 线程亲和异常。
  **ConfigureAwait(true) 语义是"恢复到各 await 点当时捕获的上下文"，中途 false 后末端 true 回不去**
- 修复：`ThumbnailService` 注入 `DispatcherQueue`（单例 UI 线程构造，回落 GetForCurrentThread），
  位图创建经 `TryEnqueue` + `TaskCompletionSource`（RunContinuationsAsynchronously 防内联）
  显式切回 UI 线程，async void 桥接 + 异常收口到任务源
- 同时：单条编码 20s 超时（`WaitAsync`，挂死 IO 不再占死信号量槽位）、catch 扩展
  TimeoutException/COMException、`WhenAll` 90s 兜底（状态机收口，解码后台继续）

## 快速切换未响应（UI 线程 2~5 秒/次钉死）
- TICK 间隙扫描：切换期间 2.8s/2.5s/4.7s 间隙，而管线日志全部正常完成
  → UI 线程被「200 容器销毁+创建+全量重排+取消扫描」钉死，快速切换 ×10 = 未响应
- 修复三件套：① 替换块内补代数检查（过期请求跳过整块 UI 重建，快速切换只执行最后一次）
  ② `PrefetchDimensionsAsync` 加 sequence 参数，写回块内复核 ③ `GalleryPage` ViewChanged
  偏移去重（集合替换误触发的 O(n) 容器扫描跳过）
- 踩坑：CA1068（CancellationToken 须末参）、CA1822（实验版方法改 static）、CA2016
  （WaitAsync 须转发 token）——`-warnaserror` 下全为错误

## 最终状态（用户确认正常）
- 不冻、不未响应、缩略图正常显示、真实宽高比、滚动/触底/添加文件夹全正常
- 构建 0 警告 0 错误、测试 168 全过
- 未提交 6 文件（>5 阈值，已按规则询问用户是否提交）

## 经验补充
- **ConfigureAwait(true) 不是"回到 UI 线程"**：中途任一 await 用 false 脱离上下文后，
  后续 true 无法切回；跨线程回归 UI 的唯一可靠手段是显式 DispatcherQueue 调度
- **服务层需要 UI 亲和时，经构造注入 DispatcherQueue + TCS 桥接**是可靠模式
- **"正常完成"≠"有效工作"**：THUMBWAIT 完成但 0 产出 = 全员静默失败，必须给 catch 加取证日志
  （异常类型 + HResult）；WinRT 的 COMException 常无 Message，HResult 是唯一线索

# 方案 B 落地：位图内存管理三件套（用户实测过关）

## 症状链（随机触底多次后）
1. 点【随机】→ 未响应：WS 曾冲到 **1.5 GB**
2. 触底追加后 LOADTOTAL 随集合规模恶化：200 条 2.8s → 600 条 11.1s → 峰值 38s

## 根因（三层叠加）
1. **位图三重引用**：`ViewModel.Thumbnail` + 条目模板 presenter（ImageBrush/探针，OneWay
   绑定会跟随置空）+ IMemoryCache 条目——**IMemoryCache 的 LRU 淘汰形同虚设**：条目被
   淘汰只移出缓存，ViewModel/presenter 仍持引用，位图不回收，随触底翻页线性累积
2. **IMemoryCache SizeLimit 语义**：原配 `SizeLimit=2000（条）`× 约 400KB/条 = 最高
   524MB 位图常驻；GC（Gen2/LOH 分配风暴）随工作集增长而加剧
3. **切换的清空+重建在垃圾堆上引发 GC 风暴** = 未响应（GC 风暴中 dotnet-stack 的
   EventPipe 注入失败 EndOfStreamException，侧面印证压力）

## 修复（5 文件，未提交）
1. **IMemoryCache 按字节限额**：`SizeLimit=200MB`，条目 `Size = bucket² × 4`（BGRA 估算）
   ——原 `Size=1` 在字节限额下才语义成立
2. **头部瘦身（Trim）**：触底追加后对视口外头部条目「CancelPendingLoad + Invalidate 缓存 +
   `Thumbnail=null`」——条目数据与布局不动（无视觉跳动），滚回时重新解码恢复；
   常驻位图上限 `MaxResidentThumbnails=300`（约 120MB）
3. **reset 彻底释放（用户方案）**：切换视图即对旧列表逐条「取消在途 + Invalidate + 置空」
   ——断开三重引用，内存即时回落
4. **GC 收集移后台线程**：首版在 UI 线程 `GC.Collect(Aggressive+compacting)` 在 GB 级堆上
   **数秒完全暂停 = 未响应**；改 `Task.Run` 后台 + `compacting:false`（压缩是暂停大头）
5. **切换回顶**：`IsQuerying=true` 时两视图 `ChangeView(null,0,null,true)`——ItemsSource
   整体替换后 ScrollViewer 保留旧偏移（WinUI 行为），新内容从中部显示

## 验证（用户实测）
- 随机触底多次 → 点【随机】：置顶、正常加载、**无未响应**
- 触底后切目录：正常；长时间滚动 UI 可交互；单条解码耗时全程恒定（1.1s 含排队）
- 构建 0 警告 0 错误、测试 169 全过

## 经验补充
- **IMemoryCache 的 LRU 只管缓存自身，管不了外部强引用**——位图类对象被 VM/模板持有
  时必须主动「Trim + Invalidate + 置空」三步走，否则淘汰机制纯摆设
- **`GC.Collect` 阻塞+compacting 在 GB 级堆上是 UI 暂停元凶**——大清理一律
  `Task.Run` 后台 + 非 compacting，宁可竞争不可停表
- **WinUI 的 ScrollViewer 在 ItemsSource 整体替换后保留旧偏移**——切视图必须显式回顶

## C1 追加：哈希分桶目录（用户提议后采纳）
- 用户问「文件名是否可按 md5 保存，md5{1-2}/md5{3-4}/md5.ext」——结论：
  **内容 md5 做键不可行**（命中也须全量读源文件算哈希，抵消磁盘缓存收益；
  失效判据用 mtime+size 指纹成本差三个数量级）；**分桶结构合理**，采纳
- 用户给的两级 65536 桶对十万级条目过细（桶比文件多），改**一级 256 桶**
  （sha256(路径) 前 2 hex），10 万条目每桶约 400 条
- 结构：`{bucket}-{hash12}.px` → `{hash前2hex}\{bucket}-{hash12}.px`；
  同一文件全部档位聚同桶，删除/扫描局部性好
- 实现：`GetEntryRelativePath` + 初始化递归枚举（EnumerationOptions RecurseSubdirectories）
  + StoreAsync 懒建子目录；表 key 用相对路径，`Path.Combine(_directory, key)` 各处通用
- 测试新增「条目按哈希分桶存放」用例，其余 GetFiles 断言改 SearchOption.AllDirectories；
  测试 136 全过

## 【重大破案】切换卡顿根因 = reset 释放把磁盘缓存删光
- 现象：A↔B 切换每次 200 条全量重解码 4~12 秒；多次切换后未响应
- 埋点定位三步：①DISK/BITMAP 埋点发现 miss 且 UI 建位图 65~320ms/条；
  ②DISKINIT（Task<int> + 启动埋点）排除扫描失败——OnLaunched 的 `_ =` 会静默吞
  InitializeAsync 异常，改为 await + 记录；③**文件数 53 条全在 21:46**（200 条被删光）
- **根因**：方案 B「reset 彻底释放」对旧列表逐条 `_thumbnails.Invalidate(path)`——
  磁盘层引入前它只清内存缓存（合理）；磁盘层引入后 Invalidate 连坐删磁盘条目，
  **每次切换清空上一目录全部缓存**，磁盘层形同虚设 + BITMAP 洪峰（UI 串行解码）→ 未响应
- **修复**：语义拆分——`Invalidate`=内容真失效（清内存+清磁盘）；
  新增 `Release`=仅释放内存位图（保留磁盘）。GalleryViewModel 两处
  （reset 释放 / 头部瘦身）改用 Release；构建 0 警 0 错待实测
- 剩余已知项：BITMAP（UI 线程逐条 SetSourceAsync 解码）200 条整页提交仍要
  数秒——双重解码问题（编码字节→UI 再解码），SoftwareBitmapSource 直通可根治，列 C2

## SoftwareBitmapSource 直通（根治 UI 线程解码，用户复测菜单仍卡后实施）

- API 证实（官方文档）：WinUI3 SoftwareBitmapSource : ImageSource、
  ThreadingModel.Both + Agile（任意线程创建/使用）、方法名 SetBitmapAsync（非 UWP 的

- 改造：GetThumbnailAsync 返回 ImageSource?（原 BitmapImage?）；bytes →

  ——整条管线零 UI 线程工作；DispatcherQueue 依赖整体删除（构造签名变两参）
- 消费面极小：ThumbnailPresenter.Source 本就是 ImageSource? 零改动；查看器只用
  GetDimensionsAsync；MediaItemViewModel 4 处类型改 ImageSource
- 行为退化项：VM.GetPixelDimensions 恒 null（SoftwareBitmapSource 无像素尺寸）——
  宽高比主路径由索引回填+探针覆盖，正常数据不触发；淡入门闩（探针 Image.ImageOpened）
  是控件级事件，对 SoftwareBitmapSource 仍应触发（待实测确认）
- 踩坑：XamlCompiler 生成代码（GalleryPage.g.cs 的 Update_Thumbnail）缓存旧类型
  BitmapImage 导致 CS1503——dotnet clean 即解；直接删 obj 被安全删除工具拦截（OneDrive）

## 直通首版翻车与修正（用户实测：缩略图不显示 + 闪退）
- 教训：文档 Both/Agile 元数据不可信——SoftwareBitmapSource 虽标注 Agile，
  但作为 XAML DependencyObject 实际有 UI 亲和，线程池创建后挂视图树 → 原生闪退
  （crash.log 无托管记录，绕过 UnhandledException）——与 BitmapImage 0x8001010E 教训同源
- 缩略图不显示：探针 Image 的 ImageOpened 对 SoftwareBitmapSource 不触发（或不可靠）
  → 淡入门闩永不满足 → ImageLayer 恒为 Opacity=0（淡入前不可见）
- 修正：管线拆两段——bytes→SoftwareBitmap 线程池解码（重 CPU 留后台）；
  new SoftwareBitmapSource + SetBitmapAsync 回 UI 线程（仅内存拷贝 ~1ms，
  仍远优于旧 SetSourceAsync 完整解码 ≥200ms）；DispatcherQueue 构造参数恢复
- 门闩适配：ThumbnailPresenter.ApplyImageSource 中 Source is SoftwareBitmapSource
  && State==Loaded → 立即 _imageOpened=true + 补挂起的淡入；ApplyVisualState 挂起条件
  加 Source is not SoftwareBitmapSource（State 先/后到两种顺序都覆盖）
- 构建 0 警 0 错待实测
