## 设置页重构（Win11 行级卡片风格）+ 幻灯片设置

按用户确认的三项决策实施：头部带卡片、内容块整体居中（720）、行级条目（Win11 风格）。

**功能变更**
- 移除设置页的「视图」「缩略图大小」两项，改由图库页工具栏「显示和大小」菜单独占。
- 主题切换控件由 RadioButtons 改为 ComboBox（跟随系统 / 浅色 / 深色）。
- 新增幻灯片设置：间隔时间（NumberBox + 「秒」单位）、切换模式（滑动 / 淡出 ComboBox）。
- 查看器按设置播放转场动画：滑动为新旧图反向位移，淡出为交叉透明度。

**关键实现要点**
- 转场动画在**代码后置**现场创建 Storyboard，不用 Resources 里的 XAML Storyboard——
  后者依赖 TargetName 的 namescope 解析，直接以元素对象作动画目标更可靠。
- 转场请求发自解码 await 之后（可能已在线程池），页面须经 DispatcherQueue.TryEnqueue 切回 UI 线程。
- 动画每轮重建并复位起始值：FillBehavior 默认 HoldEnd，上一轮压到 0 的 Opacity 若不复位，
  下一轮旧图一进场就是全透明，等于没播转场。
- NumberBox 清空输入时 Value 为 NaN（不是 0），写回设置前必须拦截，否则被钳制成 1 秒而输入框仍为空。
- 查看器不反向依赖设置服务，由 MainWindow.ApplySettings 推送；放映途中改设置即时生效
  （ApplySettings 内部 Stop→改 Interval→按需 Start，保留播放状态）。
- 幻灯片间隔默认值保持 5 秒未改（方案曾提改为 3 秒，理由不充分，按「不做未要求的变更」保留）。

## 追加 5（修正追加 4）：hover 失效的真正根因

- 用户要求 hover 色「与左栏 panel 菜单一致」。查包内 generic.xaml 实测色值（浅色主题）：
  `ControlFillColorSecondary` = `#80F9F9F9`（Button 默认 hover，80% 浅灰实色，其实相当明显），
  `SubtleFillColorSecondary` = `#09000000`（左栏 NavigationViewItem hover，3.5% 黑薄层，很微妙）。
- **但换色不是关键**。真正根因：SettingsButton 元素上有 `Background="Transparent"` 本地值，
  经 TemplateBinding 传入模板根 Grid（TemplatedParent 优先级 3），
  而 VisualState 的 hover/pressed Setter 只到 Style Setter 级（优先级 5）→ **覆盖不了，hover 永远不生效**。
- 修正：删掉元素上的 `Background="Transparent"`，改在 `Button.Resources` 覆盖三键
  `ButtonBackground`（→ SubtleFillColorTransparentBrush）/ `PointerOver`（→ SubtleFillColorSecondaryBrush）
  / `Pressed`（→ SubtleFillColorTertiaryBrush），从而与左栏菜单完全一致，且随主题自动变化。
- **佐证**：图库页 `ToolBarButtonStyle` 用 Style Setter 设透明（与 VisualState 同级、后者后应用），
  故其按钮 hover 正常——同一项目内两种写法，效果相反，是很干净的对照。
- 该结论已上升写入 MEMORY.md（WinUI 3 平台约束章节），排查「按钮无 hover」时优先查本地值透明。
- 涉及文件：src/Pixbian/Views/MainWindow.xaml（单文件）

## 追加 10：开关真正贴右 + 防御性 OffContent 清空

- 用户反馈「依旧没有达到要求」：开关仍偏左、右侧仍有「关」字。
  上轮我设了 `HorizontalAlignment="Right"` + 删除了状态文字 TextBlock，
  但**仍有问题**，根因两条：
  1. **Auto 列宽 = ToggleSwitch 自然宽**，列内 `HorizontalAlignment="Right"`
     在「列宽 = 子元素宽」时**无视觉差异**，开关仍占满整列 = 看起来在 Column 2 左边缘。
     真正让开关贴右的不是对齐属性，而是 Grid 的 **Padding 覆盖**——本行
     `Padding="16,12,0,12"`（右 0）让开关延伸至 Border 内右边缘。
  2. **「关」字来源**：`ToggleSwitch` 默认的 `OffContent` / `OnContent` 在模板里
     会按系统语言或资源字符串显示占位文字（不再是 null）。**外部不显式设空字符串**，
     模板会渲染默认内容（Win11 参考图里也是靠 OffContent="On" / OnContent="Off"
     显示状态的，本项目要的是无文字的纯开关）。
- 改动（src/Pixbian/Views/SettingsPage.xaml）：
  - Grid 加 `Padding="16,12,0,12"`（覆盖 Style 的 16,12，右 0）；
  - ToggleSwitch 加 `OffContent=""` + `OnContent=""`（显式清空默认内容）。
- **可复用结论**：Grid 内 `Auto` 列内单子元素的水平对齐**没有视觉差异**，
  「列内 Right 对齐」只在列宽 > 子元素宽时才有意义；要让控件贴父容器边缘，
  该用 Margin/Padding 调节而非对齐属性。

## 追加 12：修复 WMC0035 —— Border 只能有一个 Child

- **首次真实构建**（用户执行 `Pixbian.ps1`）暴露编译错误：
  ```
  SettingsPage.xaml(508,22): XamlCompiler error WMC0035: Duplication assignment to the 'Child' property of the 'Border'
  SettingsPage.xaml(514,22): 同上
  ```
- 根因：`Border` 是 `Decorator`，**只能有 1 个 `Child`**。我上一轮把 Expander 移入 Border 时，
  错误地把「分隔线」和「Expander」放在了 `</StackPanel>` **之后**（StackPanel 外、Border 内），
  导致 Border 同时容纳 StackPanel / 分隔线 / Expander 三个子元素 → 第 2、3 个重复赋值 Child。
- 修复：把 `</StackPanel>` 移到 Expander 之后，让 StackPanel 成为 Border 的唯一 Child，
  开关行 + 分隔线 + Expander 全部封在 StackPanel 内；顺带修正了缩进（分隔线/Expander 由 20 → 24）。
- **教训**：前十几轮我都没有终端工具、无法构建，所有结构改动都未经编译验证，
  这次一构建就暴露了结构错误。XAML 结构性错误（Child 重复赋值、标签不配对）IDE 的 lint
  往往**不报**（实测 read_lints 返回 0 诊断），必须以 `dotnet build` 为准。
  该结论已写入 MEMORY.md（WinUI 3 平台约束章节）。

## 追加 14（定案）：开关没贴右的真凶 —— ToggleSwitch 的 MinWidth=154

- 用户提供**完整应用截图**后终于定位真凶：`ToggleSwitch` 默认样式强制
  `MinWidth="{StaticResource ToggleSwitchThemeMinWidth}"`，该值 = **154px**（generic.xaml:8485 实证）。
  控件内开关轨道只占左侧约 40px，**右侧 ~114px 是模板空白**（OffContent 列虽为空，
  MinWidth 仍把控件撑到 154px）。
- 由此产生的两个视觉问题一并解释：
  1. **开关偏左**：开关轨道距 ToggleSwitch 右边缘 114px，无论外面怎么右对齐，
     视觉上开关永远离右边缘 114px+；
  2. **副标题与「关闭」挤在一起**：720 宽卡片被 154px 控件 + 长副标题挤爆，
     内层 * 列剩余空间不足，文字重叠。
- 修复：ToggleSwitch 加 `MinWidth="0"`，控件宽收缩到内容实际宽（约 52px），贴右且不再挤压文字。
- **可复用结论（已可入 MEMORY）**：WinUI `ToggleSwitch` 默认 MinWidth=154px，
  模板右侧大面积留白。需要「纯开关贴边」的场景必须显式 `MinWidth="0"`，
  否则开关视觉永远偏左 114px，且会挤压同行文字。
- 涉及文件：src/Pixbian/Views/SettingsPage.xaml（单文件）

## 追加 19：内容块达不到 960 的根因 —— Center 使 StackPanel 收缩

- 用户改 MaxWidth=960 后实测仍显示内容自然宽（约 340px）。
  根因：`StackPanel MaxWidth="960" HorizontalAlignment="Center"` 中，
  **Center 对齐会让面板收缩到内容自然宽**（行内元素全自适应，自然宽远小于 960），
  MaxWidth 只是上限、不是目标宽——这个组合对「设定期望宽」完全无效。
- 修复：`HorizontalAlignment="Center"` → `"Stretch"`。WinUI/WPF 标准行为：
  **Stretch + MaxWidth = 撑到 min(可用宽, MaxWidth)，实际宽小于可用宽时框架自动居中摆放**。
  一举两得：窄窗口撑满、宽窗口限宽居中。
- **可复用结论（应入 MEMORY）**：想要「限宽 + 居中」容器，必须 Stretch + MaxWidth；
  写 Center 的是 size-to-content，MaxWidth 形同虚设。这是 WPF/UWP/WinUI 通用的布局陷阱。

## 追加 20：限宽居中改用代码后置计算对称 Margin（定案）

- Stretch 修复后用户实测内容**靠右**（约 549px 自然宽贴右缘，左侧大片空白）——
  「Center 收缩 / Stretch 超限后如何摆放」的框架对齐细则反复不可预期，纯 XAML 方案三连败。
- 定案方案：**ScrollViewer.SizeChanged 中代码计算对称 Margin**——
  `slack = max(0, (视口宽 - 48 - 960) / 2)`，`ContentRoot.Margin = (slack, 0, slack, 0)`；
  StackPanel 去掉 HorizontalAlignment（默认 Stretch 撑满），MaxWidth 保留为声明意图。
  Margin 是最底层布局原语，行为零歧义：宽 < 960 撑满、> 960 恒居中。
- **方法论教训（重要）**：连续多轮布局问题（贴右、限宽、居中）都在「框架对齐行为的细节」上
  反复试错，每轮消耗一次构建。**对齐语义必须精确表达时应直接用 Margin/代码计算**，
  HorizontalAlignment 只用于「无歧义的贴边/拉伸」；同类问题以后直接跳到 Margin 方案。
