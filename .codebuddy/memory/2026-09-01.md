## 骨架屏淡入：探针 ImageOpened 后延迟一渲染帧（继续优化 B 方案）

### 背景
上一轮（2026-08-31）已确认闪烁根因：`ImageBrush` 无「可绘制」信号，改用透明探针 `Image` 的
`ImageOpened` 作门闩，闪烁大幅改善。但用户反馈「没有渐变的效果 + 偶发闪一下」。

### 分析（本轮根因）
探针 `ImageOpened` 只保证**探针 Image 自身**可绘制。探针与 ImageBrush 虽共享同一 BitmapImage
（纹理只解码一次），但 **ImageBrush 的纹理上传到 GPU 可能比探针晚一渲染帧**。立即播放动画时，
动画前段淡入的是空白（ImageBrush 无纹理），纹理就绪瞬间图片突现 —— 观感即「无渐变 + 偶发闪」。

### 实施（仅 ThumbnailPresenter.cs）
- 新增 `PlayFadeInNextFrame()`：`CompositionTarget.Rendering` **单次订阅**，下一渲染帧回调后立即解除。
  回调内校验 `State==Loaded && _imageOpened` 才 `ShowImageWithFadeIn()`（等待期间可能滚走/失败）。
- 两条淡入路径统一走 `PlayFadeInNextFrame()`：
  ① `OnImageOpened` 消费 `_pendingFadeIn` 时；② `ApplyVisualState` 中 `isSkeletonToImage && _imageOpened` 直接路径。
- 新增 `CancelPendingFrame()`：`DataContextChanged`/`Unloaded` 时解除未触发的 `Rendering` 订阅，
  防止容器复用后残留回调误触发。
- 字段 `_pendingRenderFrame` 防重复订阅。

- `dotnet test Pixbian.sln`：**通过**（160 个：Core 115 / WebServer 33 / Imaging 12）

- 用户实测（待反馈）：应看到骨架 → 图片 250ms 渐变，无突现感

### 教训
- **Image 控件的 ImageOpened 与其享 BitmapImage 的 ImageBrush 渲染不同步**：前者只保证自身
  可绘制，后者纹理上传可能晚一帧。共享资源的两条渲染路径就绪时机需分别考虑。
- 等「下一渲染帧」用 `CompositionTarget.Rendering` 单次订阅（回调即退订），比固定延迟更精确、
  无魔法数；但必须配套 `CancelPendingFrame` 处理容器复用/卸载。

# 图库页工具栏：全选菜单图标 + 快捷键 + 按钮悬停底色

## 需求与实现
1. 「更多」菜单两项加图标并应用快捷键：全选 `E8B3` Ctrl+A、不选择任何项目 `E711` Esc + Ctrl+D
2. 工具栏按钮 hover 需要可见的背景色

## 关键结论（可复用）
- **WinUI 3 的 Button 悬停用 Storyboard（`ObjectAnimationUsingKeyFrames`）而非 `VisualState.Setters`**，
  动画优先级最高，本地值 `Background="Transparent"` **挡不住它**。所以「设了本地值导致 hover 失效」是错的判断方向。
  本项目 hover 看不见的真因是：默认 `ButtonBackgroundPointerOver`（ControlFill 次填充）铺在纯白内容区上太淡。
- 修法沿用项目既有模式：在 Page.Resources 用 `<StaticResource x:Key="ButtonBackgroundPointerOver" ResourceKey="SubtleFillColorSecondaryBrush"/>` 覆盖主题键（约 6% / 9% 覆盖），Pressed 对应 `SubtleFillColorTertiaryBrush`。
  App.xaml 的 NavigationView 项已用同一对键，观感与系统一致。
- **主题键覆盖不要放进 `Style.Resources`**：Style 的 Setter.Value 是单一实例，多个元素共享同一 ResourceDictionary
  会触发「已是其他元素的子项」异常。覆盖放在 Page.Resources（页面内只有工具栏用 Button，无副作用）。
- **快捷键用页面级 `Page.KeyboardAccelerators`**，`KeyboardAcceleratorTextOverride` 只负责菜单上的提示文本。
  Accelerator 沿焦点树向上查找：焦点在页面内才生效；焦点停在左侧 NavigationView（页面外的兄弟节点）时不响应，
  这是平台行为，不是 bug。菜单展开时 Esc 会被 MenuFlyout 先消费（关闭菜单），属预期。
- 全选快捷键需先切到选择模式：非选择模式下条目无复选框与遮罩，直接全选没有任何视觉反馈。

# 启动崩溃排障：`##RRGGBB` 非法颜色值（可复用的诊断路径）

## 症状
`.\Pixbian.ps1` 退出码 0、构建 0 Error，但窗口不出现；`Get-Process Pixbian` 计数为 0（启动即崩）。

## 诊断路径（按序执行，每步都有明确判据）
1. `Get-Process -Name <App>` 计数 → 0 即「启动即崩」，非「构建失败」。
2. `Start-Process -PassThru` + `WaitForExit` 拿退出码 → `-1073741189` = `0xC000027B`。
3. 查 Windows 应用日志（**关键一步**）：
   `Get-WinEvent -FilterHashtable @{LogName='Application'; Level=1,2; StartTime=...}` 筛 `Pixbian`，
   得到「出错模块 `Microsoft.UI.Xaml.dll` + 异常码 `0xc000027b`」。
   - `0xc000027b` = stowed exception，**托管堆栈不在 `.NET Runtime` 日志里**（该日志为空），
     不要在那里浪费时间；它只说明「XAML 层抛了异常」。
4. **`git status --short` 列出全部改动文件**，逐个 `git diff` —— 崩溃源往往不在你以为改的那个文件。
   本次崩溃在 `App.xaml`，而我全程只改了 `GalleryPage.*` 与 ViewModel。

## 根因
`App.xaml` 主题字典里颜色写成双井号：`Color="##1D2327"`、`Color="##F0F0F1"`。

## 关键结论（重要）
- **XAML 编译期不校验颜色字面量格式**：`##RRGGBB` 能一路通过 `dotnet build` 且 0 Error 0 Warning，
  只在运行时解析时才抛。所以「构建成功 + 启动崩溃」的第一嫌疑就是 XAML 里的属性值非法。
- 同理，`dotnet build` 通过**不能**证明 XAML 运行时正确，只有真正启动才能验证。

## 修复
`##1D2327` → `#1D2327`（2 处）、`##F0F0F1` → `#F0F0F1`（1 处）。保留用户的配色意图
（Default 主题下 Pane 深色 `#1D2327` + 内容区浅色 `#F0F0F1`），只修语法。

- **菜单改为「数据定义 + 工厂方法」**：`SortKeyItems` / `SortDirectionItems` / `KindItems` /
  `LayoutItems` / `SizeItems` 静态定义，三个 `BuildXxxItems(IList<MenuFlyoutItemBase>)` 构建方法

- **每次 Opening 重建菜单**（`MenuFlyout.Opening` → `RebuildMenu`）：勾选态与可用态按当前状态生成，

- **溢出测算必须基于宿主 Grid 而非 StackPanel**：StackPanel 宽度由内容决定，隐藏按钮后它随之收缩，

  只在 `ActualWidth > 0` 时更新缓存，且首次布局完成前跳过测算。
- 收起顺序从右往左：显示模式 → 筛选 → 排序 → 幻灯片 → 选择。
- `IList<MenuFlyoutItemBase>` 而非 `IList<MenuFlyoutItem>`：`MenuFlyoutSeparator` 只继承
  `MenuFlyoutItemBase`；`MenuFlyoutSubItem` 才是 `MenuFlyoutItem` 的子类。

# hover 图片显示「Ctrl+A」：两次修复（第一次失败）

## 现象
hover 图片条目，文件名 ToolTip 里混入「Ctrl+A」。

## 根因（官方文档 by design）
声明 `Page.KeyboardAccelerators` 后，框架会把按键组合追加到作用域内**所有控件**的 ToolTip 上
（`MenuFlyoutItem` / `ToggleMenuFlyoutItem` 除外）；定义多个时**只显示第一个**（故只见 Ctrl+A）。

## 第一次修复失败（重要教训）
给两个条目模板的 Border 加 `KeyboardAcceleratorPlacementMode="Hidden"` —— **无效**，用户反馈"还是有字"。
文档措辞是「its *associated* keyboard accelerator」，指向拥有 accelerator 的元素，
但把 Hidden 移到 Page 上同样未经验证。

**教训：这类"框架自动附加"的行为，光靠推理+编译通过不能交付。**第一次我就是这样交付的，结果错了。

## 最终方案（确定性，不依赖框架黑盒）
**不用 `KeyboardAccelerator`，改走代码后置 KeyDown**——没有 accelerator 就不可能有该行为：
- 删除 `GalleryPage.xaml` 的 `Page.KeyboardAccelerators`（Ctrl+A / Ctrl+D / Esc）
- 删除 `OnSelectAllAcceleratorInvoked` / `OnSelectNoneAcceleratorInvoked` 两个方法
- 在既有 `OnGalleryPageKeyDown` 里加：Ctrl 分支加 A / D，非修饰加 Escape

**与项目既有约定一致**：Ctrl+C 复制、Delete、F2、F3 本就是 KeyDown 实现的，它们从不引发该问题
——这本身就是"方案可行"的现成证据。

## 可验证的判据（区别于第一次）
修复后全项目 `KeyboardAccelerator` **零声明**（扫描确认），剩余 6 处全是
`KeyboardAcceleratorTextOverride`（菜单文本，豁免且是正确用法）。污染源被物理移除，不依赖对框架行为的推断。

## 行为变化（已权衡）
作用域从「窗口级」（`ScopeOwner=null`）变为「焦点在本页内」。与项目其他快捷键一致，
且用户使用全选时焦点本就在图片列表内，实际无差别。

# 消除硬编码色值（规范 §4.1【必须】）

## 违规点
GalleryPage 视频时长角标：`Background="#80000000"` ×2、`Foreground="White"` ×2。

## 为什么不能用系统语义键替代（关键判断）
- `SolidBackgroundFillColorBaseBrush` 实测三主题取值：`#202020`(Dark) / `#F3F3F3`(Light) / `#FF0000`(HC)。
  浅色主题下变浅灰，配白字**完全不可读**。
- `TextFillColorInverseBrush` 存在，但其语义**正是「随主题反转」**，与「恒深底+恒白字」的需求相反。
→ 结论：**浮在图片内容之上的角标，颜色不应随主题变化**（图片内容本身不变）。
  正确做法是自建语义键并在两个主题取同值，而非套用会反转的系统键。

## 实现（2 个文件）
`App.xaml` 两个主题字典各加一对（Default 与 Dark **取同值**，注释写明是有意为之）：
- `PixbianItemOverlayBrush` = `#80000000`（半透明黑底）
- `PixbianItemOverlayForegroundBrush` = `#FFFFFF`（白字）

`GalleryPage.xaml` 两处角标改 `{ThemeResource PixbianItemOverlayBrush}` /
`{ThemeResource PixbianItemOverlayForegroundBrush}`。

## 关键认识
- **「两主题同值」不等于「漏配」**，但必须在注释里写明理由，否则后来者会当成 bug 改掉。
  角标/遮罩这类压在图片上的元素属于此列；而 Pane/内容区这类 UI 底色必须随主题变。
- 规范 §4.1 禁的是「业务 XAML 里散落硬编码」，**资源字典内的 `Color="#xxx"` 是合法位置**
  ——全集现已集中在 App.xaml（16 处），业务 XAML 零硬编码。

# 左栏圆角：根因是模板硬编码的 RightCornerRadiusFilterConverter

## 需求演化（用户三轮修正，价值很高）
1. 「左栏 panel 不需要圆角，内容区只需要左上的圆角，现在是左栏右上和右下有圆角，这是错误的」
2. 我在几何冲突上给用户三选一，用户选「恢复 WinUI 默认：内容区左上 8px 圆角紧贴左栏，
   圆角处露出左栏深色」（**即承认上一轮判为"错误"的效果其实是他要的**）

## 左栏圆角的真正来源（generic.xaml 2.3.6 实测行号）
- **17667** `RootSplitView`：
  `CornerRadius="{Binding Source={ThemeResource OverlayCornerRadius}, Converter={StaticResource RightCornerRadiusFilterConverter}}"`
  `RightCornerRadiusFilterConverter` 把 OverlayCornerRadius(8,8,8,8) 转成**只保留右侧**的 **(0,8,8,0)**。
- **35818** `PaneRoot`：`CornerRadius="{TemplateBinding CornerRadius}"` → 继承上值。
  → 左栏右上角 8、**右下角 8**，与用户「右上和右下有圆角」的描述**完全吻合**。
- 17343 行那个 `OverlayCornerRadius` 是 **NavigationView 自身**的 CornerRadius（不是 FlyoutPresenter），
  但模板根 `RootGrid` 不用它，只有 RootSplitView 经 Converter 消费。

## 三种消除方式的效果（全部实测）
| 方式 | 结果 |
|---|---|
| `NavigationView.Resources` 局部覆盖 OverlayCornerRadius=0 | **无效**。Binding 的 Source={ThemeResource} 解析绕过元素级资源 |
