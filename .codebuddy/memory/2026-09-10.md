## 补充：注册已成功（同日后续）

最终包：`Pixbian_1.0.0.0_neutral__h94vh5tyrgn60`

真正的四个关键点：
1. **必须用两级证书**：单张自签证书同时充当根与叶子时链构建不稳定（signtool 报 `0x80096019`、Add-AppxPackage 报 `0x800B0109`）。改为根 CA（`CN=Pixbian Root`）签发代码签名叶子（`CN=Pixbian`）后 `signtool verify` 立即通过。
2. **根证书必须导入 LocalMachine**：包由 AppX 部署服务（系统上下文）校验，只看得见本机存储。仅导入 CurrentUser 会报 `0x800B010A`（无法建立到信任根颁发机构的证书链）。导入 `LocalMachine\Root` 需管理员。
3. **PFX 含两张证书时签名必须指定 `/sha1 <叶子指纹>`**，否则 SignTool 报"找到多个证书"而不签名。
4. **`Add-Type -AssemblyName System.Security` 会破坏 `CertificateRequest` 的类型解析**（构造函数的密钥参数被解析成 null）。因此脚本不用它，也因此不设置 EKU（`OidCollection` 在该程序集内）；未限定 EKU 的证书等同全用途，代码签名成立。

## 实施：P1-3 键集分页（用户选方案 A，FTS5 部分经评估放弃）
- **关键发现（重要，勿再走弯路）**：FTS5 对中文子串搜索不可行——分词器按空白/标点切词，中文整句成单 token；`trigram` 分词器要求查询 **≥3 字符**，中文搜索词以 2 字居多，FTS5 无法加速且语义劣于 `LIKE '%词%'`。结论：放弃 FTS5 保留 LIKE；如未来需要可评估混合路径（≥3 字符走 trigram，其余回退 LIKE）。
- **键集分页实施**：`MediaQuery.Keyset` + `KeysetCursor(LastId, LastText, LastNumber, LastUtc)`（按排序键分字段避免装箱）；`QueryAsync` 非随机排序走「排序值 + id」双键比较（拼接仅内部列名常量，值全参数化；modified_utc 文本字典序=时间序，BINARY 比较与 ORDER BY 天然一致）；旧 OFFSET 路径保留兼容。`GalleryViewModel` 以 `_items[^1].Item` 构造游标，删除收缩后天然避免 OFFSET 错位。
- 踩坑：首版按「isText 二分」绑定游标，ModifiedDate 的值在 `LastUtc` 却被绑成 `LastText`（null）→ 第二页恒空。改为 `ResolveKeysetCursor` 按排序键三分支解析并复用 `FormatUtc`，游标格式与库内存储不漂移。
- **10 万条实测**（临时基准，已删）：插入 31.6 s；OFFSET 第 251 页 151 ms vs 键集 1 ms = **151×**，OFFSET 随页深线性恶化、键集恒定。
- 验证：build -warnaserror 0 警告 0 错误；测试 273 通过（Core 221 / Web 38 / Imaging 14）。
- 基准方法论：键集对比必须取**中部页**（末页之后无剩余条目，键集结果为空集无法对比）。

## 诊断：任务栏图标"背景不透明"
- 现象：生成的 app.ico 在任务栏显示背景不透明。
- 排查结论：文件透明机制正常，非 gen-icon.ps1 bug。
  - app-icon.svg 唯一绘制元素为内嵌 base64 PNG 的 `<image>`。
  - 内嵌位图主体为不透明深灰 #393A3A（占宽约 84%），即"带底色的成品图标图"，四角/边缘透明；中心前景。
  - 生成的 app.ico（16/32/48/256）四角 alpha 均为 0，透明通道保留正常。
  - 仓库无 .appxmanifest → unpackaged 应用，任务栏图标取自嵌入 EXE 的 app.ico。
- 根因：用户看到的"不透明背景"= 图标自带的深灰底色方块，被如实渲染进 ICO。非文件/脚本缺陷。

## 实施：.NET 10 迁移试点（分支 feature/net10-migration，同日第九批）

## 百万条规模实测与首屏排序修复（同日续）

- **触发**：用户告知后期库规模约 **100 万条** → 此前基于 10 万条的判断需重新验证。
- **实测方法**：临时基准类（递归 CTE 灌 100 万条、`modified_utc` 逐行递增避免排序退化、结果增量追加到 `C:\Temp\bench.txt`、Dispose 删库），**测完已删除临时文件**。

- **⚠️ 关键发现（首屏不走索引）**：无游标的首屏走 `ORDER BY CASE WHEN @sortKey = ... END, ..., file_name ASC`——**表达式排序无法使用索引**，100 万行逐行求值再排序 → 331 ms；同语义的原生列排序 0 ms。改为按内部常量列名拼接（新增 `ResolveOrderClause`）后复测 **331 ms → 0 ms**。**教训：只要 ORDER BY 写成 CASE 表达式，索引就全线失效；参数化排序键与“能用索引”是互斥的，正确做法是内部常量列名拼接。**
- **⚠️ 同时修掉的正确性缺陷**：随机排序首屏用 `(id * @seed) % 1000003`、后续页游标用 `random_rank` —— 两者是**不同序列**，随机翻页会重复或遗漏；副排序键亦由 `file_name` 统一为 `id`（首屏与键集分支副排序键不同，相同主排序键取值下会错位）。

## 修复：Build-Pixbian.ps1 报 CS7065 + 21 个 XAML 错误（同日续）

- **现象**：运行 `scripts\Build-Pixbian.ps1` 后 `Pixbian` 项目失败，21 错误 1 警告：`CSC error CS7065: 生成 Win32 资源时出错 -- Unable to read beyond the end of the stream`，并连锁 `WMC0001 Unknown type` / `WMC0909` / `WMC1111` / `WMC9999`（XAML 编译器 Pass2 因主程序集未产出而找不到 `LocalAssembly`）。
- **根因**：本轮扩展 `New-AppIcon.ps1` 时，ICO 组装改用 `Get-PngBytes` 函数。PowerShell 函数返回的 `byte[]` 会被流展开成 `object[]`，而 `[System.IO.BinaryWriter]::Write(byte[])` 是重载方法，对 `object[]` 输入重载解析失败、**静默不写任何字节** → `app.ico` 只剩 74 字节的 ICONDIR + 目录项（4 个图像帧长度全为 0）。scale 变体能正常生成，是因为 `File.WriteAllBytes` 是强类型参数、PowerShell 自动把 `object[]` 转回 `byte[]`，绕过了该坑。
- **修复**：ICO 组装处对 `Get-PngBytes` 返回值显式 `[byte[]]` 强转再传给 `BinaryWriter.Write`。其余逻辑（目录项长度/偏移计算）不变。验证：`app.ico` 恢复 9385 字节（9.4 KB，4 个 PNG 帧 `BitConverter` 解析偏移/长度均 OK、签名 `PNG`）；重新 `dotnet build -c Debug` **0 警告 0 错误**，连锁 XAML 错误全部消失。
- **沉淀**：PowerShell 函数返回 `byte[]` → `object[]` 展开 → `BinaryWriter.Write(byte[])` 重载静默失败，是 .NET/PowerShell 互操作的隐蔽坑；手工拼 ICO 必须显式强转。已写入 MEMORY.md PowerShell 坑条目。
- **涉及文件**：`scripts/New-AppIcon.ps1`（仅 ICO 组装两处加 `[byte[]]` 强转）、`src/Pixbian/Assets/app.ico`（重新生成为有效 9.4 KB）。

- **新增 Core**：`Models/UserDataBackup.cs`（文档 DTO + 格式常量）、`Abstractions/IUserDataBackupService.cs`（契约 + `UserDataImportOptions` / `PathPrefixMapping` / `UserDataImportResult`）。导入结果回传 `MusicFolders`——音乐目录存于设置文件而非索引库，数据层不依赖设置服务，由 UI 合并落盘。

  - **策略细节**：收藏取并集（只置位、不清除本地）；评分 `MAX(rating, @rating)` **只升不降**（备份可能较早，覆盖会丢用户后续标注）；分组成员与扫描源均 `INSERT OR IGNORE`（幂等，且不覆盖本机启用状态）。

## 批次④ 增量：路径重映射 UI + 前缀边界校验（同日续）

- **背景**：服务层早已支持 `PathPrefixMapping`，但 UI 未暴露——换盘后导入只能看着「未匹配」而无从处理。
- **UI**：导入确认对话框新增两个输入框（「旧路径前缀（备份中的）」/「新路径前缀（本机的）」，用 TextBox.Header），两者都填才生效，留空表示不改写；`ConfirmImportAsync` 改为返回三元组（确认 / 应用分类归属 / 路径映射），`BackupViewModel.ImportAsync` 增加 `pathMappings` 参数。
- **前缀边界校验（配套修复）**：`ApplyMappings` 原先只做 `StartsWith`，`D:\Lib` 会误命中 `D:\Library\...`——目录名互为前缀极常见（Lib/Library、Photos/Photos_2025），会把用户没打算迁移的文件一并改写。现在要求前缀落在目录边界上（前缀后紧跟分隔符、或前缀自身以分隔符结尾、或整串相等），改写时拼 `To.TrimEnd(分隔符) + 后缀`。
- **测试**：新增「前缀位于目录边界_不误命中同前缀目录」——库里同时放 `E:\Media\a.jpg` 与 `E:\Mediary\b.jpg`，映射 `D:\Lib → E:\Media` 后断言只命中前者；若边界校验失效，`D:\Library\b.jpg` 会被改写成 `E:\Mediary\b.jpg` 并误命中，用例即失败。

- **Core 新增**：`Abstractions/IOneDriveBackupSyncService.cs`（契约 + `BackupSyncResult`）、`Services/OneDriveBackupSyncService.cs`。
  - 探测顺序：环境变量 `OneDrive` → `OneDriveConsumer` → `OneDriveCommercial` → 用户目录下的 `OneDrive`；全失败即不可用。
  - 目标目录：用户指定优先（**必须是绝对路径**——相对路径会被解析到进程当前目录，属静默误写，直接判不可用），否则 `<OneDrive>\Pixbian`。

## 增量：L2 整库快照（导出 + 还原，同日续）

- **定位**：同机灾备与排障取证，**不是跨机迁移**（索引里存的是绝对路径，换机后全部失配；跨机迁移用 L1 用户数据包）。
- **Core 新增** `Abstractions/IDatabaseSnapshotService.cs`；**Data 新增** `Backup/SqliteDatabaseSnapshotService.cs`。
  - **导出**：`VACUUM INTO @target`（一致性在线快照；直接复制库文件可能拿到只写了一半的 WAL 半成品）；目标先写 `.tmp` 再原子替换（VACUUM INTO 要求目标不存在）；目标必须是绝对路径。**参数绑定可用**（已由用例证实）。
  - **还原**：`PRAGMA integrity_check` 校验（只读打开且 `Pooling=false`，避免校验连接延长文件句柄存活）→ `SqliteConnection.ClearAllPools()` → 当前库改名 `.bak-<时间戳>` → **删除 `-wal` / `-shm`** → 复制快照为新库。
    - `.bak` 副本必须保留：还原是「切换到某份快照」，不是「丢弃当前数据」。
    - 删除 WAL/SHM 是必做项：它们是旧库的事务日志，留着会把旧库未提交的数据带回新库，属最隐蔽的一类数据错乱。
  - **还原只保证文件层面正确**：进程内的图库集合、分类与分组仍是旧库的内存副本，界面必须提示用户重启应用（还原完成的对话框已明说）。
- **UI**：「数据与备份」分区新增「备份完整数据库」与「从快照还原」两行；还原前二次确认（明示替换范围与 .bak 保留）。
- **测试**：新增 5 个用例——快照可独立打开且含当前数据、目标已存在时覆盖、还原后内容正确**且旧库仍可从 .bak 恢复**、非快照文件被拒绝且当前库不变、相对路径被拒绝。第三条同时断言「新库内容」与「旧库备份存在」：只断言前者会掩盖「旧数据被直接丢弃」的实现错误。
- **验证**：Core 测试 260 全绿；UI `build -warnaserror` 0 警告 0 错误。
