# 真根因修复：单击图片进入选中（ItemClick 先于 SelectionChanged）

用户实测报「单击图片依然进入选中」，推翻上一轮"基线已满足"的判断。

## 真根因（时序反转）
WinUI ListViewBase 单击条目的事件顺序是 **ItemClick 先于 SelectionChanged**。Round5 的修法
（ItemClick 里 `SelectedItems.Clear()`）清的是**尚未加入的空集合**，随后控件默认逻辑照常把
点击项加入选择 → SelectionChanged 时 `HasSelection=true` → 自动进入分支命中 → 进入选择模式
且该项被勾选。逻辑反证也吻合：若时序相反（SC 先），Clear 会让模式"闪现即退"，用户看到的是
闪烁而非"进入选中"——用户报的是后者，故时序为 ItemClick 先。

## 修复（一次性标志，GalleryPage.xaml.cs 单文件 3 处）
1. 新增字段 `_suppressAutoEnterOnce`：ItemClick 打标（注释写明时序原理）。
2. `OnItemClick`（普通模式）：打标 + 保留 `Clear()`（若某时序下 ItemClick 在后则直接生效，双保险）。
3. `OnSelectionChanged` 开头消费标志：`clickedItemBody=true` 时跳过自动进入并 `grid.SelectedItems.Clear()`
   清除点击副作用；清除引发的再次 SC 为空选择、无分支命中，稳定收敛。
   点击复选框不触发 ItemClick（CheckBox 吃掉点击），标志恒 false，进入模式路径不受影响。

## 场景推演（全部闭环）
- 单击图片：ItemClick 打标 → SC 消费标志 → 拦截进入 + 清除 → 普通、无选中 ✓
- hover 点复选框：无 ItemClick → SC 正常进入模式 ✓
- 选择模式点图片：ItemClick 的 `IsSelectionMode` 分支 return（不打标），Multiple 勾选语义保留 ✓
- 残留风险：普通模式选择恒空，点击必产生选择变化 → 标志必被消费，无残留 ✓

# 按压反馈第二轮：弹簧动画 + 按住移出不回弹修复

## 用户反馈两点
1. 弹性不够自然、太生硬（原 CubicBezier 关键帧 + 80/150ms 固定时长）
2. Bug：按住左键移到图片外，图片下压后不回弹

## 修复 1：改弹簧物理动画（CreateSpringScalarAnimation）
- 关键帧直线插值「速度突变」是生硬感根源；弹簧动画加速度平滑收敛，手感自然。
- 参数：`FinalValue` + `DampingRatio` + `Period=35ms`。
  按下 `DampingRatio=0.9`（近临界阻尼，下压干脆）；回弹 `DampingRatio=0.5`（欠阻尼产生一次柔和回弹）。
  下压深度保持 0.97。弹簧无 Duration，物理自然收敛（约 200-400ms）。
- API：`visual.Compositor.CreateSpringScalarAnimation()`，构建通过——WinUI 3 存在（WASDK/26100）。

## 修复 2：按住移出不回弹（根因与双保险）
- 根因：按住移出条目后 `PointerReleased` 的冒泡路径不可靠（指针 hover 路由随位置变化、
  ListViewBase 内部捕获等），GridView 可能根本收不到 Released。
- 修法：**照片应用式「移出取消按压」**——
  ① `PointerMoved`（handledEventsToo）差异检测：`FindItemContainer(OriginalSource) != _pressedItem`
  即回弹清空；
  ② `PointerExited` 兜底（指针离开 GridView 可视区后 Move 不再触发）。
  语义升级：移出图片即提前回弹（原行为是等 Released），符合主流图片应用交互。
- 原有 Released/Canceled/CaptureLost 三路兜底保留（点击完成在条目内的正常回弹）。

# 卡顿根治：复选框常驻视觉树（Collapsed → Opacity/IsHitTestVisible）

延帧焦点后用户仍报卡顿 → 布局风暴主体（数百可见条目的复选框 Collapsed↔Visible 全量重测量排列）
才是瓶颈，Layout 成本无法靠错峰消除。

## 核心改造（WinUI 性能惯用法）
复选框不再 Collapsed/Visible，改**常驻视觉树 + 渲染属性切换**：
- `Opacity 0↔1`（绑 IsSelectionMode，经新转换器）——Opacity 是合成层属性，切换零 Measure/Arrange 成本；
- `IsHitTestVisible false↔true`（绑 IsSelectionMode）——防 Opacity=0 时命中穿透（框看不见却能被点）；
- PointerOver VisualState Setter 覆盖 `Opacity=1` + `IsHitTestVisible=True`（State Setter 优先于本地
  绑定值，既有已验证模式）：普通模式 hover 浮现且可点、选择模式绑定值本为 1/True 无副作用。
- 新增 `Converters/BoolToValueConverter`：bool→string 配置值按绑定目标类型（double/bool）显式转换
  ——XAML attribute 配置的 TrueValue/FalseValue 恒为字符串，靠绑定引擎隐转会静默失败；
  Page.Resources 注册 `BoolToSelectionOpacity`（1/0）与 `BoolToSelectionHitTest`（True/False）两实例。

## 效果
进入/退出选择模式从「数百条目全量重布局」降为「一次批量合成属性变更」——布局风暴消失。
页头整行替换与 SelectionMode 切换的小规模布局仍在（条目级成本已消除）。

- 常驻复选框参与 Grid 测量（~32px），当前条目最小档远大于此，无撑大风险；未来若支持 <40px 微缩略图需复核。
- Opacity 0 + IsHitTestVisible=false 的元素不响应指针，与 Collapsed 行为一致。

# 卡死根因：取消传播链三处缺陷（多次切换后触发）

## 用户反馈
多次切换文件夹后应用仍卡死。进程已被用户强杀，无法抓 dump，按代码链路排查。

## 三处确认缺陷与修复（3 个文件）
1. **CTS 取消后立即 Dispose（核心）**：`CancelPendingLoad` 与 `EnsureThumbnailAsync`（248-249）
   同款 `Cancel(); Dispose();`——下游在途解码任务仍持有 Token，稍后访问已释放 CTS
   （`GetThumbnailAsync` finally 的 `ThrowIfCancellationRequested`、`WaitAsync` 取消传播）抛
   **ObjectDisposedException** → 炸断整页解码 `WhenAll` 提交链 → 后续条目永远无图。
   修复：**只取消不释放**（CTS 无内核句柄，交 GC 终结回收），两处 + 注释。
2. **已取消任务的位图仍回 UI 线程**：`GetThumbnailAsync` 解码完成后不检查 token 直接
   `CreateBitmapAsync`（ConfigureAwait(true)=UI 线程）——多次切换后「已取消但解码已完成」的
   回调洪峰涌向 UI 线程逐个创建 BitmapImage → UI 假死。
   修复：CreateBitmapAsync 前 `ThrowIfCancellationRequested()`（编码成果作废，防止 UI 淹没）。
3. **旧预取不可取消**：`PrefetchDimensionsAsync` 的 Parallel.ForEachAsync 没接代数 token，
   切走后旧全量文件 IO 继续跑，多次切换线性叠加 IO 竞争。
   修复：ExecuteLoadAsync 维护代数级 `_loadCts`（同样只取消不释放），预取全部接 token；
   收藏切换单条预取传 `CancellationToken.None`（与视图代数无关）。

## 排除项（排查中验证过）
- 解码信号量 `_decodeGate` Release 在内层 finally，无槽位泄漏；
- `GetDimensionsAsync` 不走解码信号量，预取不会被解码饿死；
- ASTA 序列化假设未证实（StorageFile 从 MTA 调用官方允许），未作为修复依据。

# 布局循环崩溃：ProgressRing 与大重排同帧（实证定案）

## 现象
「渲染帧等待」轮后应用启动即崩（概率 ~3/4）。crash.log：`LayoutCycleException: Layout cycle detected`。
进程被 App.xaml.cs 的 UnhandledException(e.Handled) 吞掉 → 窗口存在但 UI 已坏 =「没有正常启动」。

## 排查过程（二分 + 连启验证）
- 二分一：ProgressRing 直挂 Border → 崩
- 二分二：恢复 StackPanel+TextBlock（上上轮结构）→ **一次未崩**（后证为运气）
- 二分三：StackPanel 仅包 ProgressRing（无文字，用户需求）→ 崩
- 二分四：x:Load 加载/卸载替代 Visibility + IsActive 恒 True → 仍崩（排除状态机竞态）
- **结论：与包裹结构、加载方式无关，是 ProgressRing 本身**

## 根因（实证结论）
ProgressRing 的模板动画**参与测量**（DesiredSize 随动画状态变化）；「渲染帧等待」让覆盖层
（动画中）与 GridView 大重排首次有机会**同帧**，二者交替布局失效 → 循环超限 →
LayoutCycleException。此前所有版本替换块发生在覆盖层首帧渲染之前（SQLite 同步完成包装），
动画与大重排从不同帧 → 从不崩。这也解释了 loading 晚 3 秒与崩溃是同一时序的两面。

## 修复（实证有效）
覆盖层进度指示改 **ProgressBar IsIndeterminate=True**（固定轨道内位移动画，
DesiredSize 恒定，机制上排除测量循环）+ x:Load 加载/卸载 + 不透明背景。
**连启 3 次全部稳定，crash.log 零新增**（此前崩率 3/4）。文字已按用户要求移除。

## 平台结论（值得长期记忆）
- **ProgressRing 的动画参与布局测量，与同格大重排（集合重建）同帧时概率性 LayoutCycleException；
  loading 指示优先用 ProgressBar indeterminate（DesiredSize 恒定）**
- x:Load 需要配 x:Name（WMC0907）
- LayoutCycleException 的托管堆栈为空（原生布局循环），crash.log 取证无堆栈可用；
  UnhandledException e.Handled=true 会吞掉启动崩溃 → 进程活着但 UI 已坏，用户感知为「没有正常启动」

## 验证（每项单独列出）
- `dotnet build`：**通过**（0 Warning 0 Error；x:Load 缺 x:Name 一次 WMC0907）
- `dotnet test Pixbian.sln`：**159 全通过**（Core 114 / WebServer 33 / Imaging 12）
- **连启 3 次 × 7 秒观察：3/3 稳定，crash.log 零新增**

## 图库文件夹加载性能优化（第 0 批埋点 + 第 1 批元数据回填）
- 起因：通读「打开文件夹」链路后确认头号瓶颈是**每次加载都要对整页条目逐个开文件读头取宽高**
  （索引里根本没有 width/height），且该过程阻塞撤除 loading 覆盖层，即转圈时长 = N 次文件 IO。
- 结论修正：设想中的「大小/日期」其实索引里早已有（FileSize / CreatedUtc / ModifiedUtc / TakenUtc），
  真正缺的是 **width / height / duration_ms**；且绝不能把这些塞进同步扫描路径（会掉到分钟级）。

### 第 0 批：基线埋点
- 在 `GalleryViewModel.ExecuteLoadAsync` 加 5 条 `Diagnostics.Log`：
  `LOAD`(SQL 查询) / `STAT`(两条 COUNT) / `PROBE`(尺寸预取) / `THUMBWAIT`(整页解码) / `LOADTOTAL`(端到端)。
- 目的：让后续优化可度量。**未取得数据前不动 SQL**——排序 CASE 表达式、directory LIKE 前缀
  与 BINARY 排序规则不匹配、OFFSET 深翻页三项仍需 `EXPLAIN QUERY PLAN` 实测，不凭推断改。

### 第 1 批：元数据后台回填（新增 M3）
- 架构遵循分层约束：Core 定 `IMediaMetadataProbe` 抽象 + `MediaMetadataBackfillService`，
  UI 层注入 `MediaMetadataProbe` 实现；Core 全程不碰 WIC / WinRT API。
- 索引两阶段：扫描仍只写文件属性（秒级），宽高与时长由后台分批补齐；
  `GalleryViewModel` 预取收口为**只对「索引无宽高」的条目发起**，回填完成后降为零文件 IO。
- 探测状态三态 Pending / Completed / **Failed**：失败必须落为 Failed 而非停留 Pending，
  否则损坏文件每轮被反复捞取、占满批次额度，回填永不收敛（已用测试固化）。
- 回填并发定 2（前台预取是 4）：后台常驻任务不得与用户正在浏览的解码争抢 IO，宁可慢不能抢。
- Schema v2：`metadata_state`（NOT NULL DEFAULT 0）、`metadata_utc`，外加
  **部分索引** `WHERE metadata_state = 0`（回填推进后索引自动收缩）。
- 元数据写回只覆盖尺寸/时长列，用户数据（收藏/评分/分类）用 `COALESCE` 保护。
