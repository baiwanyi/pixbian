### 1.2 已核实为「做得好」的控制（不必返工）

- **SQL 注入防御彻底**：全参数化；`LIKE` 通配符 `% _ \` 转义；`IN` 子句参数名由序号生成；排序键用参数化 `CASE` 而非拼接字段名；`user_version` 拼接为 long 强类型常量。

- **ReDoS 四道防线**齐备（构造期 1s 超时 / 超时标记危险规则 / 整批 30s 总时限 / 文本截断 4096），并刻意不用 `RegexOptions.Compiled` 避免程序集不可卸载——属于超出平均水平的设计判断。
- **密码学正确**：PBKDF2-SHA256 / 100k / 16B 随机盐 / `FixedTimeEquals` 恒定时间比较 / 256 位 CSPRNG 令牌；哈希长度与盐长度校验防篡改绕过。
- **响应安全头齐全**（`nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy`、CSP `self` 基线），头部值统一过滤 CR/LF 阻断响应拆分。
- **只读服务 + 主键寻址**：`/media/{id}`、`/thumb/{id}` 拒收路径参数，落盘前再经 `PathGuard` 二次校验（纵深防御）；对外 JSON 不含绝对路径。
- **索引跳过重解析点**（防目录环与越权读取）。

### 1.3 加固建议（按性价比排序）

1. **TLS 化或明确代理解耦**：内置自签证书 + 首次配对指纹确认，或文档中强制「仅经反向代理暴露」并在 UI 明示风险（对标 Jellyfin Hardening Guide）。
2. **绑定收敛**：改为可选网卡/指定 IP；启动时读取 Windows 网络类别（`NetworkListManager`），「公用」网络下拒绝监听或强制二次确认。
3. **连接治理**：`SemaphoreSlim` 限制并发连接（如 32）、`CancellationTokenSource` 级 10s 首字节超时、24h 硬超时；缓冲区改池化。
4. **流式响应**：`/media` 无 Range 与小 Range 改为 `FileStream` + 分块写（`CopyToAsync`），禁止整文件入内存。
5. **解码上限**：ImageSharp 设 `Configuration.Default.MemoryAllocator` 上限 + 先读文件头校验像素数（>50 MP 拒绝或降级）。
6. **审计日志**：`LoggerMessage` 覆盖登录成败、401/429/416、启停、配置变更；脱敏（IP 保留 /24、不记路径全名）；按大小轮转（如 5 MB × 3）。
7. **对账保护**：枚举过程记录"不可访问目录数"，>0 时跳过删除并告警。
8. **补齐 LICENSE + CI（含 `-warnaserror` 与 `dotnet test`）+ SBOM**；规划 .NET 8（2026-11 EOL）迁移。

### 2.2 性能资产（已属先进，建议保持）

- **解码量与集合规模解耦**：视口 ±1 屏窗口 + 距中心优先级 + 每拍 ≤4 条，命中"O(视口)"而非 O(集合)。
- **统一解码档位 512**：缓存条目数从「档位 × 文件」降为「文件」，切档位全量命中——典型的工程取舍且论证充分。
- **两级缓存 + 指纹失效**：磁盘 LRU 2 GB，条目头带 mtime+size，原子替换，任何故障静默降级。
- **信号量 + 20 s 超时自愈**：防止被杀软/坏道挂死的单条 IO 占死管线。
- **后台任务节流比例**：批 2.5 s 让出 1.5 s（约 1/3），并设批次数上限。
- **随机排序走固定 `random_rank` 游标**：避免 `ORDER BY RANDOM()` 全表排序与深翻重复/遗漏。

### 2.3 优化建议

1. 以**位图内存账本**替代强制 GC：按视口显式 `Release`，用内存指标驱动回收，去掉 `GC.Collect`。注意"移到后台线程"并不能规避 STW 停顿（见 P-01 更正）。
2. 查看器引入**分级解码**：当前已加 8192 最长边上限兜底（见第七节 P0-2）；完整方案是按视口设置 `DecodePixelWidth/Height`，并在放大到 1:1 时按需重载原图（对标 Windows 照片）。`PreviousImage` 无需处理——已由 `CompleteTransition` 回收。
3. 搜索改 **FTS5 虚表**或至少「前缀索引 + 扫描限流」；排序改**键集分页**（`(sort_key, id) > (?, ?)`）替代 OFFSET；为 `random_rank`、`kind` 建覆盖索引。
4. 磁盘缓存驱逐改**小顶堆 + 分批裁剪**（每次最多驱逐 N 条），避免长锁与全量排序。
5. Web 端网格用 `/thumb/{id}` 替 `/media/{id}`，查看器先 512 垫场再原图；视频 tile 改为点击后创建 `<video>`。

## 四、架构与可维护性

**优点**：Core 零平台依赖 + 抽象注入、单向依赖、模型集中、文档级头部注释（职责/复用/约束三段式）在同类项目中属上乘；`Directory.Build.props` 集中版本、分析器开启、`NU1900` 精准豁免（未屏蔽真实漏洞告警）都做得对。

**扣分项**：

- **巨型文件**：`GalleryPage.xaml.cs` 99 KB、`MainWindow.xaml.cs` 69 KB、`GalleryViewModel.cs` 58 KB、`SettingsPage.xaml.cs` 27 KB。单文件承载过多职责，违背"30 秒规则"，且因无 UI 测试，重构成本高。建议按「选择/加载/键盘交互/上下文菜单」拆分为 partial 或协作组件。
- **无 CI**：仓库无工作流配置，`-warnaserror` 与 `dotnet test` 依赖人工执行。
- **知识沉淀优秀但封闭**：大量"实测结论"注释极有价值，建议抽取为 `docs/` 的《避坑清单》并纳入 CR 检查表。

1. **共享服务的"产品级硬化"**：Immich/Jellyfin 默认假定"不可信网络"，因此强制 TLS 终止、用户/RBAC、审计日志、配额。Pixbian 的威胁模型停留在"可信家庭局域网"，一旦用户在公司/酒店网络开启即破防 —— 需在 UI 与文档中把"可信网络"前提显式化。
2. **大图与缓存的分级策略**：Windows 照片与 Lightroom 用「金字塔/代理预览」把内存与视口解耦。Pixbian 目前"统一 512 + 原图全解"是两端跳变，缺中间档（1024/2048），这正是 P-01/P-02 的根因。
3. **工程流水线**：digiKam/Immich/Jellyfin 均有 CI + 版本化迁移 + 制品与 SBOM。Pixbian 依赖人工，且 UI 层无测试网，随着巨型文件累积，变更风险会非线性上升。
