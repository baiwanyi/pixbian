## 搜索栏样式三次修正（聚焦后底部不再变粗变黑）——最终方案

### 现象
搜索框点击获得焦点后，底部边框加粗并变成强调色/深色，与未聚焦状态不一致（默认模板的 Focused 视觉状态所致）。

### 根因（查 WindowsAppSDK 1.6 的 generic.xaml 确认，非猜测）
- `TextControlBorderThemeThickness` = `1`（未聚焦，四边 1px）
- `TextControlBorderThemeThicknessFocused` = `1,1,1,2`（**聚焦时底部加粗到 2px**）
- `TextControlBorderBrushFocused` → `TextControlElevationBorderFocusedBrush`，其渐变含 `SystemAccentColorLight2`（**强调色**）
- 模板 Focused 状态的 `DiscreteObjectKeyFrame` 用 `{ThemeResource}` 引用上述两个键——这正是可以低成本覆盖的切入点

### 修复
在 `AutoSuggestBox.Resources` 中覆盖同名主题资源（ThemeResource 沿视觉树向上查找，元素级优先）：
```xml
<AutoSuggestBox.Resources>
    <Thickness x:Key="TextControlBorderThemeThicknessFocused">1</Thickness>
    <StaticResource x:Key="TextControlBorderBrushFocused" ResourceKey="TextControlBorderBrush" />
</AutoSuggestBox.Resources>
```
仅 2 个资源条目，无需重写 200+ 行 TextBox 控件模板。

## 搜索框边框色：去掉 TextControlBorderBrush 的「黑色底」

### 现象
用户反馈 `BorderBrush="{ThemeResource TextControlBorderBrush}"` 自带一个黑色底边。

### 根因（查 generic.xaml 确认）
`TextControlBorderBrush` → `TextControlElevationBorderBrush`（generic.xaml Light 段 7737 / Dark 段 2183），
是一个 `MappingMode="Absolute" StartPoint="0,0" EndPoint="0,2"` 的**竖向渐变**，并带 `ScaleTransform ScaleY="-1" CenterY="0.5"` 翻转：
- `GradientStop Offset="0.5"` = `ControlStrongStrokeColorDefault` = 浅色 **#72000000**（45% 黑）→ 翻转后落在**底部**
- `GradientStop Offset="1.0"` = `ControlStrokeColorDefault` = 浅色 #0F000000（6% 黑）→ 落在顶部

上淡下深，所以底部看起来有一条黑边。这是 WinUI「elevation border」的刻意设计，不是 bug。

### 修复
在 `AutoSuggestBox.Resources` 里覆盖同名资源为纯色（沿用覆盖 ThemeResource 的手法）：
```xml
<StaticResource x:Key="TextControlBorderBrush" ResourceKey="ControlStrokeColorSecondaryBrush" />
```
`ControlStrokeColorSecondaryBrush` = 浅色 #29000000（16% 黑）/ 深色 #18FFFFFF，四边一致且随主题切换。

### 备选色（改 ResourceKey 即可换挡）
| 资源键 | 浅色值 | 深色值 | 观感 |
|---|---|---|---|
| `ControlStrokeColorDefaultBrush` | #0F000000 | #12FFFFFF | 极淡，接近无边框 |
| `ControlStrokeColorSecondaryBrush` | #29000000 | #18FFFFFF | 适中（已采用） |
| `ControlStrongStrokeColorDefaultBrush` | #72000000 | #8BFFFFFF | 与原渐变底部同深度，偏重 |

若要完全固定色值（放弃主题自适应），改用：
`<SolidColorBrush x:Key="TextControlBorderBrush" Color="#E5E5E5" />`

## 列表缩略图清晰度优化（自适应视图主因：请求尺寸语义错误）

### 根因分析（4 条，按影响排序）
1. **请求尺寸与显示尺寸不匹配（最主因）**：`JustifiedPanel.RowHeight = ThumbnailSize`，条目显示宽度 = 宽高比 × 行高；
   但 `GetThumbnailAsync(mode, size)` 的 size 是**最长边**语义，调用方传的却是行高。
   3:2 横图显示 384×256 却只请求 256 长边（实际位图 256×171）→ 放大 1.5 倍；16:9 放大 1.78 倍；2:1 放大 2 倍。
2. **DPI 缩放失效**：`DisplayInformation.GetForCurrentView()` 在 WinUI 3 桌面应用中已弃用且通常抛异常，
   原代码 catch 后回退 `dpiScale = 1` → 150%/200% 屏上缩略图只有 1x 分辨率。
3. **系统缩略图未要求精确缩放**：未传 `ThumbnailOptions.ResizeThumbnail`，系统返回缓存中最接近的档位，
   可能小于请求值，位图被拉伸后发虚。
4. **条目 Margin 破坏内容区宽高比**：自适应条目模板 `Border Margin="0,0,8,8"`，而 `JustifiedPanel` 按
   `ratio × RowHeight` 分配尺寸 → 内容区比分配尺寸少 8px，宽高比与位图失配，
   `Stretch="Uniform"` 后一边留白、露出 `ChromeMedium` 背景色边，且非整数缩放使边缘发虚。

### 修复
- `ThumbnailSizes`（Core/Models/AppSettings.cs）：新增 `DecodeBuckets = [128,192,256,384,512,768,1024,1536,2048]`
  与 `SnapToBucket(double)`，把请求尺寸量化到固定档位，控制系统的缩略图缓存与内存缓存条目规模。
- `ThumbnailService`：删除 `DisplayInformation`（弃用 API），改由 `IThumbnailService.RasterizationScale`
  接收主窗口同步的 `XamlRoot.RasterizationScale`，按**物理像素**请求；
  请求时传 `ThumbnailOptions.ResizeThumbnail` 强制系统精确缩放；回退解码路径改用
  `DecodePixelType.Physical` 且同时给宽高（解码器保持宽高比 Fit 到框内，避免整幅解码的内存峰值）；
  缓存键加入「代次」，缩放比变化时整体失效，旧代次条目随滑动过期淘汰。
- `MediaItemViewModel`：`EnsureThumbnailAsync` 按 `size × Clamp(AspectRatio,1,2)` 推导显示区最长边再量化
  （上限 2 倍：常见画幅 4:3~2:1 全覆盖，全景图不至于让内存成倍膨胀）；
  首帧宽高比多为 1.0，位图到位后若目标尺寸变大则补一次升级加载——**只升级不降级**，
  否则解码舍入造成的宽高比抖动会在档位边界来回重新解码；用 `_inflightSize` 防重入递归。

## 列表缩略图四次优化（改用 WIC Fant 重采样——画质感根因）

### 根因
前三次都在改「解码分辨率」，但分辨率到位后画质仍偏软。真正的差距在**插值算法**：
- `BitmapImage.DecodePixelWidth` 走 WIC 默认路径，**插值模式不可控**；
- `BitmapTransform` 的默认 `InterpolationMode` 是 `Linear`（**双线性**），
  在中等比例缩小（如 1200×800 → 768×512，约 0.64 倍）时会丢细节并产生锯齿。
  这正是 Windows 照片应用与 Pixbian 的画质差距所在。
- JPEG 大图虽然能吃到 WIC 的 DCT 域预缩放（1/2、1/4、1/8），插值影响较小；
  但中等尺寸图与非 JPEG 格式（PNG/HEIC/WebP）无 DCT 缩放，插值质量就是全部。

### 修复（`ThumbnailService.DecodeImageThumbnailAsync`）
改用 `BitmapDecoder` + `BitmapTransform` 显式高质量降采样：
```csharp
var decoder = await BitmapDecoder.CreateAsync(stream);
var target = ComputeTargetSize(decoder.OrientedPixelWidth, decoder.OrientedPixelHeight, physicalSize);
using var softwareBitmap = await decoder.GetSoftwareBitmapAsync(
    BitmapPixelFormat.Bgra8,
    BitmapAlphaMode.Premultiplied,
    new BitmapTransform {
        ScaledWidth = (uint)target.Value.Width,
        ScaledHeight = (uint)target.Value.Height,
        InterpolationMode = BitmapInterpolationMode.Fant   // 关键：替代默认的 Linear
    },
    ExifOrientationMode.RespectExifOrientation,
    ColorManagementMode.ColorManageToSRgb);
```
- 用 `OrientedPixelWidth/Height`（已计入 EXIF 方向）算目标尺寸，配合 `RespectExifOrientation`，
  竖拍横图不会被压反；`ColorManageToSRgb` 保证宽色域（Adobe RGB / Display P3）正确转换。
- 原图不大于目标时直接全尺寸解码，跳过降采样与中转。
- `BitmapImage` 不能直接承载 `SoftwareBitmap`，故编码到 `InMemoryRandomAccessStream` 再交给它解码；
  **不再设 `DecodePixel*`**（流已是最终尺寸，再降采样等于二次缩放，且保证了不变形）。

### 中转编码器的选择（性能）
- JPEG 无 alpha → `BmpEncoderId`（纯内存拷贝，开销可忽略）；
- 其余格式可能有 alpha → `PngEncoderId`（保留 alpha，否则透明区被预乘成黑底）。
- 判断依据：`decoder.DecoderInformation.CodecId == BitmapDecoder.JpegDecoderId`。

  且 Windows PowerShell 5.1 没有 `System.Reflection.Metadata`，只能走二进制字符串搜索。

## 列表缩略图五次优化（显示尺寸回写 + 物理域量化——精度根因）

### 根因（前四轮都未触及的精度问题）
前四轮解决了「解码分辨率」与「插值算法」，但请求尺寸本身就不对：
1. **请求尺寸与实际显示尺寸脱节（主因）**：`JustifiedPanel` 为填满行宽会对整行做
   `scale ∈ [0.5, 1.5]` 缩放，实际显示区最长边 = `max(ratio,1) × RowHeight × scale`；
   而请求端按 `RowHeight × clamp(ratio,1,2)` 计算，误差因子**恰为 scale**。
   实测（256 行高、3:2 横图、scale=1.3、150% DPI）：显示 749 物理，请求只到 576 → 放大 1.3 倍发虚。
   症结：自适应视图的组内 GridView 未订阅 `ContainerContentChanging`，
   缩略图由 `GalleryViewModel` 在**布局之前**按名义值批量发起，之后**没有任何反馈通路**。
2. **网格视图按宽高比放大请求**：内容区是正方形，`Uniform` 下 3:2 图实际显示 256×170.7，
   最长边恒为 256；请求被放大到 384 → 2.25 倍内存、解码更慢，零清晰度收益。
3. **量化在逻辑域而非物理域**：先 `SnapToBucket` 再乘 DPI，档位误差被缩放比成倍放大。
4. **档位过疏**：旧 `DecodeBuckets` 相邻比值 1.33~1.5，最坏过采样 1.5 倍，
   而 WinUI 3 的 `Image` **没有 mipmap**，缩小只能靠双线性，倍率越大细节损失越明显。
5. **小图（原图 < 显示区）交给显示端放大**：显示端插值不可控，比 WIC 的 Cubic 明显发虚。

### 修复
- `ThumbnailSizes`（Core/Models/AppSettings.cs）：`DecodeBuckets` 加密到 17 档
  `[128,160,192,224,256,320,384,448,512,640,768,896,1024,1280,1536,2048,2560]`，
  相邻比值 ≤1.33；语义由逻辑像素改为**物理像素**。
- `ThumbnailService`：
  - 改为**先换算物理像素再量化**（`SnapToBucket(ceil(size × RasterizationScale))`）；
    物理档位已隐含缩放比，故删除冗余的缓存代次 `_generation`（`DecodeThumbnailAsync` 因此转为 static）。
  - `ComputeTargetSize` 增加插值模式返回值：缩小用 `Fant`、**放大用 `Cubic`**（Fant 放大偏软）；
    放大上限 2 倍（`MaxUpscaleFactor`），超过则保留原图；比例差 <1% 跳过重采样。
- `JustifiedPanel`：新增 `IDisplaySizeAware` 契约，`MeasureOverride` 在 `child.Measure` 后
  回写实际分配尺寸（读 `DataContext`，与解析宽高比同一通路）。
- `MediaItemViewModel`：实现该接口；`ResolveDecodeSize()` 改为无参、优先用回写的显示尺寸，
  未回写时才按 `_requestedThumbnailSize × clamp(AspectRatio,1,2)` 估算，且**不再量化**（交给服务层物理域）；
  `EnsureThumbnailAsync` 改为「只升不降 + 升幅须超 12% 容差」，防解码舍入与布局抖动引发反复重解码；
  `OnThumbnailChanged` 在位图置空时重置 `_loadedThumbnailSize`，使下一次请求必定重解码。
- `GalleryPage.xaml.cs`：网格视图 `OnContainerContentChanging` 补 `SetDisplaySize(size, size)`。
- 圆角：`WinUI 3 的 Border 不裁剪子内容`，`Image` 四角会露出直角尖角。
  改用 `Border.Background` 承载 `ImageBrush`（背景必定按 `CornerRadius` 绘制），
  `x:Bind` 到 `ImageBrush.ImageSource` 实测可编译通过。

### 经验教训
- **「请求尺寸」与「显示尺寸」之间必须有回写通路**：自定义布局面板只要在 `MeasureOverride`
  里对子项做了缩放，名义尺寸就一定失真。可靠做法是在 `child.Measure` 后把实际分配尺寸回写给
  DataContext（`IDisplaySizeAware`），由条目自行判断是否要重新解码。
- **量化必须在物理域**：先逻辑量化再乘 DPI 会让档位误差被缩放比成倍放大；
  反过来，物理档位已隐含缩放比，缓存键天然区分，不需要额外的「代次」失效机制。
- **放大与缩小要用不同插值**：`Fant` 在缩小时最优但放大偏软，`Cubic` 放大边缘更锐利；
  `BitmapTransform` 的默认 `Linear` 两头都不占优。
- **竖图不需要二次升级**：竖图的最长边就是行高，而首帧按正方形（ratio=1）请求的最长边同样是行高，
  故首帧请求已覆盖；只有横图（`max(ratio,1) > 1`）才需要布局回写后升级。实测验证了这个推断。
- **`Border` 的 `CornerRadius` 不裁剪子内容**，圆角缩略图要把图片交给 `Border.Background` 的
  `ImageBrush`（背景绘制必定按圆角），而不是内嵌 `Image`。
- 本次遗留（未做，属功能扩展）：扫描器未把图片宽高写入索引（`MediaItem.Width/Height` 多为 null，
  详情页 `DimensionText` 显示「—」），导致首帧 `AspectRatio` 只能是 1.0。

## 遗留两项的评估（用户问「是否需要」）

### 结论
1. **扫描期写宽高：不做**（原方案路径错误）。2. **色彩链路：不改**。

### 第 1 项：重新定性为「布局抖动」，且原方案不可行
- **定性修正**：这一项解决的**不是清晰度**（清晰度已由本次修复解决），而是**布局抖动**。
  日志证据：129 条解码发生在 `disp=327.7x327.7`（正方形）状态下，200 条条目首帧**全部**按正方形排列，
  拿到位图后才整行重排成真实比例 —— 肉眼可见的整体抖动，比「先模糊后清晰」更刺眼。
- **但「扫描期写宽高」这条路走不通**（查 csproj 与源码确认，非猜测）：
  1. **架构硬约束**：`Pixbian.Core` 是零项目引用的最底层、TFM 为纯 `net8.0`；
     `ImageMetadataReader` 在 `Pixbian.Imaging`（引用 Core）。**Core 无法反向引用 Imaging**，
     也不能用 WIC（会把 Core 绑到 `net8.0-windows10.x`，破坏 `Core.Tests` 的 net8.0 基线）。
     要接必须在 Core 定义抽象 + UI 层注入实现。
  2. **覆盖率不足**：`ImageMetadataReader` 读的是 **EXIF 标签**（`TagExifImageWidth`/`TagImageWidth`），
     PNG、无 EXIF 的 JPEG、截图与处理过的图**全部读不到**，返回 null —— 花了代价只覆盖一部分。
  3. **扫描性能**：MetadataExtractor 解析完整元数据段，相比当前只读 `FileInfo` 的枚举，
     首次扫描会从秒级掉到分钟级。
  4. **存量数据**：必须全量重扫一次才生效。
- **推荐的替代路径**：图库加载时用 `StorageFile.Properties.GetImagePropertiesAsync()` 取宽高。
  覆盖率 100%（覆盖所有 WIC 格式含 PNG/HEIC，不依赖 EXIF 标签）、走 shell 属性缓存、只读文件头不解码；
  且不动 Core / 扫描器 / schema，存量数据立即生效。属新功能，需单独确认。

### 第 2 项：维持不改，但修正一处此前表述
- WIC 分支色彩管理**已验证正确**：显式 `ColorManageToSRgb` → 像素已转 sRGB → BMP/PNG 无 profile
  → 解码端按 sRGB 处理，一致。EXIF 方向由 `OrientedPixel*` + `RespectExifOrientation` 保证。
- **此前表述有误**：我说「色彩链路全部正确」，但「原图不重采样」分支走的是
  `BitmapImage.SetSourceAsync`，**绕过了显式的 `ColorManageToSRgb`**，
  其自身 ICC 处理行为**未实测**，对 Adobe RGB 素材理论上可能与 WIC 分支不一致。
  （顺带收益：本次改动把该分支的触发条件从「原图 ≤ 显示尺寸」收窄为「放大 > 2 倍」，
  更多图片走的是已验证的 WIC 路径，而仍走原图分支的都是很小的图，影响随之变小。）
- 其余未验证项：中转 PNG 编码的预乘 alpha 转换（半透明图边缘理论上可能偏暗/黑边）；
  `GetSoftwareBitmapAsync` 指定 `Bgra8`，10 位/HDR 图降到 8 位，理论上有色带但缩略图场景可接受。

### 教训
- 评估「要不要补数据」时，先看**依赖方向**再谈实现：Core 是零引用的最底层，
  任何想让 Core 使用上层服务（Imaging/Media）的方案都必须改为「Core 定抽象 + UI 层注入」。
- EXIF 标签宽高 ≠ 像素宽高，且覆盖率远低于 100%；若要可靠取尺寸，
  应走 WIC / Windows 属性系统而非元数据标签解析。

## 实施：预取宽高消除首屏布局跳变（第 1 项的替代方案）

### 问题重述
首帧 `AspectRatio` 只能是 1.0，200 条条目**全部**先按正方形排版，拿到位图后再整行重排。
上一轮日志佐证：129 条解码发生在 `disp=327.7x327.7`（正方形）状态下。

### 实现（3 个文件）
- `ThumbnailService`：
  - 接口新增 `Task<(int, int)?> GetDimensionsAsync(path, ct)`。
  - **图片**用 `BitmapDecoder` 的 `OrientedPixelWidth/Height` —— 关键点：它与缩略图解码
    用的是**同一个属性**（`DecodeImageThumbnailAsync` 也用它算目标尺寸），
    故预取宽高比与最终位图宽高比**必然一致**，不存在 EXIF 方向分歧。
    且**只读文件头不解码像素**，远快于解码缩略图。
  - **视频**：WIC 不支持视频容器，改用 `file.Properties.GetVideoPropertiesAsync()`，
    并按 `VideoOrientation.Rotate90/Rotate270` 交换宽高 —— 手机竖拍视频的帧数据横向存储，
    不处理旋转会让宽高比反过来，**比不预取更糟**；180 度不改变宽高比，无需交换。
  - 缓存用 `ConcurrentDictionary<string, (int,int)>` 常驻（每条仅两个 int，十万条也才数 MB），
    不用 `IMemoryCache` 以免挤占缩略图的 `SizeLimit=2000`。
- `MediaItemViewModel`：
  - 新增 `_probeWidth/_probeHeight` 与 `SetDimensions(int,int)`（触发 `AspectRatio` 通知）。
  - `AspectRatio` 优先级改为：位图尺寸 → **预取尺寸** → 索引尺寸 → 1.0。
    顺带把原来的嵌套三元重构为 getter + 早返回（原写法已违反「禁止嵌套三元」）。
- `GalleryViewModel`：
  - 新增 `PrefetchDimensionsAsync`，用 `Parallel.ForEachAsync`（并发度 4）并发探测，
    结果进 `ConcurrentBag`，最后**一次性** `EnqueueAsync` 批量写回
    （逐条 await 会让 UI 线程切换成为瓶颈）。
  - 在 `ExecuteLoadAsync` 中置于 `LoadThumbnailsForVisibleItemsAsync` **之前**。
  - `ToggleFavoriteAsync` 重建 VM 后补一次预取，否则该条目会跳回方图再跳回来。

### 两个必须记住的坑（本次实踩）
1. **`VideoProperties.Width/Height` 是 `uint` 不是 `uint?`**，写 `.Value` 会报 CS1061。
2. **不能在 `EnqueueAsync(Action)` 之外引用其内部定义的局部变量**（CS0103），
   但也不能改成 `EnqueueAsync(async () => { await Prefetch... })` —— 那会**自我死锁**：
   外层在 UI 线程 await，内层预取又要 `EnqueueAsync` 排队回 UI 线程。
   正解：把变量提到 lambda 外声明 `MediaItemViewModel? updated = null;`，lambda 内赋值，出队后再用。

## 图片清晰度优化 · 第 1 步：缩略图并发度治理

### 根因（基线数据揭示，非预期中的清晰度问题）
基线采集 1795 条 THUMB 记录，暴露出**真正的洼地不是画质而是延迟**：
- 比值 P50=1.157 / P95=1.231 / **Max=1.245** —— 显示端仅需缩放 13~24%，肉眼几乎不可辨，
  **据此判定 MagicScaler 方案可彻底取消**（原以为过采样倍率大，实测已足够精确）。
- 但解码延迟 **P50=6929ms / P90=8924ms** —— 端到端近 7 秒，这才是用户感知的"卡"。
- 根因在两处叠加：
  1. `GalleryViewModel.LoadThumbnailsForVisibleItemsAsync` 里 `_ = item.EnsureThumbnailAsync(...)`
     是 **fire-and-forget**，循环只 await 了入队动作，1224 条条目的解码任务**同时点火**、无任何上限。
  2. `ThumbnailService` 的解码全程留在调用线程（`ConfigureAwait(true)`），
     上百个 CPU 密集续体轮流抢占 UI 线程 → 位图迟迟无法提交。
  3. 附带问题：逐条 `EnqueueAsync` 让每个条目多付一次线程切换，上千条时调度本身成瓶颈
     （违反既有记忆里"批量写回 UI 线程"的结论）。

### 修复
`ThumbnailService`：
- 新增 `_decodeGate` 信号量，并发上限 `Math.Clamp(Environment.ProcessorCount / 2, 2, 8)`。
- **职责按线程亲和性切开**：CPU 密集段（WIC 解码 / 重采样 / 编码）整体移入 `Task.Run` 并经信号量限流，
  产出 `byte[]`；`BitmapImage`（DependencyObject）的创建单独抽为 `CreateBitmapAsync(byte[])` 留在 UI 线程。
- 图片与视频两个分支统一改为返回字节数组（`EncodeImageThumbnailAsync` / `EncodeVideoThumbnailAsync`），
  共用新增的 `ReadAllBytesAsync(IRandomAccessStream)`。
- 实现 `IDisposable` 释放信号量（CA1001 强制，本项目 `-warnaserror`）。
- 同步更正文件头文档：原写"本服务一律不使用 ConfigureAwait(false)"的理由已变，
  改为"CPU 段经信号量限流后放线程池，只把编码字节交回 UI 线程"。

`GalleryViewModel.LoadThumbnailsForVisibleItemsAsync`：
- 改为**一次**入队 UI 线程收集全部 Task，之后 `Task.WhenAll` 真正等待完成。
- 不再自行节流（解码并发已由服务层信号量统一管控），避免两级限流互相掩盖真实并发度。

### 教训（本轮关键）
- **"删除代码"在任何异步加载链路里都是高危操作**：先问"删掉后，谁还负责这件事"。
  本项目缩略图加载实际有两条路径（ContainerContentChanging 按需 + ExecuteLoadAsync 整页兜底），
  且两条路径的覆盖并不对称（自适应视图缺前者）——删兜底前必须先补齐前者的覆盖。
- WinUI 虚拟化列表的 `ContainerContentChanging` 绑定是**逐控件**的：网格视图绑了不代表
  自适应视图的分组 GridView 也绑了。检查"按需加载是否生效"必须逐个视图确认，不能想当然。
- **故障第一响应是看诊断数据而非猜**：THUMB=0 立刻指出"加载来源被切断"，比任何推理都准。
  埋点日志在排障时价值远高于其侵入性，这也是保留埋点的理由（待全部治理完成再统一移除）。

## 待排查：详情边栏（详细操作面栏）打开时双击无法打开查看器

### 现象（用户反馈，未处理）
当【详细操作】边栏（即 `DetailsPane` 详情面板，标题"详细信息"）处于打开状态时，
在图库区**双击条目无法打开图片查看器**；关闭边栏后双击恢复正常。

### 已定位的代码事实（仅分析，未改）
- 边栏由 `MainWindow` 承载：`DetailsColumn`（第 1 列，宽 280px）与 `PageHost`（第 0 列，承载 GalleryPage）
  是同一 `Grid` 的相邻两列，**逻辑上不重叠**；`IsPaneVisible` 仅在 `HasSelection && IsDetailsPaneVisible && IsChromeVisible` 时为真
  （MainWindow.xaml.cs:229），即必须先单击选中条目 → 边栏才弹出。
- 双击打开查看器的入口：`GalleryPage.xaml.cs:221 OnItemDoubleTapped`，经
  `FindItemContainer(e.OriginalSource)` 向上找 `GridViewItem`，再取 `container.Content as MediaItemViewModel`；
  若命中容器非 `GridViewItem`（重排后命中组容器/空容器）则 `item is null` → 不调用 `OpenViewerAsync`。
- 网格视图 `GridViewControl` 的 `SelectionMode="Extended"`（GalleryPage.xaml:475）：Extended 模式下
  **单击即触发选中并弹边栏**，边栏开启后整个列表因 `DetailsColumn` 宽度动画（0→280px）被水平压缩重排。
- `OnItemDoubleTapped` 已打 `DBLTAP` 诊断日志（sender/container/item 类型），但当前改动未实际运行采集。

### 怀疑方向（待实测确认，按可能性排序）
1. 边栏开启 / 列表重排后，双击命中位置的 `FindItemContainer` 返回容器 `Content` 非 `MediaItemViewModel`
   （命中 `GroupItem` 或其它非条目容器），`item` 为 null，`OpenViewerAsync` 不被调用。
2. `Extended` 选择模式下单击=选中+弹边栏的时序与 `DoubleTapped` 的 `Tapped` 序列相互干扰，
   双击第二次 `Tapped` 被选择逻辑吸收，导致 `DoubleTapped` 不触发或 `OriginalSource` 落点改变。
3. 布局压缩使条目实际命中区域偏移，双击落在 `JustifiedView`/`GridViewView` 的 `ScrollViewer` 空白带
   而非条目上，`OriginalSource` 为 ScrollViewer 而非 `GridViewItem`。

### 验证方案（后续处理时执行）
- 保留 `DBLTAP` 日志，打开边栏后双击条目，对比边栏关闭场景的 `container` / `item` 取值差异，
  据此区分上述 3 个方向。
- 若属方向 1：在 `OnItemDoubleTapped` 内对 `container.Content` 做类型判断失败时，改用
  `ItemsControl.Items` / `ContainerFromItem` 反查，或直接由 `e.OriginalSource` 的 `DataContext` 取 `MediaItemViewModel`。
- 若属方向 2/3：考虑把打开查看器的触发从 `DoubleTapped` 上移到容器级或改用 `ItemClick` 双击处理。
