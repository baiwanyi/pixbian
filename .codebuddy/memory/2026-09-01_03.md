# 2026-09-01 工作日志（第 4 卷）

## 第四轮：布局循环第二层根因——面板监听位图属性（LayoutCycleException 的完整解释）

### 为什么 AspectRatio 修复不够
- 前轮把位图尺寸从 AspectRatio 优先级降到底部，比值不再变化；
  但 `OnThumbnailChanged` **仍无条件发** `OnPropertyChanged(nameof(AspectRatio))`，
  且 `JustifiedPanel.OnItemPropertyChanged` 同时监听 **Thumbnail 与 AspectRatio** 两个通知。
- 结果：每张缩略图解码完成 → 两个通知 → 面板全量重测（无虚拟化，O(200)）。
  200 条逐张到位 = 200 次全量重排 ≈ 4 万次子项 Measure + SetDisplaySize；
  其中回写超容差的条目再触发升级解码 → 位图再到位 → 再通知 → **正反馈循环**。
- 23:11 实例（无任何修复）与 23:52 实例（含 AspectRatio 修复）都循环，
  区别只是循环入口不同：前者由「比值真变化」驱动，后者由「通知风暴」驱动。

### 两处修复
1. `JustifiedPanel.OnItemPropertyChanged` **删除 Thumbnail 监听**，只留 AspectRatio：
   布局几何仅由宽高比决定，位图替换不改变任何几何（骨架屏→图片的切换在
   ThumbnailPresenter 状态机内部，不依赖面板重排）。
2. `MediaItemViewModel.NotifyAspectRatioChanged()`：**通知值去重**（哨兵 `double.NaN`，首次必发）。
   `SetDimensions` 与 `OnThumbnailChanged` 统一走它；值不变时静默，消除空转重测。

### 自证日志（临时，定位后删除）
- `JustifiedPanel.MeasureOverride` 加节流打点：`PANEL|measures={增量}|width={视口宽}|children={子项数}`，
  每 500ms 一条。正常浏览每 500ms 仅 1~5 次；循环时数百上千次，
  且若 `width` 在两个值间交替即实锤「滚动条临界震荡」这一潜在第三层根因。

### 方法论
- **驱动布局的 INPC 通知必须值去重**：WinUI 的绑定与订阅方不做值相等检查，
  相同值的通知同样触发绑定更新与 InvalidateMeasure。
- **订阅方按「属性名」过滤时，要审一遍每个被监听属性的变更频率**：
  高频变更源（如每张位图到位）× 全量重排（无虚拟化）= 平方级风暴。
- **诊断脚本 delegate 的 P/Invoke marshaling 失败会静默返回空结果**：
  前轮 `EnumWindows` 报「窗口数 0」实为脚本回调签名问题（EnumWindowsProc 委托在循环中被 GC 回收），
  17720 实例实际有窗口（23:36 有用户交互日志佐证）。基于错误空结果的推论必须作废。
  正确做法：回调委托保存到变量再传入，防 GC。
- 构建报大片 XAML "Unknown type" 时先查首个 CS 错误（CS0103 字段名笔误），
  XAML 错误全是连锁假错误——与既有结论一致。

### 验证（每项单独列出）
- `dotnet build -warnaserror`：**通过**（0 Warning 0 Error；首轮失败为字段名笔误 CS0103 连锁 XAML 假错）
- `dotnet test`：**168 全通过**（Core 123 / WebServer 33 / Imaging 12）
- **待用户重启复现**：正常则点击恢复；若 `diag.log` 出现密集 `PANEL|measures=` 且 width 交替，
  则第三层根因（滚动条震荡）实锤，改 `VerticalScrollBarVisibility` 或行高钳制即可。
