## 第十九轮：根因定案并修复——整批取消导致缩略图永不加载

### 心跳判据修复后的决定性数据（推翻所有「渲染停摆」结论）
修复判据后复现：`04:46:30 THUMBSUBMIT|200` → **3 分钟内心跳 380 次从未中断**
（最大间隙 1812ms，正常），**UI 线程完全存活**。
但业务日志：**200 条提交后一条 THUMB 都没有**（对比 PageSize=50 那次 8.6 秒全部完成）。
线程级 5 秒采样：全线程 CPU 合计 31ms（0.6% 单核），8 次 dotnet-stack 均只有 6 个托管线程全空闲。
→ **不是慢、不是渲染停摆，是任务凭空消失。**

### 根因：虚拟化下 ContainerFromItem 的语义被误用
`GalleryPage.CancelOffscreenThumbnails`（滚动停止时调用）遍历**全部** Items，
对 `grid.ContainerFromItem(item) is null` 的项调 `CancelPendingLoad()`。
注释假定「null = 已回收」，但虚拟化下 **null 也表示「从未进入视口」**，两者无法区分。

竞态链：
```
集合替换 → 滚动位置重置触发 ScrollViewerViewChanged
   → CancelOffscreenThumbnails（此时容器尚未生成，全部 null）
   → 200 条在途解码被整批取消
   → EnsureThumbnailAsync 提前 return（_inflightSize 已置位）
   → 无任何机制重新发起
   → 缩略图永不出现 = 用户看到「冻结」
```
「有时正常、有时冻结」由此竞态解释，与用户描述的「概率性」吻合。

另注：`THUMBWAIT|200|0`（0ms）曾被视为异常，实属正常——
整页提交时 `EnsureThumbnailAsync` 因 `_inflightSize == target` 提前 return，
WhenAll 等到的全是立即完成的空转 Task；真正解码在 SetDisplaySize 触发的 Task A 里。

### 重大教训：心跳被 GC 回收，判据失效（自埋的坑）
```csharp
var heartbeat = DispatcherQueue.CreateTimer();   // 局部变量！
heartbeat.Start();                                // 构造函数结束即无强引用
```
`heartbeat` 是**局部变量**，构造函数结束后无强引用 → **GC 回收后定时器永久静默停止**。
- Pixbian 内存 362 MB、图片解码频繁分配 → GC 频繁 → **启动 41 秒后心跳停止**；
- MinRepro 内存小、84 秒未触发 GC → 心跳"看起来正常"。
**前几轮据「TICK 停止在 THUMBSUBMIT 之前」推出的「UI 线程先停摆」结论全部作废。**
→ 已改为 `_heartbeat` 字段强引用。

### 由此修正的关键认知
- **诊断用的定时器/回调对象必须持字段强引用**，否则 GC 会静默杀死判据，且误判方向完全相反。
- 短窗口（8~15s）测 CPU 增量容易看到 0；但跨数分钟的累计 CPU 也会涨（曾观测 103s→211s），
  二者不矛盾（工作集中在前期）。判断"是否空闲"须看**线程级**增量，且多次采样。
  本轮用线程级 5s 窗口复测：`BUSY_THREADS=0`、`TOTAL_CPU_5S=0ms`、`CPU_DELTA_10S=0.00s`，
  托管栈 6 次采样均只有 6 个线程全空闲 → **卡死稳态确实是 CPU 0**。

- **UIA 是「内在状态」取证器**：截图只证明"画出来什么"，UIA 证明"状态是什么"。
  两者矛盾 = 渲染呈现层死；一致 = 逻辑层死。这是 UI 类「点了没反应」问题的分水岭测试。
- **`off`（IsOffscreen）字段极有价值**：off=False 的元素画不出来 = 上屏管线死，
  而非元素不在或被遮挡。

## 第七轮：截图破案——「点击无效」= 渲染合成冻结（UI 线程活着、画面停在最后一帧）

### 截图取证（Capture.ps1 8 张 × 5 秒）+ 同时段日志对齐，得到决定性事实
- shot01(00:47:10) ~ shot07(00:47:40) **画面完全静止**：「收藏夹 / 媒体库为空」，30 秒一帧未变；
  shot03 窗口被用户移动过（非客户区系统直接画，可拖动）→ 客户区是死帧。
- 同期 diag.log：00:47:13.979 NAVCLICK（用户点图库）→ LOAD|图库|count=200 →
  **PANEL children=200 正常测量**（200 个子项已进渲染树！）→ THUMBWAIT|200|10658 →
  LOADTOTAL|图库|13111 —— **业务全程正常跑完**。
- crash.log 00:47:14 又是启动噪声（ClassFactory），非 LayoutCycle。

### 结论：「点击无效」的机制
**UI 线程活着**（输入接收、布局测量、业务执行全部正常），**渲染合成线程死了**——
画面永远停在死亡瞬间的最后一帧（恰是收藏夹空态）。点图库后的一切变化
（切页、200 条内容、缩略图）都发生在冻结帧之后，用户永远看不到。
- 为什么「片段能打开」：切片段发生在渲染死**之前**（00:40:22，当时画面还活着）。
- 为什么绑定全 OneWay 仍显示旧标题：不是绑定问题，是**整个 surface 不再上屏**。
- 与 LayoutCycle 的关系：同一病根（窗口级合成树被某操作打断）的两种表现——
  00:13 抛 LayoutCycleException 崩溃；00:24/00:40/00:47 静默冻结（无异常）。

### 死亡时刻的共同点（四次会话全部吻合）
死亡瞬间 = **loading 遮罩 Visibility 切换**（不透明 Border 盖满内容区、
位于背景图 + ThemeShadow + Mica 的窗口级合成树中）。内容换成静态文本仍复现
→ 刺激源是**遮罩 Border 的显隐本身**，不是进度动画。

### 本轮动作
1. `SyncLoadingOverlay` 改为**永久 Collapsed**（OVERLAY|suppressed 留痕）——排除实验；
   查询仅几十毫秒，无遮罩可接受。若画面不再冻结即实锤，再设计替代方案（如仅隐藏
   内容不遮盖、或带 IsHitTestVisible=False 的半透明层）。
2. 抓了死帧进程 dump（C:\Temp\PixbianShot\dead.dmp）：`pe` 显示主线程无托管异常——
   **渲染线程是 native（Composition/DWM），托管 dump 看不到**，native 分析成本高，
   先走排除实验路线。

### 验证
- `dotnet build -warnaserror`：通过（0 警告 0 错误）
- 待用户实测：点图库后若能看到 200 张图正常显示 → 实锤遮罩显隐破坏合成树

### 方法论
- **「日志说成功 + 用户说不行」= 去看屏幕**：业务日志无法证明用户看到了什么，
  截图是 UI 类问题的终极证据。8 张 × 5 秒连拍 + 日志时间戳对齐，一轮锁定。
- **画面可拖动 ≠ 客户区活着**：WinUI 窗口移动由 DWM 整体平移 surface，
  客户区内容可以完全冻结而窗口照常拖动/关闭。
- **渲染冻结三类死法**：LayoutCycleException（抛异常）、静默冻结（无异常，画面停帧）、
  遮罩卡死（不透明层吞输入）。三者症状都是「点击无效」，取证方向完全不同：
  前者看 crash.log、中者对比「日志活动 vs 画面变化」、后者看遮罩显隐留痕。

## 第六轮：LayoutCycleException 嫌疑排除（00:24 会话实为启动噪声）＋ 三级输入探针

### 用户回传日志的重大反转
- `crash.log` 00:24:03 的记录是 `COMException ClassFactory (0x80040111)` + LimitedAccessFeatures
  —— **WASDK 每次启动都有的既有噪声**（00:11 同款），**不是** LayoutCycleException！
  00:24 会话布局循环从未发生。
- 时序：00:23:52 收藏夹加载完（58ms/0条）→ 00:24:03 用户点图库 →
  00:24:04.371 `LOAD|新建文件夹(2)|count=200` → STAT → **PROBE|0|1（回填生效、零预取）** →
  **THUMBWAIT/LOADTOTAL 永久缺失** → 卡点锁定在 `LoadThumbnailsForVisibleItemsAsync`
  （整页 200 张解码提交后 `Task.WhenAll` 未返回）。
- `PANEL` 在 00:24:07-20 持续正常输出（3~10 次/500ms、width 恒定 1007、children=200）
  → **UI 线程活着、布局正常、面板无辜**——「点击无效」但布局在跑。
- 撤层（IsQuerying=false）在代码顺序上位于 THUMBWAIT 之前，理论应已执行，但**无日志证明**。

### 本轮改动
1. **兜底撤层**（`ExecuteLoadAsync` finally）：sequence 匹配收尾时若 `IsQuerying` 仍为 true
   则强制撤除并记 `OVERLAY|force-hide`。覆盖层是不透明全内容区遮罩，任何提前退出路径
   （作废 return / 静默异常 / 取消传播）漏撤层都会永久吞掉全部点击——布局照常、日志照常、
   唯独点不动，与用户症状完全一致。正常路径幂等无害。
2. **三级输入探针**（全部【临时诊断】，结案后删）：
   - `NAVCLICK`（MainWindow.OnNavigationSelectionChanged）：点击是否到达 UI 事件层；
   - `OVERLAY|show=0/1`（SyncLoadingOverlay）：遮罩每次显隐留痕；
   - `THUMBSUBMIT|count`（LoadThumbnailsForVisibleItemsAsync 前）：整页解码提交留痕。
3. PANEL 日志保留。

### 复现时的判读表（下次用户回传 diag.log 按此二分）
| 现象 | 结论 |
|---|---|
| 无 NAVCLICK | 点击未到 UI 事件层 → 输入路由被吞（找全窗口透明遮挡 / NCP 配置） |
| 有 NAVCLICK 无 LOAD | 加载链路前段挂起（等帧/QueryAsync） |
| 有 LOAD 无 THUMBSUBMIT | 集合替换 EnqueueAsync 或统计阶段挂起 |
| 有 THUMBSUBMIT 无 THUMBWAIT | 整页解码 WhenAll 挂起（头号嫌疑：OneDrive 按需文件解码下载挂死） |
| OVERLAY show=1 后无 show=0 且无 force-hide | 遮罩卡死吞输入（兜底已加，理论上不应再现） |

### 方法论
- **crash.log 必须逐条看异常类型**，不能见 crash 就套用上次的结论：
  同一位置前后两条记录（00:13 LayoutCycle / 00:24 ClassFactory）性质完全不同。
- **「布局在跑 + 点击无效」≠ 死循环**：不透明遮罩卡住、命中测试失效、输入路由被吞
  都是这个表现。死循环判据（CPU 100% + 日志 0 增长）不满足时必须转向输入侧排查。
- **代码顺序 ≠ 执行顺序**：撤层写在 THUMBWAIT 之前不代表它执行了——异步链路上
  每个关键状态变化（尤其显隐）都应留痕，否则无从取证。
