## 缩放首选项两处修复（用户反馈）
- 「适应窗口不生效」根因：设置变更只更新 VM 属性，当前图不重置——切回适应窗口后当前图保持实际大小，翻页才恢复，观感即「不生效」。修复：页面监听 `ViewerInitialZoom` PropertyChanged，设置变更即时生效（适应窗口 = Pan 归零 + SetZoom(1.0) + ClampPan；实际大小 = 立即对当前图应用）。
- 「实际大小先适应再放大」根因：`LoadCurrentAsync` 无条件 `SetZoom(1.0)`，全图就绪后才应用实际大小。修复：ActualSize 模式装载时跳过 SetZoom(1.0)；`CurrentItem` 变化时用**索引库元数据宽高**（`MediaItem.Width/Height`）预应用 100%（口径与 `GetImageContentRect`/双击一致，未计 EXIF 旋转），全图就绪后精确校正——全程实际尺寸无跳变。
- 运行实测：直接改 settings.json 切换两模式对比截图——fitToWindow 整图高度适配居中；actualSize 仅显示 100% 局部 ✓。OneDrive 锁产物闪退再现，等待 30s 后启动正常。

## 播放 4K 视频 CPU 高（定位 + 修复，待用户实测）
- 现象与判据（用户提供）：播放 2K–4K 时 CPU 持续 60%+；系统「电影和电视」播同一文件**明显更低** → 排除「解码本身/文件问题」，锁定**应用侧呈现路径**；控制条自动隐藏后 CPU 无变化 → 排除控制条（但命中层不随控制条隐藏，未被排除）。
- 结论：主因是覆盖在视频之上的**全屏透明命中层**（上一轮为接收单击而加）——覆盖层会打断硬件覆盖（zero-copy）路径，每帧经合成器混合，4K 下每帧数十 MB 拷贝。
- 修复：①删除铺满画面的透明命中层，`Tapped`/`PointerMoved` 改挂舞台根 `StageRoot`（经冒泡接收，MediaPlayerElement 未启用传输控件时不处理指针）；②播放态一并隐藏被完全遮挡的全窗背景图 `WallpaperImage`（2560 宽解码位图，避免继续参与每帧合成）。
- 风险与回退：若实测「单击画面唤不出控制条」，说明 MediaPlayerElement 吞了指针事件 → 回退为在画面之上保留命中层，但改为只覆盖画面区（不覆盖标题栏那 48px）并接受合成开销，或改用其他命中方案。
- 验证：`dotnet build -warnaserror` 0 警告 0 错误。**CPU 是否下降需用户实测确认**（未做运行时测量）。
- 未做（待实测后再定）：播放期间让后台常驻任务（元数据回填 `StartBackfillResidency`、缩略图解码）让路——若实测 CPU 仍高，用 `C:\Temp\Pixbian-Diag.ps1 -Tail N` 看播放期间 diag.log 是否仍在产出即可判定。
- 涉及文件：`src/Pixbian/Views/VideoPlayerPage.xaml`、`src/Pixbian/Views/MainWindow.xaml.cs`。
- **实测更正（用户反馈「依然 CPU 高」）**：移除透明命中层**未**降低 CPU → 命中层不是主因（先前假设证伪，勿据此继续排查）。追加改动：窗口根 `RootGrid` 加不透明黑底——窗口若存在透明区域，DWM 按带 alpha 窗口处理、全窗每帧参与 alpha 合成，视频拿不到「独立翻转/硬件覆盖」直通路径；壁纸图铺满其上，常态视觉不变。
- 待用户三实验收敛：①播放时点全屏对比 CPU（全屏走硬件覆盖，若大幅下降即确认窗口合成路径是元凶）；②播放时 `powershell -File C:\Temp\Pixbian-Diag.ps1 -Tail 80` 看后台回填/缩略图是否仍在产出；③用 Release 构建（`.\Pixbian.ps1 -Configuration Release`）复测，排除 Debug 构建自身开销。
- 坑复现：构建报 MSB3026（Pixbian.exe 被运行中的进程锁住）→ 须先结束进程再构建（本轮已由用户批准后结束 PID 13720）。
- 涉及文件（追加）：`src/Pixbian/Views/MainWindow.xaml`。
- **【最终定论】播放 CPU 高 = 文件软解，非应用问题**：用户提供系统「电影和电视」播放同一 4K 文件的任务管理器截图——**Video Decode 同样 0%、CPU 94%**（我们 91%），两者持平。此前「系统播放器明显更低」系对比口径误差。根因：该文件编码不受 UHD 630 硬解支持（AV1/VP9 10bit/HEVC 4:2:2 等），或缺 HEVC 解码扩展。处置走环境侧：装「HEVC 视频扩展」或 HandBrake 转码 H.264/HEVC 8bit。应用侧三处优化（移除透明命中层、隐藏壁纸、窗口根不透明底）保留；**单击画面是否仍能唤出控制条待用户确认**（命中层已删，改为舞台根冒泡接收）。
- **结论二次修正（用户补充：PotPlayer 没这种困扰）**：系统播放器与我们同为 Media Foundation 管线（91% vs 94%）→ 两者持平只证明"同一管线"，**不代表应用侧无解**。PotPlayer 自带 FFmpeg 解码器 + DXVA/D3D11 硬解，不依赖系统 MFT，所以快。Windows 默认不提供 HEVC 解码器（需装「HEVC 视频扩展」）。
- 三条处置（代价递增）：①装/换 HEVC 扩展（仅 HEVC 有效、零代码）；②`MediaSource.CreateFromUri` 替换 `CreateFromStorageFile` 做 A/B（1 行）；③引入 FFmpegInteropX 换解码后端（只换解码，MediaPlayerElement 呈现与界面不变；代价包体 +数十 MB、LGPL 合规）。
- 前提与待确认：拿到视频编码（项目已能读 `VideoMetadata.VideoCodec`，取自 MediaClip 的 Subtype，界面未展示）；用户是否接受引入 FFmpeg 依赖（产品决策）。
## 引入 FFmpegInteropX 换解码后端（方案③ 落地）
- 决策：视频为 **AV1**、UHD 630 无硬解 → 用户确认接受引入 FFmpeg（+数十 MB 包体、LGPL）。
- 依赖核实（NuGet 官方页，非凭记忆）：FFmpegInteropX 2.1.0.81200，库 Apache-2.0，支持 WinUI 3 / 桌面，资产 net6.0-windows10.0.17763；ffmpeg 二进制 LGPL-2.1-or-later；内置 D3D11 硬解（H264/HEVC/AV1/VP9 自动探测）+ dav1d AV1 软解。
- 实现：`VideoPlayerViewModel` 新增 `CreatePlaybackItemAsync`——`FFmpegMediaSource.CreateFromStreamAsync` + `CreateMediaPlaybackItem`，失败回退 `MediaSource.CreateFromStorageFile`；`_ffmpegSource` 字段强引用（防 GC 中断播放），`Dispose` 时释放。
- 踩坑四条（均已在 csproj 注释）：①CsWinRT 报 `Platform.xml 10.0.26100.0` 缺失（本机只装 19041）→ 用 `CsWinRTWindowsMetadata` 指向 19041（`TargetPlatformVersion` 被 TFM 覆盖、无效）；②新报 `CsWinRT1028`（6 个自定义 WinRT 类未加 partial）→ 未启用 AOT，NoWarn 豁免并注明启用 AOT 时需补齐；③RID 为空导致 ffmpeg 原生库未复制（运行期静默回退）→ 加条件化 `RuntimeIdentifier=win-x64`；④RID 使产物落到 `win-x64` 子目录 → `Pixbian.ps1` 硬编码路径同步。
- 合规：`docs/THIRD-PARTY-NOTICES.md`（新增，含动态链接/可替换/源码获取说明）+ 设置页「关于」一行归属声明。
- 验证：`dotnet build -warnaserror` 0 警告 0 错误；测试 181 全通过；输出目录已含 avcodec-62/avformat-62/avutil-60/swscale-9/FFmpegInteropX.dll 等。**CPU 是否下降需用户实测**。
- 涉及文件：`src/Pixbian/Pixbian.csproj`、`src/Pixbian/ViewModels/VideoPlayerViewModel.cs`、`Pixbian.ps1`、`src/Pixbian/Views/SettingsPage.xaml`、`docs/THIRD-PARTY-NOTICES.md`（新增）。
- **实测反馈：AV1 CPU 仍接近 100%** → 定位到默认 `VideoDecoderMode=AutomaticSystemDecoder` 会优先系统解码器，AV1 下系统解码器能播就不会用 FFmpeg（换后端等于没换）。修复：按编码判断，AV1 用 `ForceFFmpegSoftwareDecoder`（dav1d），其余保持自动（保住硬解）；并显式 `MaxDecoderThreads = Environment.ProcessorCount`（FFmpeg 默认不放开多线程）。
- 两条 API 事实（编译器实测）：配置挂在 `MediaSourceConfig.Video`（`VideoConfig`）上，`MediaSourceConfig` 本身没有这些属性；`MaxDecoderThreads` 是 `uint`，需显式转换。
- 新增一次性埋点 `VIDEODEC|codec=..|mode=..|threads=..`（回退时记 `fallback=system`），用于确认实际生效的解码后端；查法：`Get-Content "$env:LOCALAPPDATA\Pixbian\Logs\diag.log" -Tail 20 | Select-String VIDEODEC`。
- 验证：`dotnet build -warnaserror` 0 警告 0 错误。CPU 是否下降待用户实测。
- 涉及文件（本轮）：`src/Pixbian/ViewModels/VideoPlayerViewModel.cs`。
- **验证结论（三项证据齐全，FFmpeg 后端确认生效）**：进程路径 `...\win-x64\Pixbian.exe`；已加载模块含 `avcodec-62.dll / avformat-62.dll / avutil-60.dll / FFmpegInteropX.dll`；日志 `VIDEODEC|codec=av1|mode=ForceFFmpegSoftwareDecoder|threads=6`（编码识别、强制软解、线程数均正确）。
- **重要陷阱（务必记住）**：给项目加 RID 后产物移到 `win-x64` 子目录，**旧 exe 仍留在原目录且可直接双击启动**——跑旧产物时缺 ffmpeg 原生库、会静默回退系统解码，表现就是"改动似乎完全没效果"。今后排查"改动没生效"第一件事应确认进程路径（`(Get-Process Pixbian).Path`），确认 ffmpeg 是否加载可用模块列表（`(Get-Process Pixbian).Modules` 过滤 avcodec/FFmpegInteropX）。
- 现状：dav1d 6 线程软解 4K AV1 会跑满多核（任务管理器 100% 属预期），用户反馈播放流畅；要真正降低占用只能把片源转码为 H.264 / HEVC 8bit 走硬解。
