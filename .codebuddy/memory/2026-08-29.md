### WinUI 3 编译四大阻塞坑（重要，务必复用）
1. **XamlCompiler 静默崩溃（ExitCode 1，只报 MSB3073）**
   根因：`MrtCore/…/Microsoft.UI.Xaml.Markup.Compiler.interop.targets` 第 286 行要求 `$(VsInstallRoot)` 非空才能推导 MSVC 路径；而 `dotnet build` 用的 .NET SDK MSBuild **不设置** `VsInstallRoot`，导致 `VCInstallPath32/64` 为空、XamlCompiler 崩溃，真实 XAML 错误被吞掉。
   修复：`Directory.Build.props` 用 `InitialTargets` + `Exec` 调 vswhere 设置 `VsInstallRoot`。
2. **`ControlsResourcesVersion="Version3"` 在 WASDK 1.6 不存在**
   报 `WMC0011: Unknown member`。该属性自 WASDK 1.7 起才有。`XamlControlsResources` 不要加任何属性。
3. **MSB4062 无法加载 `ExpandPriContent` / `RemovePayloadDuplicates`**
   根因：`MrtCore.PriGen.targets` 第 50 行以 `$(MSBuildExtensionsPath)` 拼接 `AppxMSBuildToolsPath`；dotnet SDK 的该属性指向 dotnet 目录（无 AppxPackage 子目录），程序集实际由 VS「通用 Windows 平台开发」工作负载提供。
   修复：① 装 `Microsoft.VisualStudio.Workload.Universal`（必须，缺一不可）；② 在 `Directory.Build.props` 的 **PropertyGroup（评估阶段）** 用 `Exists()` 按 Community/Professional/Enterprise 探测并覆盖 `AppxMSBuildToolsPath`。
   **注意：必须评估阶段设置**。MrtCore 的属性组在项目评估时即求值，放进 Target 为时已晚。
4. **运行时 SxS 错误 `side-by-side configuration is incorrect`**
   根因：`app.manifest` 里的 `<dpiHosted xmlns="…/SMI/2019/WindowsSettings">` 未注册（编译时也有 warning 81010002，但易被忽略）。
   修复：删除 `dpiHosted`，只保留 `dpiAwareness`（SMI/2016）+ `activeCodePage`（SMI/2019）。

### 终端找不到 dotnet 的环境问题（2026-08-29 22:05，已解决）
用户在新终端执行 `dotnet` 报 CommandNotFoundException。**根因不是安装问题，也不是"重开终端"能解决的**：
1. 机器级 PATH **已正确**包含 `C:\Program Files\dotnet\`（用 `[Environment]::GetEnvironmentVariable("Path","Machine")` 确认）。
2. 用完整路径 `& "C:\Program Files\dotnet\dotnet.exe" --version` 能正常输出 `8.0.424`。
3. 真正根因：**explorer 进程的环境块陈旧**。explorer 启动于 12:37，而 SDK 安装于 18:53，
   explorer 早了 6 小时，其环境块里没有 dotnet 路径。
   所有从开始菜单 / 资源管理器 / 桌面启动的终端都**继承 explorer 的环境**，所以重开终端也没用。
4. **解法**：重启 explorer，让它重新读取注册表 PATH：
   `Get-Process explorer | Stop-Process -Force; Start-Sleep 3; Start-Process explorer`
   （副作用：已打开的资源管理器窗口会关闭，任务栏/桌面会闪一下，风险低）
5. 一次性绕过手段（不重启 explorer 时）：在当前终端执行
   `$env:Path = [Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [Environment]::GetEnvironmentVariable("Path","User")`

**诊断教训**：用 `Start-Process powershell` 起子进程验证环境时会**继承当前 shell 的环境**，
无法验证"新终端"的真实情况（我第一次就误判为"重开即可"）。
`Start-Process -UseNewEnvironment` 在本机也报异常不可用。可靠判据是直接对比 explorer 启动时间与软件安装时间。

- 但其 `FFmpegInteropX.DotNet.dll` 内部引用 `Microsoft.Windows.SDK.NET v10.0.26100.38`，与项目编译用的 `v10.0.19041.38` 冲突 → **CS1705**。
- 把 TFM 升到 `net8.0-windows10.0.26100.0` 也走不通：CsWinRT 需要 `C:\Program Files (x86)\Windows Kits\10\Platforms\UAP\10.0.26100.0\Platform.xml`，本机只有 19041 的，需装 1–2GB 的 SDK 26100。
- **实际包体积 175.6 MB**（`ffmpeginteropx.desktop.ffmpeg` v8.1.2 占 166.1 MB），远超方案预估的 60–100 MB。
- **许可是好消息**：官方 nuspec 声明 `LGPL-2.1-or-later AND Zlib AND MIT`，**不含 GPL**（未链 libx264/libx265），故无需开源本应用。
- 当前实现改用 **Windows 系统 API**（`VideoProperties` + `MediaClip`），保持 1809 兼容、零额外体积；代价是 MKV 与部分编码依赖系统解码器。
- 若要切 FFmpegInteropX，需：装 SDK 26100 → TFM 改 26100 → 重评 1809 兼容目标。切换步骤已写进 `PhotoApps.Media.csproj` 注释。

### 修复了一个 M3 遗留的致命 bug（测试没覆盖到，运行时才暴露）
`MediaItemViewModel.TakenDateText` 写成 `ToString("yyyy'年'M'月'd'日", ...)`。
C# 单引号无需转义，.NET 把它当自定义格式串的引号起始，最后的「日」缺配对引号 → **运行时抛 FormatException**。
M3 时库里无数据、该属性从未求值，所以没暴露；本次启动有数据后直接崩溃（异常码 0xC000027B / STOWED_EXCEPTION，表面看是 WinRT 崩溃，极具迷惑性）。
**正解**：用字符串插值 `$"{local.Year}年{local.Month}月{local.Day}日"`，彻底避开格式串陷阱。
教训：中文日期/时间不要塞进自定义格式串；`@"h\:mm\:ss"` 那类逐字串写法是安全的（外部已验证过）。

### 排障手法沉淀
- WinUI 崩溃且只看到 `0xc000027b` 时：先看事件日志 `Application Error` 定位模块，再在 `App` 构造/OnLaunched 加**临时启动日志**确认崩溃点，最后挂 `UnhandledException` 打印托管堆栈。本次靠这套组合拳把「看起来像 WinRT 崩溃」的问题定位到一行 C# 日期格式化。
- 现状：`App.OnUnhandledException` 会把异常追加到 `%LOCALAPPDATA%\PhotoApps\Logs\crash.log`。

### 🐛 修复了跨线程修改 UI 集合导致的随机崩溃（严重，M4 后实测发现）
现象：`PhotoApps.exe` 启动时**有时崩溃**，异常码 `0xc000027b`（STOWED_EXCEPTION），
故障模块 `Microsoft.UI.Xaml.dll`；且**不触发 `Application.UnhandledException`**（crash.log 为空），
即 WinUI 的 XAML 层原生 FailFast，托管异常处理器抓不到。

根因：**仓储层统一使用 `ConfigureAwait(false)`**（为提升吞吐），导致 ViewModel 里
`await _mediaItems.QueryAsync(...)` 之后代码落到**线程池线程**，紧接着执行
`Items.Clear()` / `Items.Add()` 修改 `ObservableCollection`。
`ObservableCollection` 与 `BitmapImage` 都不是线程安全的，XAML 从非 UI 线程收到集合变更通知即崩溃。
因为是竞态，加/不加日志的时序差异就能决定崩不崩 —— 极难复现与定位。

修复（已验证连续 3 次启动稳定）：
1. 新增 `src/PhotoApps/Services/DispatcherQueueExtensions.cs`，提供 `EnqueueAsync(Action)`，
   基于 `DispatcherQueue.TryEnqueue` + `TaskCompletionSource` 把代码块切回 UI 线程。
2. `GalleryViewModel` / `SettingsViewModel` 注入 `DispatcherQueue`（默认 `GetForCurrentThread()`），
   所有 `await` 仓储之后的集合修改与状态更新，一律包进 `_dispatcherQueue.EnqueueAsync(...)`。

**后续铁律**：任何 `await`（尤其是仓储层、带 ConfigureAwait(false) 的）之后要改 UI 绑定集合、
创建 `BitmapImage`、或触发 PropertyChanged 影响界面，必须先切回 UI 线程。

### 诊断手法沉淀（WinUI 3 随机崩溃）
- 崩溃码 `0xc000027b` + 模块 `Microsoft.UI.Xaml.dll` → 多半是**跨线程触碰 UI 对象**，不是 XAML 标记问题。
- `Application.UnhandledException` 抓不到时，不要怀疑处理器写错，先认定是 XAML 层原生崩溃。
- 定位组合拳：临时启动日志（每步写 %TEMP%）确认崩溃点 → 挂 UnhandledException 抓托管堆栈
  → 若日志为空则转向线程亲和性排查。本次最终靠"代码没变却时崩时不崩"这一现象锁定为竞态。

### 随机抽样设计要点
- **随机数用 `RandomNumberGenerator.GetInt32`**，不用 `Random.Shared`——后者取模有偏差且可预测，随机浏览场景会呈现明显重复模式。

### 🐛 第二轮跨线程崩溃（发现模式引入，已修复，教训更深）
现象：应用启动数秒后进程消失（首次检查 responding=True，4 秒后 PROCESS GONE），`0xc000027b` + `Microsoft.UI.Xaml.dll`，crash.log 仍为空。

**根因不是一处而是两层，比上一轮更深**：
1. `DiscoverViewModel.NextAsync`：`PickRandomAsync` 全程 `ConfigureAwait(false)` → await 后在线程池线程直接改 `StatusText`、发起 `EnsureThumbnailAsync`（内部 `new BitmapImage()`）。
2. **`EnqueueAsync` 的延续陷阱（本轮新认知）**：`await _dispatcherQueue.EnqueueAsync(action)` 完成后，调用方延续**落回发起时的线程上下文**——若发起时在线程池线程（无同步上下文），延续就在线程池线程！
   所以 `GalleryViewModel.ExecuteLoadAsync` 里 EnqueueAsync 之后的 `LoadThumbnailsForVisibleItemsAsync`（内部创建 BitmapImage）仍在错误线程；
   连 `finally { IsLoading = false; }` 也是。这解释了「图库加载完几秒后崩溃」——缩略图异步解码完成、创建 BitmapImage 时崩。

**修复模式（唯一可靠的姿势）**：**所有 UI 状态读写都包进 EnqueueAsync 的 action 内部**，绝不依赖「EnqueueAsync 之后的代码在 UI 线程」这一错误假设：
- 需要跨 await 传递 UI 数据时，在 action 内写入局部变量（闭包捕获），如 `pending` 列表。
- `EnsureThumbnailAsync` 这类必须「在 UI 线程发起」的方法，用 `EnqueueAsync(() => _ = item.EnsureThumbnailAsync(...))` 发起，不 await 结果。
- catch/finally 里的 StatusText/IsLoading 同样要 EnqueueAsync。

本轮修复清单：DiscoverViewModel.NextAsync/FavoriteAsync、GalleryViewModel.ExecuteLoadAsync（含 catch/finally）、SetThumbnailSizeAsync、LoadThumbnailsForVisibleItemsAsync（改为接收 pending 参数）、GalleryViewModel.ToggleFavoriteAsync（同类隐患顺手修复）、删除 DiscoverViewModel.SetCurrentAsync 孤立方法。

### 安全设计要点（M7）
- 只读模式：非 GET/HEAD 一律 405；`/media/{id}` 只收数据库主键，路径来自自有 DB 且必须过 PathGuard（位于已启用库目录内）。

- 会话令牌 256 位 CSPRNG、HttpOnly Cookie、8 小时过期；登录失败 5 次锁 IP 15 分钟；60 req/min 固定窗口限流（除 health）。
- 响应统一安全头（nosniff/DENY/no-referrer/CSP self）；头部值过滤 CRLF 防响应拆分。
- 解析器：头部 16KB/正文 64KB/URI 2048 上限；拒绝绝对 URI；「完整但巨大的头部」也要查大小（测试抓到的真实缺口——最初只在"未找到结束标记"时检查）。
- JSON 输出绝不包含绝对路径；前端只用 textContent 写 DOM（无 innerHTML），CSP 禁内联脚本。
- Web 默认关闭；测试后已把 isWebSharingEnabled 恢复为 false。
