## 搜索栏样式三次修正（聚焦后底部不再变粗变黑）——最终方案

### 现象
搜索框点击获得焦点后，底部边框加粗并变成强调色/深色，与未聚焦状态不一致（默认模板的 Focused 视觉状态所致）。

### 根因（查 WindowsAppSDK 1.6 的 generic.xaml 确认，非猜测）
- `TextControlBorderThemeThickness` = `1`（未聚焦，四边 1px）
- `TextControlBorderThemeThicknessFocused` = `1,1,1,2`（**聚焦时底部加粗到 2px**）
- `TextControlBorderBrushFocused` → `TextControlElevationBorderFocusedBrush`，其渐变含 `SystemAccentColorLight2`（**强调色**）
- 模板 Focused 状态的 `DiscreteObjectKeyFrame` 用 `{ThemeResource}` 引用上述两个键——这正是可以低成本覆盖的切入点

### 修复
在 `AutoSuggestBox.Resources` 中覆盖同名主题资源（ThemeResource 沿视觉树向上查找，元素级优先）：
```xml
<AutoSuggestBox.Resources>
    <Thickness x:Key="TextControlBorderThemeThicknessFocused">1</Thickness>
    <StaticResource x:Key="TextControlBorderBrushFocused" ResourceKey="TextControlBorderBrush" />
</AutoSuggestBox.Resources>
```
仅 2 个资源条目，无需重写 200+ 行 TextBox 控件模板。

## 搜索框边框色：去掉 TextControlBorderBrush 的「黑色底」

### 现象
用户反馈 `BorderBrush="{ThemeResource TextControlBorderBrush}"` 自带一个黑色底边。

### 根因（查 generic.xaml 确认）
`TextControlBorderBrush` → `TextControlElevationBorderBrush`（generic.xaml Light 段 7737 / Dark 段 2183），
是一个 `MappingMode="Absolute" StartPoint="0,0" EndPoint="0,2"` 的**竖向渐变**，并带 `ScaleTransform ScaleY="-1" CenterY="0.5"` 翻转：
- `GradientStop Offset="0.5"` = `ControlStrongStrokeColorDefault` = 浅色 **#72000000**（45% 黑）→ 翻转后落在**底部**
- `GradientStop Offset="1.0"` = `ControlStrokeColorDefault` = 浅色 #0F000000（6% 黑）→ 落在顶部

上淡下深，所以底部看起来有一条黑边。这是 WinUI「elevation border」的刻意设计，不是 bug。

### 修复
在 `AutoSuggestBox.Resources` 里覆盖同名资源为纯色（沿用覆盖 ThemeResource 的手法）：
```xml
<StaticResource x:Key="TextControlBorderBrush" ResourceKey="ControlStrokeColorSecondaryBrush" />
```
`ControlStrokeColorSecondaryBrush` = 浅色 #29000000（16% 黑）/ 深色 #18FFFFFF，四边一致且随主题切换。

### 备选色（改 ResourceKey 即可换挡）
| 资源键 | 浅色值 | 深色值 | 观感 |
|---|---|---|---|
| `ControlStrokeColorDefaultBrush` | #0F000000 | #12FFFFFF | 极淡，接近无边框 |
| `ControlStrokeColorSecondaryBrush` | #29000000 | #18FFFFFF | 适中（已采用） |
| `ControlStrongStrokeColorDefaultBrush` | #72000000 | #8BFFFFFF | 与原渐变底部同深度，偏重 |

若要完全固定色值（放弃主题自适应），改用：
`<SolidColorBrush x:Key="TextControlBorderBrush" Color="#E5E5E5" />`

在无交互桌面会话里模拟鼠标悬停**不可靠**，本次依次失败：

## 列表缩略图清晰度优化（自适应视图主因：请求尺寸语义错误）

### 根因分析（4 条，按影响排序）
1. **请求尺寸与显示尺寸不匹配（最主因）**：`JustifiedPanel.RowHeight = ThumbnailSize`，条目显示宽度 = 宽高比 × 行高；
   但 `GetThumbnailAsync(mode, size)` 的 size 是**最长边**语义，调用方传的却是行高。
   3:2 横图显示 384×256 却只请求 256 长边（实际位图 256×171）→ 放大 1.5 倍；16:9 放大 1.78 倍；2:1 放大 2 倍。
2. **DPI 缩放失效**：`DisplayInformation.GetForCurrentView()` 在 WinUI 3 桌面应用中已弃用且通常抛异常，
   原代码 catch 后回退 `dpiScale = 1` → 150%/200% 屏上缩略图只有 1x 分辨率。
3. **系统缩略图未要求精确缩放**：未传 `ThumbnailOptions.ResizeThumbnail`，系统返回缓存中最接近的档位，
   可能小于请求值，位图被拉伸后发虚。
4. **条目 Margin 破坏内容区宽高比**：自适应条目模板 `Border Margin="0,0,8,8"`，而 `JustifiedPanel` 按
   `ratio × RowHeight` 分配尺寸 → 内容区比分配尺寸少 8px，宽高比与位图失配，
   `Stretch="Uniform"` 后一边留白、露出 `ChromeMedium` 背景色边，且非整数缩放使边缘发虚。

### 修复
- `ThumbnailSizes`（Core/Models/AppSettings.cs）：新增 `DecodeBuckets = [128,192,256,384,512,768,1024,1536,2048]`
  与 `SnapToBucket(double)`，把请求尺寸量化到固定档位，控制系统的缩略图缓存与内存缓存条目规模。
- `ThumbnailService`：删除 `DisplayInformation`（弃用 API），改由 `IThumbnailService.RasterizationScale`
  接收主窗口同步的 `XamlRoot.RasterizationScale`，按**物理像素**请求；
  请求时传 `ThumbnailOptions.ResizeThumbnail` 强制系统精确缩放；回退解码路径改用
  `DecodePixelType.Physical` 且同时给宽高（解码器保持宽高比 Fit 到框内，避免整幅解码的内存峰值）；
  缓存键加入「代次」，缩放比变化时整体失效，旧代次条目随滑动过期淘汰。
- `MediaItemViewModel`：`EnsureThumbnailAsync` 按 `size × Clamp(AspectRatio,1,2)` 推导显示区最长边再量化
  （上限 2 倍：常见画幅 4:3~2:1 全覆盖，全景图不至于让内存成倍膨胀）；
  首帧宽高比多为 1.0，位图到位后若目标尺寸变大则补一次升级加载——**只升级不降级**，
  否则解码舍入造成的宽高比抖动会在档位边界来回重新解码；用 `_inflightSize` 防重入递归。

## 列表缩略图三次修复（修复「图片变形」回归）

## 列表缩略图四次优化（改用 WIC Fant 重采样——画质感根因）

### 根因
前三次都在改「解码分辨率」，但分辨率到位后画质仍偏软。真正的差距在**插值算法**：
- `BitmapImage.DecodePixelWidth` 走 WIC 默认路径，**插值模式不可控**；
- `BitmapTransform` 的默认 `InterpolationMode` 是 `Linear`（**双线性**），
  在中等比例缩小（如 1200×800 → 768×512，约 0.64 倍）时会丢细节并产生锯齿。
  这正是 Windows 照片应用与 Pixbian 的画质差距所在。
- JPEG 大图虽然能吃到 WIC 的 DCT 域预缩放（1/2、1/4、1/8），插值影响较小；
  但中等尺寸图与非 JPEG 格式（PNG/HEIC/WebP）无 DCT 缩放，插值质量就是全部。

### 修复（`ThumbnailService.DecodeImageThumbnailAsync`）
改用 `BitmapDecoder` + `BitmapTransform` 显式高质量降采样：
```csharp
var decoder = await BitmapDecoder.CreateAsync(stream);
var target = ComputeTargetSize(decoder.OrientedPixelWidth, decoder.OrientedPixelHeight, physicalSize);
using var softwareBitmap = await decoder.GetSoftwareBitmapAsync(
    BitmapPixelFormat.Bgra8,
    BitmapAlphaMode.Premultiplied,
    new BitmapTransform {
        ScaledWidth = (uint)target.Value.Width,
        ScaledHeight = (uint)target.Value.Height,
        InterpolationMode = BitmapInterpolationMode.Fant   // 关键：替代默认的 Linear
    },
    ExifOrientationMode.RespectExifOrientation,
    ColorManagementMode.ColorManageToSRgb);
```
- 用 `OrientedPixelWidth/Height`（已计入 EXIF 方向）算目标尺寸，配合 `RespectExifOrientation`，
  竖拍横图不会被压反；`ColorManageToSRgb` 保证宽色域（Adobe RGB / Display P3）正确转换。
- 原图不大于目标时直接全尺寸解码，跳过降采样与中转。
- `BitmapImage` 不能直接承载 `SoftwareBitmap`，故编码到 `InMemoryRandomAccessStream` 再交给它解码；
  **不再设 `DecodePixel*`**（流已是最终尺寸，再降采样等于二次缩放，且保证了不变形）。

### 中转编码器的选择（性能）
- JPEG 无 alpha → `BmpEncoderId`（纯内存拷贝，开销可忽略）；
- 其余格式可能有 alpha → `PngEncoderId`（保留 alpha，否则透明区被预乘成黑底）。
- 判断依据：`decoder.DecoderInformation.CodecId == BitmapDecoder.JpegDecoderId`。

  凡拿不准的 API 名，用二进制搜 winmd 字符串表确认（winmd 字符串堆是 **ASCII/UTF-8**，不是 UTF-16）：
  `[System.Text.Encoding]::ASCII.GetString([System.IO.File]::ReadAllBytes($winmd)).IndexOf("方法名")`。
- winmd **不能**用 `[System.Reflection.Assembly]::LoadFrom` 加载（.NET 8 报 0x80131515 不支持操作），
  且 Windows PowerShell 5.1 没有 `System.Reflection.Metadata`，只能走二进制字符串搜索。
