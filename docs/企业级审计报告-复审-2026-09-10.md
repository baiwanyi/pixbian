### 1.2 三条关键结论

1. **供应链是本轮最实质的风险，且已被门禁放过。** 实测 `dotnet list package --vulnerable --include-transitive` 报出 `SQLitePCLRaw.lib.e_sqlite3 2.1.6`（**High**）与 `SixLabors.ImageSharp 3.1.7`（Moderate）两个漏洞依赖；而由 `.github/workflows/ci.yml:25-29` 组成的「restore → build `-warnaserror`」两步门禁在本机实测为 **0 警告 0 错误**——**漏洞告警不会在 build 阶段重放，因此 CI 永远不会因为它失败**。修复成本极低（改两行版本号），应作为 P0。

2. **README 与实现存在方向性矛盾，会误导使用者、审计者与贡献者。** README 明确写「**关于 FFmpeg：未引入**」，而 `src/Pixbian/Pixbian.csproj:110` 直接引用 `FFmpegInteropX 2.1.0.81200` 并随产物分发原生 FFmpeg 8.1.2（`avcodec-62.dll` 等）。技术栈表同样整表过时（宣称 .NET 8 / C# 12 / SDK 8.0.424，实际 net10 / LangVersion 13 / 10.0.401），测试规模宣称 181 而实际 356。文档可信度直接影响安全与许可判断，应作为 P0。

3. **数据层的「查询-索引」匹配度是性能的主要短板。** 项目在分页（键集游标 151×）与缩略图管线上的工程水平已达产品级，但索引层仍是「一列一索引」的朴素形态：键集分页缺 `(排序列, id)` 复合索引、页头统计每次两次全表 `COUNT(*)`、对账查询同时受 `OR` 与 `LIKE` 前缀通配拖累，且对账把三份全量集合（发现/既有/命中）同时驻留内存。10 万条量级下这是**内存与延迟的双重线性恶化点**。

### 2.2 CI 门禁有效性（实测，High）

| 检查 | 命令 | 实测结果 |
|---|---|---|
| CI 等价构建 | `dotnet build Pixbian.sln -c Release -warnaserror` | **已成功生成，0 警告 0 错误**（耗时 22s） |
| 漏洞扫描 | `dotnet list package --vulnerable --include-transitive` | **2 个易受攻击的包**（见 2.1） |

**结论**：`.github/workflows/ci.yml:25-29` 的两步式流程（`dotnet restore` → `dotnet build --warnaserror`）**无法把 NuGet 审计告警提升为构建错误**。原因是 NuGet 审计告警（NU1901–NU1904）在 **restore 阶段**产生；当 restore 已完成、项目处于 "所有项目均是最新的" 状态时，`dotnet build` 不会重放审计告警，`-warnaserror` 因而不触发。这不是 `NoWarn;NU1900` 造成的（NU1900 是"漏洞库不可达"，与真实漏洞 NU1902/NU1903 无关，前轮的豁免判断本身正确），而是**流程设计缺口**。

**修复（P0）**：在 CI 增加独立的门禁步骤，把漏洞扫描本身变成失败条件：

```yaml
- name: Audit vulnerable packages
  shell: pwsh
  run: |
    dotnet list Pixbian.sln package --vulnerable --include-transitive |
      Tee-Object -Variable audit
    if ($audit -match '易受攻击的包|has the following vulnerable') { throw '发现易受攻击的依赖' }
```

### 4.1 经本轮核实**属实**的安全控制（不必返工）

- **HTTP 解析边界完备**：头部 16 KB / URI 2048 B / 请求体 64 KB 上限（`HttpRequestParser.cs:30-32`）；完整但超限的头被二次校验拒绝（`:56-59`）；不支持 `chunked` → 无分块攻击面。
- **慢速攻击防护到位且认知正确**：首字节 10 s / 整连接 60 s 链接令牌，注释明确指出 `NetworkStream.ReadAsync` 不受 `ReceiveTimeout` 约束这一常见误区（`WebAccessServer.cs:318-325`）。
- **响应头 CRLF 注入防护**：写入前过滤 `\r`/`\n`（`HttpTypes.cs:159-163`）。
- **并发连接有上限**：32（`WebAccessServer.cs:82,94,301`），超限直接关闭不排队。
- **认证链路正确**：PBKDF2-SHA256/100k/16B 盐、`FixedTimeEquals` 恒定时间比较、256 位 CSPRNG 令牌、8 小时过期、UA 绑定、令牌轮换、无会话固定（登录即签发全新令牌）。
- **限流键不可伪造**：取自套接字源 IP（`WebAccessServer.cs:328`），**未使用** `X-Forwarded-For` 等客户端可控头。
- **越权（IDOR）防护**：`{id}` 强制 `long.TryParse` + 主键查库，客户端无法传路径；`PathGuard` 校验在打开文件之前（`WebAccessServer.cs:641,686`）；对外 JSON 不含绝对路径。
- **Range 解析严格**：拒绝多区间、`start<0`、`start>=len`、`end<start`，end 钳制到 `len-1`（`RangeParser.cs:31,56,71,83,88-91`）。
- **静态资源为嵌入常量**，不读磁盘、无路径拼接（`WebAssets.cs:26,29,37,44`）。
- **日志脱敏与防注入**：IP 记 /24（`AppLog.cs:57-78`）、`\r\n` 清洗防日志伪造（`:109-113`）、不记录口令与令牌。
- **异常不泄漏**：客户端响应为固定文本，堆栈仅落日志（`WebAccessServer.cs:471-474,664-670`）。
- **搜索参数经参数化 + 通配符转义**：`% _ \` 转义后绑定 `@search`（`SqliteMediaItemRepository.cs:660-661,724-728`）。

### 7.2 三条最关键的差距与可借鉴动作

**差距 1：依赖治理"零自动化"，而同栈的 Files 与对标的 Jellyfin/Immich 均有自动化。**
Pixbian 拥有 CI 却未把**漏洞扫描**纳入门禁（2.2 已实测证实），也没有锁文件与自动更新。这是"有流水线但流水线不查最关键的东西"。
→ **可借鉴**：Files 的 Dependabot 自动 PR + Immich 的 SBOM 产物。**动作**：CI 增加漏洞门禁步骤（2.2 已给出 YAML）+ 启用锁文件 + 开启 Dependabot。

**差距 2：大图与缓存缺"中间档"，是内存问题的结构性根因。**
Immich 用 thumb/preview/original 三尺寸，digiKam 多级持久化，Windows 照片用分块渐进；Pixbian 是"512 缩略图 → 原图全解"的两端跳变（虽有 8192 兜底）。前轮已识别此点（P-01/P-02 的根因）。
→ **可借鉴**：Immich 的"多尺寸预生成 + 按视口取用"。**动作**：在 512 与原始之间增加 1024/2048 档，查看器按视口请求对应档位，仅在 1:1 时加载原图。

**差距 3：远程共享的威胁模型停留在"可信家庭局域网"，而 Immich/Jellyfin 默认"零信任"。**
Pixbian 已在 UI/文档显式化前提（前轮 7.15，方向正确），但仍缺**多用户/RBAC**与**审计日志的完整闭环**（本轮 SEC-01 指出限流表本身还是 DoS 面）。
→ **可借鉴**：Jellyfin 的"官方推荐反向代理终止 TLS + Hardening 文档"路线（Pixbian 已对齐）。**动作**：保持不内置 TLS 的取舍，但补齐 S-103/S-102 的依赖升级，避免"Zero Trust 的文档 + 有漏洞的实现"这种反差。

### 7.3 相对成熟案例的**优势项**（应保持）

- **领域层纯净度**：Core 零项目引用、零平台依赖（对标产品多把领域逻辑与平台耦合）。这是同类个人项目中少见的纪律。
- **实测结论沉淀**：把"为什么不做"的实测证据写入配置注释（如 `Pixbian.csproj:73-90` 对两处 `NoWarn` 的完整论证），可维护性高于多数同类项目。
- **索引分离与游标分页**：键集游标 + 固定 `random_rank` 的组合，规避了同类项目常见的深翻退化与随机分页重复/遗漏。

**经复核判定不做的四项（含理由）**：

| 原方案 | 复核结论 |
|---|---|
| 对账改流式分块比对（原 PERF-01） | 差集语义决定了「本次发现的路径集合」必须驻留（用于判定库内路径是否仍存在），能省的只有 `existing` 那一份，即峰值内存由三份降为两份。10 万条目量级下三份合计约 30–60 MB，属可接受范围；而改动需把仓储接口从 `IReadOnlyList<string>` 改为异步流，触及接口、实现、索引服务与三处测试桩。**收益与改动面不匹配，不做。** |
| 缩略图缓存改用索引库 `file_size`/`modified_utc` 替代源文件 `stat`（原 PERF-06） | 两点证伪：① `FileInfo.LastWriteTimeUtc` 读的是文件系统元数据（NTFS 上通常驻留内存），并非必然产生物理寻道，收益被高估；② **正确性风险**——索引库的 mtime 可能已陈旧（文件被外部修改但未重新索引），用它判断「源是否变化」会漏判，反而把过期缩略图当作有效返回。现实现直接 stat 源文件属**正确性优先**。**不做。** |
| 缩略图内存表设条目上限（原 PERF-06 后半） | 前提被既有机制证伪：`_entries` 规模受 `_capacityBytes`（LRU 2 GB）约束，条目数 ≈ 容量 ÷ 平均条目大小，并非无界增长；真实相册（10 万张、单档位）下约 10–15 MB。**不做。** |
| 路径校验加实体解析防符号链接绕过（原 SEC-10） | 两点：① `ImageEditService` 目前**界面尚未暴露任何落盘编辑入口**，该攻击面不存在；② 正确解析任意层级目录的符号链接需要 `GetFinalPathNameByHandle` 级别的 P/Invoke，而现有 `ValidateDestination` 已覆盖「同一路径 / 大小写变体 / `..` 归一后相同」三种主要情形。**收益低于复杂度，不做。** |

**新增测试 5 个**（测试基线 356 → **361**）：`TryLogin_超长密码_按失败处理`、`ValidatePasswordStrength_超长密码_被拒绝`、`StartAsync_会话相关响应_禁止被缓存`、`GetPathsUnderDirectoryAsync_前缀相似的兄弟目录_不发生误匹配`（守护区间改写边界：`D:\Lib` 不得匹配 `D:\Lib2` / `D:\LibX`）、`迁移v8_创建分页与计数所需索引`。

### 百万条规模实测与首屏排序修复（2026-09-10 同日续）

**触发**：用户告知后期库规模约 **100 万条**，此前基于 10 万条的判断需重新验证。按「先测真实规模 → 再测单点耗时 → 最后改代码」的方法论，用递归 CTE 灌入 100 万条合成条目实测（`modified_utc` 逐行递增以避免排序退化）：

| 测量项（100 万条，库文件 475 MB） | 结果 |
|---|---|
| 灌入 100 万条（含 12 个索引维护） | 39.3 s |
| 页头计数 `CountByQuery` | **26 ms** |
| 深页键集游标 `QueryAsync(60)` | **2 ms** |
| 对照：原生 `ORDER BY modified_utc, id LIMIT 60` | **0 ms** |
| 仓储首屏 `QueryAsync(60)` | **331 ms** |
| 子树路径 `GetPathsUnderDirectoryAsync`（返回 100 万条） | 551 ms / 托管堆 +69 MB |

**修复一：首屏排序不走索引（331 ms）**

无游标的首屏走 `ORDER BY CASE WHEN @sortKey = 0 THEN ... END, ..., file_name ASC`——**表达式排序无法使用索引**，100 万行必须逐行求值再排序。对照实验最直观：同语义的原生列排序 **0 ms**，仓储查询 **331 ms**。键集分支（后续页）用的是真实列名，所以 2 ms、只有首屏受损。

修复为按内部常量列名拼接（`ResolveOrderClause`，列名与方向词均不来自用户输入）后复测：**331 ms → 0 ms**。

**修复二：随机排序首屏与后续页序列不一致（正确性缺陷）**

随机排序的首屏用 `(id * @seed) % 1000003`，而后续页的游标分支用 `random_rank >= @cursor`——**两者是不同的序列**，随机浏览翻页会重复或遗漏条目（SchemaV4 引入 `random_rank` 正是为解决该问题，但首屏分支未同步）。现已统一为 `random_rank ASC`。

副排序键亦由 `file_name` 统一为 `id`，与键集分支一致；此前两者不同，相同主排序键取值下首屏与后续页同样会错位。

**实测修正的两个判断**：

| 原判断 | 实测结论 |
|---|---|
| 「页头计数需要计数缓存或增量维护」 | **不需要**——26 ms 可接受，v8 的 `(kind, deleted_utc)` 索引已使计数走 index-only scan |
| 「对账三份集合约 280 MB」 | **量级成立但来源需修正**：实测单份 69 MB（合成路径较短），按真实路径长度折算约 130 MB/份、三份约 280 MB；但优先级应排在首屏之后 |

**测试调整**：`CategoryRepositoryTests.QueryAsync_按分类筛选_仅返回该分类条目` 与 `MediaQueryTests.DeleteByIdsAsync_按主键删除` 此前通过下标假设固化了旧的 `file_name` 副排序键，已改为按文件名 / 主键定位，使其只验证各自声明的语义；新增 `QueryAsync_首屏与后续页_副排序键一致` 锁定「分页拼接 = 单次全量」契约。

**验证**：`build -c Release -warnaserror` **0 警告 0 错误**；`test -c Debug` **362 通过 / 0 失败**（移除临时基准后：Core 233 / WebServer 65 / Imaging 14 / UI 50）。

**遗留（仍未做）**：对账流式化（三份集合约 280 MB 峰值）与元数据回填在 100 万条下的收敛问题（现参数单次最多 5000 条，跑完 100 万条需触发约 200 次）。

### 对账流式化与回填复核（2026-09-10 同日续）

**一、对账流式化（已实施）**

原实现把「本次发现的路径」「库内既有路径」「命中集合」三份同时驻留托管堆，百万条规模下按真实路径长度折算约 280 MB。改造为：

- `discovered` 直接累积为 `HashSet`（不再额外保留一份 `List` 引用）
- 新增 `IMediaItemRepository.EnumeratePathsUnderDirectoryAsync`（`IAsyncEnumerable<string>`），对账改为**流式读取库内路径并即时比对**，失效条目按 500 条一批删除

峰值内存由「三份全量」降为「一份集合 + 一个删除批次」，后者恒定与目录规模无关。

**未采用的替代方案**：曾考虑用 `indexed_utc` 作扫描标记，以单条 SQL 完成差集删除（`WHERE indexed_utc < @scanTime`，内存趋近 0）。放弃原因：该方案把对账正确性绑定到「时间戳严格递增」这一新前提上，时钟回拨或两次扫描落在同一时刻会让行为依赖 `<` 与 `=` 的精确区分；对账是**不可逆删除**，不值得为再省 130 MB 引入新的正确性依赖。

**二、元数据回填复核（结论：无需改造，此前判断有误）**

此前依据「每批 200 条 × 并发 2 × 单次 25 批」推断「100 万条需触发 200 次、等于不可用」。复核代码后发现**自动续跑已存在**：`SettingsViewModel.StartBackfillResidency` 在启动 8 秒后进入常驻循环，每轮推进 25 批（5000 条）、间隔 1 分钟后继续，直到清零退出。

真实约束是**吞吐**而非触发次数：按每批约 4 秒（2.5 秒探测 + 1.5 秒让出）计，100 万条约需 8.9 小时。这是「不与前台争抢磁盘 IO」的有意取舍（机械盘上并发度与让出比例直接决定前台是否卡顿），且回填不阻塞浏览（缩略图独立解码，仅尺寸 / 时长排序与等高比例在填充完成前不够精确），故**不做改动**。

**可选的参数调整（留待决定，未擅自改）**：轮间 1 分钟停顿占单轮时长约 37%（25 批 ≈ 100 秒 vs 停顿 60 秒），缩短至 5 秒可提速约 1.5 倍（8.9 → 5.8 小时），代价是减少一次长时间喘息。因无法在真实文件系统上实测其前台影响，暂不改动。

**验证**：`build -c Release -warnaserror` **0 警告 0 错误**；`test -c Debug` **362 通过 / 0 失败**（Core 233 / WebServer 65 / Imaging 14 / UI 50）——对账改造未改变既有对账用例的语义。

**用户手工验收（2026-09-10）**：**通过**——真实库扫描对账、图库首屏与连续翻页、随机排序浏览均正常。至此首屏排序修复与对账流式化闭环（提交 `3c4197b`）。

## 十、结论

**Pixbian 的领域层与数据层安全基本功（全参数化 SQL、PathGuard 纵深防御、PBKDF2 + 恒定时间比较、ReDoS 四道防线）经本轮复核仍然**明显优于同类个人项目**，性能工程在缩略图与分页两处已达产品级水平；前轮 11 项"已闭环"中 9 项经代码核实属实。**

本轮把风险重心从"设计缺陷"移到了**两处低成本但被忽视的运维缺口**：

1. **供应链无人看管**——2 个已知漏洞依赖（含 1 个 High）可被局域网触发，且 CI 门禁因流程设计缺口**实测不会拦截**。这是本轮唯一的 High，也是修复成本最低的一项（改版本号 + 加一个 CI 步骤）。
2. **文档与实现反向漂移**——README 在 FFmpeg、运行时版本、测试规模三处与实现矛盾，其中"FFmpeg 未引入"直接影响体积、许可义务与攻击面的判断。

此外，数据层"查询-索引"匹配度（复合索引缺失、每页两次全表 COUNT、对账三份全量集合）是 10 万条量级的线性恶化点，应纳入下个迭代。

完成 P0 四项（约 2 人日）后，本仓可达到 **A−** 水准；P1 完成后在"本地面向个人的媒体浏览器"这一品类中，其工程质量将进入第一梯队。
