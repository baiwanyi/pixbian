## 1. 目标与范围

### 1.1 目标

| 维度 | 目标 |
| --- | --- |
| 产品定位 | Windows 照片应用的轻量替代品，为散落各处的照片与视频建立本地索引 |
| 核心体验 | 打开即用、浏览不卡、缩略图清晰、本地优先 |
| 技术目标 | 验证 WinUI 3 在中等复杂度桌面应用中的工程可行性，沉淀可复用的分层与避坑经验 |

### 1.2 功能范围（现状）

| 模块 | 能力 |
| --- | --- |
| 浏览 | 自适应行式（Justified）与网格双视图；虚拟化 + 分页增量加载；按类型 / 收藏 / 分类 / 目录 / 文件名筛选；排序 = 排序键 × 方向两维 |
| 查看器 | 缩放 0.1×–8×、旋转、幻灯片播放、EXIF 信息面板、按 EXIF 方向自动摆正；显示旋转与落盘旋转分离 |
| 视频 | 系统解码器播放，倍速 0.25×–4×、音量 / 静音、进度拖动；元数据（时长 / 分辨率 / 编码 / 码率 / 音轨） |
| 分类 | 自定义分类 + 正则规则（匹配文件名 / 完整路径 / 扩展名），规则启停、优先级排序、批量重匹配 |
| 索引 | 添加 / 移除扫描源；全量扫描与前缀对账自动清理失效条目；尺寸与时长由后台任务分批回填 |
| 局域网 | 内置 HTTP 服务，浏览器浏览与流式播放；密码保护、只读、IP 限流 |
| 操作 | 多选批量收藏 / 删除 / 重命名；删除走回收站（可还原），或仅从索引移除 |
| 界面 | 自定义标题栏、全窗口背景图 + 玻璃卡片、深浅主题跟随系统 |

### 1.3 非目标（明确不做）

- 不做图片编辑器：裁剪、调色等能力保留在服务层，但**不作为编辑工作流对外暴露**
- 不做云端同步、账号体系、跨设备
- 不做人脸 / 场景 / AI 识别——初版方案中的「发现模式」已全链路移除，理由见 [ADR-11](#adr-11-移除发现模式)
- 不做多语言与遥测

### 2.2 工具链安装

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Install-Toolchain.ps1
```

自动跳过已装组件，需要时弹 UAC。三个易踩的坑：

1. **「通用 Windows 平台开发」工作负载不可省略**。缺失时 PRI 生成任务加载失败，报 `MSB4062`。
2. **VS 桌面开发工作负载会顺带安装某个版本的 .NET SDK**（如 9.x），`global.json` 必须保留，否则可能用附带版本编译导致失败。
3. **非管理员进程调用 `setup.exe` 会以 `ExitCode 5007` 静默失败**，脚本已处理提权。

### 2.3 构建与验证

```powershell
dotnet build -c Release          # 必须 0 警告（CI 用 -warnaserror）
dotnet test -c Debug             # 181 用例，可无 UI / 无网络运行
.\scripts\Build-Pixbian.ps1      # 一键构建并独立启动（不占用终端）
dotnet publish src/Pixbian -c Release -p:Platform=x64 -o artifacts\win-x64
```

### 2.4 目标框架版本规则

界面与平台库的 Windows TFM 取 **`10.0.26100.0`**：以 Win11 25H2（Build 26200）为基准向下取整到
已发布的 SDK 版本——向上取未发布的版本会导致本机 SDK 缺失、构建失败。
TFM 升到 26100 **不需要**安装 26100 SDK，只需本机已发布的 SDK 不高于它。

### 3.1 物理分层

```

├── Directory.Build.props      语言 / 平台 / 包版本集中管理，含 VS 与 PRI 任务路径解析
├── global.json                锁定 .NET 10 SDK
├── Pixbian.sln
├── scripts/Build-Pixbian.ps1       一键构建并独立启动
├── scripts/Register-Pixbian.ps1    发布、自签证书打包并注册稀疏包
├── scripts/Install-Toolchain.ps1   工具链一键安装
├── scripts/New-AppIcon.ps1         由 Assets/app-icon.png 生成多尺寸 ICO 与包徽标
├── docs/                      本文档、界面设计规范、第三方许可声明
└── src/
    ├── Pixbian/               WinUI 3 界面层：Views / ViewModels / Controls / Services / Converters
    ├── Pixbian.Core/          领域层：模型、索引、分类引擎、路径安全（纯 net10.0）
    ├── Pixbian.Data/          SQLite 仓储与 Schema 迁移（纯 net10.0）
    ├── Pixbian.Imaging/       WIC 解码、EXIF 读取、非破坏性编辑
    ├── Pixbian.Media/         视频元数据读取（系统 API）
    ├── Pixbian.WebServer/     局域网 HTTP 服务（纯 net10.0）
    └── *.Tests/               xunit 测试：Core / Imaging / WebServer
```

### 3.2 依赖方向（强制）

```
Pixbian           →  Core / Data / Imaging / Media / WebServer
Pixbian.Data      →  Core
Imaging / Media / WebServer  →  Core（三者彼此不相互依赖）
Pixbian.Core      →  仅 .NET BCL（零项目引用）
```

#### 与初版方案的偏差：Web 服务提供方的调整

初版方案规划 `PhotoApps.Server`（HTTP 服务端）与 `PhotoApps.Client`（HTTP 客户端）两个工程，
意图是让未来的移动端共用同一套 HTTP API。

**实际调整为 `Pixbian.WebServer`。** 原因：

1. 初版方案中「先定义 HTTP 契约、UI 再对接」的**双轨并行前提并不成立**——HTTP 层只是 UI 之外
   的一个薄适配层， abstractions 已在 Core 就位，直接面向 Core 接口开发不影响契约稳定性。
2. HTTP 客户端暂无对应需求，提前建设属于推测性投入。

结论：**保留了威胁模型与安全边界，去掉了无消费者的额外工程**。

### 3.3 关键约束

| 约束 | 理由 |
| --- | --- |
| `Pixbian.Core` TFM 固定为**纯 `net8.0`**，不得引用任何 WinRT / WIC API | 一旦引入 windows TFM，`Core.Tests` 必须在 Windows 上运行，纯领域层测试基线即被破坏 |
| 跨层数据交换统一使用 `Pixbian.Core.Models` | 禁止向上泄漏 `SqliteDataReader` 等基础设施类型 |
| 需要平台能力时：**Core 定抽象 + UI 层注入实现** | 保持 Core 可移植 |
| 包版本只在 `Directory.Build.props` 维护 | 禁止在各 csproj 写死版本号 |
| 只使用稳定发行版 | 禁止 alpha / beta 预发布包 |

## 4. 数据模型

### 4.1 核心模型（`Pixbian.Core/Models/`）

| 类型 | 说明 |
| --- | --- |
| `MediaItem` | 媒体条目。路径为业务主键；承载尺寸、时长、收藏、分类、评分、元数据探测状态与随机序列 `RandomRank` |
| `MediaKind` | 枚举：`Image` / `Video`，存为 INTEGER |
| `Category` | 分类。名称唯一，带展示色与排序号 |
| `CategoryRule` | 分类规则。正则模式 + 匹配目标 + 优先级 + 启停 |
| `RuleMatchTarget` | 枚举：`FileName` / `FullPath` / `Extension` |
| `MediaMetadataState` | 枚举：`NotProbed(0)` / `Completed(1)` / `Failed(2)` |
| `AppSettings` / `WebAccessSettings` | 应用与 Web 服务配置 |

### 4.2 数据库 Schema

SQLite，当前 `PRAGMA user_version = 4`（v1 初始结构 → v2 元数据探测状态 → v3 规模化查询索引 → v4 固定随机序列）。**时间统一存 ISO8601 往返格式 UTC 文本，布尔与枚举存整数。**

#### v1 — 初始结构

```sql
CREATE TABLE media_items (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    path         TEXT    NOT NULL UNIQUE,   -- 业务主键
    file_name    TEXT    NOT NULL,
    directory    TEXT    NOT NULL,
    kind         INTEGER NOT NULL,
    file_size    INTEGER NOT NULL,
    created_utc  TEXT    NOT NULL,
    modified_utc TEXT    NOT NULL,
    indexed_utc  TEXT    NOT NULL,
    taken_utc    TEXT    NULL,
    width        INTEGER NULL,
    height       INTEGER NULL,
    duration_ms  INTEGER NULL,
    is_favorite  INTEGER NOT NULL DEFAULT 0,
    category_id  INTEGER NULL,
    rating       INTEGER NOT NULL DEFAULT 0,
    deleted_utc  TEXT    NULL
);

CREATE TABLE library_folders (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    path          TEXT    NOT NULL UNIQUE,
    display_name  TEXT    NOT NULL,
    added_utc     TEXT    NOT NULL,
    is_enabled    INTEGER NOT NULL DEFAULT 1,
    last_scan_utc TEXT    NULL
);

CREATE TABLE categories (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT    NOT NULL UNIQUE,
    color      TEXT    NULL,
    sort_order INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE category_rules (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    name              TEXT    NOT NULL,
    pattern           TEXT    NOT NULL,
    category_id       INTEGER NOT NULL REFERENCES categories(id) ON DELETE CASCADE,
    target            INTEGER NOT NULL DEFAULT 0,   -- RuleMatchTarget
    is_enabled        INTEGER NOT NULL DEFAULT 1,
    priority          INTEGER NOT NULL DEFAULT 0,
    is_case_sensitive INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE tags (id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL UNIQUE);

CREATE TABLE media_tags (
    media_id INTEGER NOT NULL REFERENCES media_items(id) ON DELETE CASCADE,
    tag_id   INTEGER NOT NULL REFERENCES tags(id)        ON DELETE CASCADE,
    PRIMARY KEY (media_id, tag_id)
);
```

v1 索引：

```sql
ix_media_items_kind       ON media_items(kind)
ix_media_items_taken      ON media_items(taken_utc DESC)
ix_media_items_directory  ON media_items(directory)
ix_media_items_category   ON media_items(category_id)
ix_media_items_size       ON media_items(file_size)
ix_category_rules_enabled ON category_rules(is_enabled, priority DESC)
```

> **注意**：v1 **未建** `is_favorite` 的部分索引——筛选收藏走全表扫描。
> 这是现阶段可接受的设计（收藏条目占比通常很低且总量不大），但属已知优化点。

#### v2 — 元数据探测状态

```sql
ALTER TABLE media_items ADD COLUMN metadata_state INTEGER NOT NULL DEFAULT 0;  -- MediaMetadataState
ALTER TABLE media_items ADD COLUMN metadata_utc   TEXT    NULL;

CREATE INDEX ix_media_items_metadata_pending
    ON media_items(id) WHERE metadata_state = 0;   -- 部分索引，支撑回填的待处理查询
```

#### v3 — 规模化查询索引

`modified_utc` 与 `file_name` 是默认排序与文件名排序的排序键，此前无索引支撑，
每次分页查询都退化为全表排序。SQLite 可反向扫描索引，单列升序索引同时服务升降两个方向。

```sql
CREATE INDEX ix_media_items_modified  ON media_items(modified_utc);
CREATE INDEX ix_media_items_file_name ON media_items(file_name);
```

#### v4 — 固定随机序列与游标分页

把随机排序从「主键乘种子取模」的 `ORDER BY` 表达式（无法走索引、每次查询全表计算）
改为入库时生成一次、永久不变的 `random_rank` 列：排序走索引扫描，
分页基于游标（`rank >= 上一页末条`）而非 `OFFSET` 深翻。
rank 由 `id` 经 Knuth 乘法哈希（乘数 `2654435761`）对素数 `2147483647` 取模生成，
新条目由 `AFTER INSERT` 触发器填充。

```sql
ALTER TABLE media_items ADD COLUMN random_rank INTEGER NULL;
UPDATE media_items SET random_rank = (id * 2654435761) % 2147483647 WHERE random_rank IS NULL;
CREATE INDEX ix_media_items_random ON media_items(random_rank);

CREATE TRIGGER IF NOT EXISTS trg_media_items_random_rank
AFTER INSERT ON media_items
BEGIN
    UPDATE media_items
    SET random_rank = (NEW.id * 2654435761) % 2147483647
    WHERE id = NEW.id;
END;
```

> `MediaQuery.RandomSeed` 仍然保留：游标为 null 时（旧调用方与部分测试）查询回落到
> 「表达式 + `OFFSET`」行为，种子在此路径下继续生效。界面侧的随机浏览一律走游标路径。

### 4.3 迁移规则

- 版本号记录于 `PRAGMA user_version`，迁移在**单个事务内**原子执行，中断后重启可续跑。
- **已发布的迁移脚本禁止修改**。需要变更结构时新增 v(N+1)。
- 全部 SQL 参数化，动态条件统一 `(col = @p OR @p IS NULL)` 形式。

## 5. 核心流程

### 5.1 索引（两阶段）

索引刻意拆成两个阶段，让界面在秒级可用：

| 阶段 | 执行者 | 内容 |
| --- | --- | --- |
| 扫描 | `MediaIndexingService.ScanAsync` | 只写文件属性（路径、文件名、目录、大小、时间、类型） |
| 回填 | `MediaMetadataBackfillService` | 像素尺寸与视频时长，后台分批补齐 |

扫描要点：

- 「消失文件」对账（`ReconcileAsync`）：扫描完成后取该目录下索引中的全部路径，
  与本次发现集合做**内存差集**（`HashSet` 查找，O(1)/条）后批量删除，避免用 SQL 表达集合差。
  对账**必须在本次全部写入完成后**进行，中途失败不得触发删除，以防数据丢失。
- 移除扫描源时按前缀同步清理其下条目，避免留下无法访问却又可见的僵尸记录。
- 跳过**重解析点**（符号链接 / 联接）、隐藏、系统与临时文件，规避目录环与越权读取。
- 路径入库前经 `PathGuard` 规范化，保证与索引时的前缀一致。
- 扫描以 500 条为一批批量 Upsert；`taken_utc` 取文件系统 created 与 modified 中较早者兜底，
  **不是 EXIF 拍摄时间**（EXIF 的 `TakenAt` 只在查看器解析，既未展示也未回写索引库）。

### 5.2 元数据回填

参数：每批 **200 条**、并发 **2**、批间让出 **1.5 秒**、单次运行最多 **25 批**。

三态设计的关键：**失败必须落为 `Failed`**。否则损坏文件会在每轮被反复捞取，
占用批次额度，导致回填永不收敛。

写回只覆盖 `width` / `height` / `duration_ms` 与状态列；收藏、评分、分类属用户数据，
由 `COALESCE` 保护。

**排他必须用 `Interlocked.CompareExchange` 而非布尔字段**：触发点有扫描回调与启动流程两处，
存在并发进入。改用 `SemaphoreSlim` 持有字段会触发 CA1001（在 `-warnaserror` 下是错误）。

回填与索引刻意解耦：不参与扫描的状态流转、不向用户暴露进度、失败不打断当前操作。
已在回填时直接返回而不排队——两个回填任务会各自取到同一批待处理条目（彼此的更新尚未提交），
重复探测同一批文件并在数据库写锁上互相等待，叠加的持续文件 IO 会让前台浏览表现为卡死。

### 5.3 分类规则

规则按 `priority` 降序、命中即止。用户正则属不可信输入，四道 ReDoS 防护：

1. 编译后构造时**强制 1 秒匹配超时**
2. 触发超时的规则**标记为 `IsDangerous` 并在本次匹配中跳过**
3. **整批匹配 30 秒总时限**
4. 待匹配文本**截断至 4096 字符**

> 初版方案设定截断 260 字符，实际放宽至 4096——260 不足以覆盖深层目录的完整路径。

批量重匹配由 `CategoryViewModel` 驱动：**分页读取 → 逐页 `MatchBatch` → 事务写回**，
避免一次性载入全部条目。

### 5.4 缩略图管线

请求尺寸语义统一为「**显示区最长边**」，处理顺序：

1. 先乘 `RasterizationScale` 换算物理像素
2. 再向上量化到 **17 档解码档位**（128–2560，相邻比值 ≤ 1.33）
3. 最后归一到**统一档位 512**：请求档位 ≤ 512 一律按 512 解码、缓存与落盘，显示端由 `Image` 缩小呈现
4. 缓存键 `path|bucket`

统一档位让磁盘与内存只维护一档主流尺寸：条目数从「档位数 × 文件数」降为「文件数」，
切换视图档位时全量命中、不再重复解码。代价是低档视图的位图内存与重采样成本升高
（512² 对 256² 为 4 倍），由内存缓存的**字节**限额与列表头部瘦身兜底；
超过 512 的请求（大图预览）仍按各自档位缓存。

- 图片：`BitmapDecoder` + `BitmapTransform`，缩小用 `Fant`、放大用 `Cubic`（上限 2 倍），
  遵循 EXIF 方向并色彩管理到 sRGB
- 视频：系统 `SingleItem` 缩略图，保留原始宽高比
- 解码重采样在线程池经信号量限流（并发 `CPU/2`，钳制 2–8），中间产物为 `byte[]`，
  **只在最后一跳回 UI 线程构造 `BitmapImage`**
- 单条编码设 **20 秒超时**：编码内部的文件 IO 无内建取消，文件被杀软锁定或机械盘坏道重试
  会让任务永久挂起并占死解码信号量槽位，进而令整条管线静默死亡；超时后放弃该条并释放槽位，管线自愈
- 成品字节另存**磁盘缓存**（两级哈希分桶、条目头带源文件 mtime + size 指纹、LRU 2 GB），
  命中即跳过「读原图 → 解码 → 重采样 → 编码」全链路；磁盘层是纯加速层，任何故障静默退化为重新编码
- 缓存失效分两种语义：`Invalidate` 为内容真失效（清内存 + 清磁盘），`Release` 仅释放内存位图（保留磁盘）
- `ThumbnailPresenter` 维护「骨架屏 / 缩略图 / 失败占位」三态；切到图片终值的时机以探针 `Image`
  的 `ImageOpened`（**控件级**「内容可绘制」信号，位图级事件只表示 CPU 解码完成）为门闩，
  并再等一渲染帧（`ImageBrush` 的纹理上传可能比探针晚一帧）
- **图片淡入与骨架呼吸动画当前均已停用**：切到图库时 200 张图密集就绪，
  200 个 `Storyboard` 同帧 `Begin` 会压死渲染线程，故直接置终值。门闩与跃迁判据保留，
  现用于决定「何时切终值」，恢复动效须改 Composition API 并只对可见项启用
- 查看器走**两级加载**：先以 512 预览垫场，全图解码完成后替换，并用装载序号防止翻页串图

> **绝对不要让位图尺寸参与任何驱动布局的属性**。位图按档位量化解码，宽高比相对原图有微小偏差；
> 一旦覆盖已有准确值，就会形成「解码 → 宽高比抖动 → 重排 → 回写显示尺寸 → 再解码」的环。
> 位图尺寸只能作兜底（预取与索引均无尺寸时），**优先级必须排最后**。

### 5.5 视频播放

基于 `MediaSource` / `MediaPlayer`，**不引入 FFmpeg**，零额外体积。

元数据读取走 `VideoProperties`（`StorageFile.Properties.GetVideoPropertiesAsync`），
得到时长、分辨率与码率；编码、帧率与音轨参数需另经 `MediaClip` 的编码属性补齐
（并非所有容器都支持，失败时降级为仅基础属性，不整体失败）。
按旋转标记（90 / 270 度）交换宽高存入 `width` / `height`，界面只读不再换算。

### 5.6 图片查看器与非破坏性编辑

- **显示旋转与落盘旋转分离**：显示旋转只改界面渲染变换（`RotationDegrees`，不触碰文件）；
  落盘旋转由 `ImageViewerViewModel.SaveRotationAsync` 经 `ImageEditService` 重编码，
  输出路径由调用方传入，服务层强制「不得与源路径相同」，原文件保持只读
- **落盘旋转当前无界面入口**：`SaveRotationAsync` 在代码中尚无调用方，
  查看器工具栏的「左转 / 右转」只改显示角度，不写文件
- 编辑服务基于 ImageSharp，已实现裁剪、调色与 90 度整数倍旋转；
  任意角度旋转交由界面渲染变换处理、不落盘。界面目前**未暴露任何落盘编辑**
- 按 EXIF 方向自动摆正

### 5.7 删除

两种语义：

| 语义 | 行为 |
| --- | --- |
| 删除到回收站 | `SHFileOperation` + `FOF_ALLOWUNDO`（可还原），成功后同步移除索引记录 |
| 从索引移除 | 仅删数据库记录，不动磁盘文件 |

> **数据库为物理 `DELETE`，非软删除。** `deleted_utc` 列存在且查询时被过滤，
> 但**从未被写入**——初版方案规划的「批量软删除」未实施。保留列不影响正确性。

### 5.8 局域网 Web 服务

基于 `TcpListener` 自研 HTTP/1.1（见 [ADR-05](#adr-05-自研-http-服务)），逐连接独立任务，服务为**只读**。

| 端点 | 说明 |
| --- | --- |
| `GET /`、`GET /index.html` | 浏览器端页面 |
| `GET /app.css`、`GET /app.js` | 前端资源 |
| `GET /api/health` | 健康检查；不鉴权不限流，供网络探测 |
| `POST /api/login` | 登录，换取会话令牌 |
| `GET /api/items` | 分页列表，参数 `kind` / `q` / `offset` / `limit`（`limit` 默认 60，钳制 1–200） |
| `GET /api/items/{id}` | 条目详情 |
| `GET /thumb/{id}` | 缩略图，最长边 320 |
| `GET /media/{id}` | 原始文件流，支持 Range（供视频拖动） |

安全约束：

- 非 `GET` / `HEAD` 一律 `405`
- 媒体与缩略图**只接受数据库主键**，绝不接受客户端传入的路径；落盘前再经 `PathGuard`
  校验位于已启用库目录内
- 对外 JSON **不含绝对路径**

安全机制：PBKDF2（SHA-256，10 万次迭代，16 字节随机盐，32 字节哈希），
存储格式 `迭代数(十进制).盐(Base64).哈希(Base64)`；**密码哈希**用 `CryptographicOperations.FixedTimeEquals`
恒定时间比较，会话令牌只在服务端字典中按哈希查找、不参与客户端可控的比较路径；
令牌为 256 位 CSPRNG，仅存内存，8 小时过期，重启失效；
同一 IP 登录失败 5 次锁定 15 分钟；固定窗口限流 60 次 / 分钟。

## 8. 关键设计决策（ADR）

### ADR-01：.NET 8 + WASDK 2.4

**决策**：全项目统一 `net8.0`（LTS），WASDK 2.4.0。

**理由**：WASDK 2.0 不支持 .NET 9，初版方案的 .NET 9 计划不成立。

### ADR-02：显式平台，禁用 AnyCPU

**决策**：只保留 x64 与 ARM64，构建时校验并在 csproj 内将 `AnyCPU` 重定向到 x64。

**理由**：WinRT 互操作与 WASDK 均要求明确平台，AnyCPU 会在运行期暴露难以定位的失败。

### ADR-03：自包含引入 WASDK，修正 XAML 编译器路径属性

**决策**：`Microsoft.WindowsAppSDK` 以包引入而非运行时下载；XAML 编译器路径属性使用
**`PkgMicrosoft_WindowsAppSDK_WinUI`**。

**理由**：WASDK 2.x 中旧的 `PkgMicrosoft_WindowsAppSDK` 属性已失效，沿用会导致
MarkupCompilePass1 静默失败，症状是全项目爆 `CS0103`，极难归因。

### ADR-04：视频播放走系统解码器，不引入 FFmpegInteropX

**决策**：基于系统解码器，零额外体积。

**理由**：成本收益不成立——FFmpeg 编解码包体积以百 MB 计，而与 `MediaPlayerElement`、
窗口化、Surface 的兼容性问题反而更多。代价是格式支持取决于系统解码器。

> 代价是可接受的：绝大多数用户视频为 H.264 / HEVC。若后续确有 MKV 等特殊容器需求，
> 建议**按需下载 Windows 应用商店解码器**，或评估 FFmpegInteropX（MIT）的打包体积。

### ADR-05：自研 HTTP 服务

**决策**：基于 `TcpListener` 实现 HTTP/1.1，**不用 `HttpListener`**。

**理由**：`HttpListener` 需 `netsh http add urlacl` 预留 URL 或管理员权限，与「免安装、
免管理员、xcopy 部署」的目标冲突。自研约 300 行，只覆盖本项目所需的 GET/HEAD + 静态响应。

### ADR-06：PBKDF2 + 内存会话

**决策**：PBKDF2（SHA-256，10 万次迭代，16 字节盐）+ 恒定时间比较；会话令牌仅存内存。

**理由**：局域网服务面向不可信网络，密码不可明文或弱哈希存储；令牌不落盘则重启即失效，
无需管理吊销列表。

### ADR-07：索引两阶段 + 三态回填

**决策**：扫描只写文件属性；尺寸与时长由后台分批补齐，探测状态三态。

**理由**：让界面秒级可用。三态中「失败必须落为已失败」是收敛的必要条件。

### ADR-08：缩略图档位量化 + 只回传 `byte[]`

**决策**：请求尺寸先乘 `RasterizationScale` 再量化到 17 档，最后归一到**统一档位 512**
（请求档位 ≤ 512 一律按 512 解码、缓存与落盘，显示端缩小呈现）；解码在线程池完成，
中间产物为 `byte[]`，只在最后一跳回 UI 线程构造 `BitmapImage`；成品字节另存磁盘缓存（LRU 2 GB）。

**理由**：档位量化避免同一图片因滚动产生大量不同尺寸的解码结果，直接提升缓存命中率；
统一档位进一步把条目数从「档位数 × 文件数」压缩为「文件数」，切换视图档位时全量命中；
线程亲和性切开可避免跨线程传递 `SoftwareBitmap` 的陷阱。
另设单条编码 20 秒超时，防止被锁定的文件占死并发槽位令整条管线静默死亡。

### ADR-09：分类重匹配分页批处理 + 事务

**决策**：分页读取 → 逐页匹配 → 事务写回。

**理由**：一次性载入全部条目在大库上会引发内存峰值与长事务锁。

### ADR-10：删除走回收站，数据库物理删除

**决策**：文件删除用 `SHFileOperation` + `FOF_ALLOWUNDO`；数据库为物理 `DELETE`。

**理由**：相册类应用的误删代价高，回收站是必要的兜底。数据库不做软删除是因为
索引可从文件系统重建，保留墓碑记录没有消费者。

### ADR-11：移除发现模式

**决策**：初版方案中的「发现模式」（与设备照片 / 通用文件夹集成、时间轴、地点相册）
**全链路移除**，不保留任何残余代码。

**理由**：该能力依赖 Windows 照片应用的封闭实现，且需授予 `broadFileSystemAccess`
与图片库权限——与「轻量替代、本地优先、最小权限」的定位冲突。

### ADR-12：随机排序用入库生成的固定序列，而非 `ORDER BY` 表达式

**决策**：随机排序改用入库时生成一次、永久不变的 `random_rank` 列
（Schema v4：`(id * 2654435761) % 2147483647`，`AFTER INSERT` 触发器填充）。
分页以「`rank >=` 上一页末条」为**游标**推进，不再依赖 `OFFSET`。
`MediaQuery.RandomSeed` 仅作为游标为 null 时的回退路径保留。

**理由**：`ORDER BY RANDOM()` 会对全表排序，数据量上万后开销无法接受。
初版的「主键乘种子取模」表达式虽然避免了全表排序，但仍是 `ORDER BY` 中的计算列，
无法走索引、每次查询都要全表求值，且深翻页时 `OFFSET` 需线性跳过已读行。
改为固定的 `random_rank` 列后，排序退化为索引扫描，分页退化为索引范围查询；
序列在一次「洗牌」内不变，翻页既不会重复也不会遗漏。

| 项 | 说明 |
| --- | --- |
| 深色主题背景图 | 固定 `light.jpg` 不随主题切换，深色下文字对比度不足（`dark.jpg` 已在 Assets 待用） |

> 查看器绕过 `ThumbnailService`（现为两级加载：512 预览垫场 + 全图替换 + 装载序号防串图）、
> 内存缓存按条数限流（现为字节限额 200 MB）。

### 10.3 待实测确认后再优化

以下两项**必须先跑 `EXPLAIN QUERY PLAN` 实测**，不得凭推断动手：

1. SQL 排序使用 `CASE` 表达式导致索引失效
2. `directory LIKE` 前缀与 BINARY 排序规则不匹配

> `OFFSET` 深翻页已由随机排序的游标分页取代（Schema v4：`rank >=` 上一页末条）。
> 非随机排序暂不做游标——2.5 万条实测下 `OFFSET` 是索引遍历（几十毫秒），收益不成立。
