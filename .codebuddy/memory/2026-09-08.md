## 「新建规则」不弹出且污染后续对话框（crash.log 实锤）
- 根因：「归入分类」ComboBox `SelectedValue` 用 x:Bind TwoWay 绑 VM 的 long 属性——分类列表为空/重建时 Selector 把 SelectedValue 置 null，TwoWay 回写拆箱 null → NRE（crash.log：UpdateTwoWay_8_SelectedValue），异常打断弹层 → 对话框不弹且后续 ContentDialog 全部失效。
- 修复：SelectedValue 改 OneWay（VM→UI），UI→VM 由 SelectionChanged 手动回写（`SelectedValue is long` null 安全归零）。SelectedIndex 绑 int 无拆箱风险可保留 TwoWay。
- 方法论：对话框/弹窗类「点击无效」直接查 `%LOCALAPPDATA%\Pixbian\Logs\crash.log`，App.UnhandledException 会把真实异常全量落盘。

- **时间线实证（关键）**：崩溃从 19:11 起就有（早于本次改动），22:09–22:37 用旧构建（Release DLL 23:02 才重建）同样崩；我的改动 23:01 落地、23:07（Debug）仍崩但**崩得更早**（旧构建在 14 条全部 realize 完 1.7s 后崩，新构建在 PREP idx=0 之后立刻崩）。→ 属「早已存在的缺陷被新改动提前引爆」，不要回滚优化。
- crash.log 末尾两条托管异常全在 `JustifiedVirtualizingLayout`：`FindFirstRowEndingAfter` 的 `RowOffsets[count]` 越界（19:19）、`CloseRow` 的 `set_Item` 越界（19:12）——后者即当日日志已修的「哨兵项 / EnsureCapacity」两坑，故 19:1x 的崩溃已修；22:0x 之后的崩溃**无任何托管记录**（LAYOUT 埋点计数 0，measure/arrange 的 try/catch 都没进过）= 纯原生 fail-fast。
- 待验证的两条主因：① `IndexRangeFromY → GetRealizedRange → FindFirstRowEndingAfter` 是唯一**没有 try/catch** 的行表读取路径，且由 `ScrollViewer.ViewChanged` 回调触发，托管异常穿过 XAML ABI 即转成 stowed exception（0xc000027b 且不写 crash.log）；本次把 `_justifiedLayout` 修好后这条链路**首次真正被执行**（此前是死代码），与「改完立刻崩且更早」吻合。② 集合替换走「ItemsSource=null → UpdateLayout() → 新集合」，同步强制布局与 `AspectRatiosApplied → InvalidateRows → InvalidateMeasure` 交错，可能在布局 pass 内失效布局。
- 附带发现（独立缺陷）：`OnScrollViewChanged` 用 `remaining = Extent - Offset - Viewport` 判触底，内容短于视口时 remaining 为负 → 恒满足「距底两屏内」→ 每次 ViewChanged 都发 LoadMore（日志里 14 条的收藏夹反复出现 `reset=False|count=0` 空查询）。判据应补 `remaining > 0`。

## bug1 复盘：等高视图幽灵元素占据首格（1 文件 4 处改动）
- **取证链路**（无堆栈闪退的复用问题推荐方法）：① 复现脚本自启动 + UIA 驱动（点【选择】→ 点导航） + 截屏；② 加 `TempTiming` 探针打印 `SyncJustifiedElements` 遍历结果（`i`/child-index/当前 DataContext/期望 DataContext）。
- **关键证据**（SYNC 探针原话）：
  ```
  SYNC|i=0 |idx=-1|count=109|cur=XHS_(@一只🐰)_...photo_1.jpeg|new=
  SYNC|i=18|idx=0 |count=109|cur=weibo-7893929649-...-1.jpg     |new=weibo-7893929649-...-1.jpg
  ```
  children 0..17 = `idx=-1`（被 Repeater 清空但仍在视觉树上的"幽灵"）且 DataContext 仍持有**上一个列表的第一个文件**；child 18 才是真正承载新 items[0] 的元素。
- **根因**：`ItemsRepeater` 切 `ItemsSource` 时，旧的「置空 → UpdateLayout → 赋新」三步在同一同步块里执行，置空只把元素标成 `idx=-1` 但不会立刻从视觉树卸下；下一拍赋新集合时 `GetOrCreateElementAt` 取不到这些仍在树上的元素（未进回收池），只能新建并追加，幽灵于是占据首格（前几个视觉槽位），新条目被挤到后面——这就是用户看到的「上一个列表的第一个文件替换当前列表的第一个文件」。
- **踩坑**：`ItemsRepeater.ElementClearing` 太激进——任何 recycle 都会触发（不只是 ItemsSource 变化，模式切换/布局变化也会），清掉 DataContext 后列表全空。回退该方案，改成精准清空。
- **根治**（`Views/GalleryPage.xaml.cs`，4 处）：
  1. `RebuildJustifiedElements` 里 `ItemsSource=null` 之前先 `ClearJustifiedElementContexts()` 清掉所有子元素的 DataContext（断掉对旧条目的脏绑定，非布局属性不会触发 fail-fast）。
  2. **`ApplyPendingJustifiedItems()` 不再同拍调用，改成 `DispatcherQueue.TryEnqueue(ApplyPendingJustifiedItems)`**——延一个消息拍，让 Repeater 完成对清空元素的回收/从视觉树卸下，下一拍赋新集合即走 `GetOrCreateElementAt` 的复用路径而不是新建追加，幽灵消失。
  3. `SyncJustifiedElements()` 按索引兜底对齐 DataContext（幽灵场景下全部 `continue`，但作为未来保险保留）。
  4. 探针移除。
- **验证**：构建 `-warnaserror` 0 警告 0 错误；自启动 + UIA 复现脚本 + 截屏，切换到 youtube 后 9 个缩略图全部正确渲染，首格显示正确的 youtube 第一条。日志 `ENS|just|idx=0|name=<youtube[0]>` 立即触发。
- **教训**：ItemsRepeater 切 ItemsSource 的「null → UpdateLayout → new」三步需要拍间隔（TryEnqueue）让 Repeater 完成 recycle；同拍执行 = 新元素追加在幽灵之后 = 视觉错位。这条对所有 ItemsRepeater 项目通用。

## bug1 第二轮：选择状态跨集合残留干扰回收（1 文件 1 行改动）
