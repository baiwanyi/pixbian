## 1. 目标与范围

### 1.1 目标

| 维度 | 目标 |
| --- | --- |
| 产品定位 | Windows 照片应用的轻量替代品，为散落各处的照片与视频建立本地索引 |
| 核心体验 | 打开即用、浏览不卡、缩略图清晰、本地优先 |
| 技术目标 | 验证 WinUI 3 在中等复杂度桌面应用中的工程可行性，沉淀可复用的分层与避坑经验 |

### 1.2 功能范围（现状）

| 模块 | 能力 |
| --- | --- |
| 浏览 | 自适应行式（Justified）与网格双视图；虚拟化 + 分页增量加载；按类型 / 收藏 / 分类 / 目录 / 文件名筛选；排序 = 排序键 × 方向两维 |
| 查看器 | 缩放 0.1×–8×、旋转、幻灯片播放、EXIF 信息面板、按 EXIF 方向自动摆正；显示旋转与落盘旋转分离 |
| 视频 | 系统解码器播放，倍速 0.25×–4×、音量 / 静音、进度拖动；元数据（时长 / 分辨率 / 编码 / 码率 / 音轨） |
| 分类 | 自定义分类 + 正则规则（匹配文件名 / 完整路径 / 扩展名），规则启停、优先级排序、批量重匹配 |
| 索引 | 添加 / 移除扫描源；全量扫描与前缀对账自动清理失效条目；尺寸与时长由后台任务分批回填 |
| 局域网 | 内置 HTTP 服务，浏览器浏览与流式播放；密码保护、只读、IP 限流 |
| 操作 | 多选批量收藏 / 删除 / 重命名；删除走回收站（可还原），或仅从索引移除 |
| 界面 | 自定义标题栏、全窗口背景图 + 玻璃卡片、深浅主题跟随系统 |

### 1.3 非目标（明确不做）

- 不做图片编辑器：裁剪、调色等能力保留在服务层，但**不作为编辑工作流对外暴露**
- 不做云端同步、账号体系、跨设备
- 不做人脸 / 场景 / AI 识别——初版方案中的「发现模式」已全链路移除，理由见 [ADR-11](#adr-11-移除发现模式)
- 不做多语言与遥测

## 3. 工程结构

### 3.1 物理分层

```
pixbian/
├── Directory.Build.props      语言 / 平台 / 包版本集中管理，含 VS 与 PRI 任务路径解析
├── global.json                锁定 .NET 8 SDK
├── Pixbian.sln
├── Pixbian.ps1                一键构建并独立启动
├── build/Install-Toolchain.ps1
├── tools/gen-icon.ps1         由 Assets/app-icon.svg 生成多尺寸 ICO
├── docs/                      本文档、界面设计规范、第三方许可声明
└── src/
    ├── Pixbian/               WinUI 3 界面层：Views / ViewModels / Controls / Services / Converters
    ├── Pixbian.Core/          领域层：模型、索引、分类引擎、路径安全（纯 net8.0）
    ├── Pixbian.Data/          SQLite 仓储与 Schema 迁移（纯 net8.0）
    ├── Pixbian.Imaging/       WIC 解码、EXIF 读取、非破坏性编辑
    ├── Pixbian.Media/         视频元数据读取（系统 API）
    ├── Pixbian.WebServer/     局域网 HTTP 服务（纯 net8.0）
    └── *.Tests/               xunit 测试：Core / Imaging / WebServer
```

### 3.2 依赖方向（强制）

```
Pixbian           →  Core / Data / Imaging / Media / WebServer
Pixbian.Data      →  Core
Imaging / Media / WebServer  →  Core（三者彼此不相互依赖）
Pixbian.Core      →  仅 .NET BCL（零项目引用）
```

#### 与初版方案的偏差：Web 服务提供方的调整

初版方案规划 `PhotoApps.Server`（HTTP 服务端）与 `PhotoApps.Client`（HTTP 客户端）两个工程，
意图是让未来的移动端共用同一套 HTTP API。

**实际调整为 `Pixbian.WebServer`。** 原因：

1. 初版方案中「先定义 HTTP 契约、UI 再对接」的**双轨并行前提并不成立**——HTTP 层只是 UI 之外
   的一个薄适配层， abstractions 已在 Core 就位，直接面向 Core 接口开发不影响契约稳定性。
2. HTTP 客户端暂无对应需求，提前建设属于推测性投入。

结论：**保留了威胁模型与安全边界，去掉了无消费者的额外工程**。

### 3.3 关键约束

| 约束 | 理由 |
| --- | --- |
| `Pixbian.Core` TFM 固定为**纯 `net8.0`**，不得引用任何 WinRT / WIC API | 一旦引入 windows TFM，`Core.Tests` 必须在 Windows 上运行，纯领域层测试基线即被破坏 |
| 跨层数据交换统一使用 `Pixbian.Core.Models` | 禁止向上泄漏 `SqliteDataReader` 等基础设施类型 |
| 需要平台能力时：**Core 定抽象 + UI 层注入实现** | 保持 Core 可移植 |
| 包版本只在 `Directory.Build.props` 维护 | 禁止在各 csproj 写死版本号 |
| 只使用稳定发行版 | 禁止 alpha / beta 预发布包 |

## 4. 数据模型

### 4.1 核心模型（`Pixbian.Core/Models/`）

| 类型 | 说明 |
| --- | --- |
| `MediaItem` | 媒体条目。路径为业务主键；承载尺寸、时长、收藏、分类、评分与元数据探测状态 |
| `MediaKind` | 枚举：`Image` / `Video`，存为 INTEGER |
| `Category` | 分类。名称唯一，带展示色与排序号 |
| `CategoryRule` | 分类规则。正则模式 + 匹配目标 + 优先级 + 启停 |
| `RuleMatchTarget` | 枚举：`FileName` / `FullPath` / `Extension` |
| `MediaMetadataState` | 枚举：`NotProbed(0)` / `Completed(1)` / `Failed(2)` |
| `AppSettings` / `WebAccessSettings` | 应用与 Web 服务配置 |

### 4.2 数据库 Schema

SQLite，当前 `PRAGMA user_version = 2`。**时间统一存 ISO8601 往返格式 UTC 文本，布尔与枚举存整数。**

#### v1 — 初始结构

```sql
CREATE TABLE media_items (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    path         TEXT    NOT NULL UNIQUE,   -- 业务主键
    file_name    TEXT    NOT NULL,
    directory    TEXT    NOT NULL,

    file_size    INTEGER NOT NULL,
    created_utc  TEXT    NOT NULL,
    modified_utc TEXT    NOT NULL,
    indexed_utc  TEXT    NOT NULL,
    taken_utc    TEXT    NULL,

CREATE TABLE categories (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,

CREATE TABLE category_rules (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
```

### 4.3 迁移规则

- 版本号记录于 `PRAGMA user_version`，迁移在**单个事务内**原子执行，中断后重启可续跑。
- **已发布的迁移脚本禁止修改**。需要变更结构时新增 v(N+1)。
- 全部 SQL 参数化，动态条件统一 `(col = @p OR @p IS NULL)` 形式。

## 5. 核心流程

### 5.1 索引（两阶段）

索引刻意拆成两个阶段，让界面在秒级可用：

| 阶段 | 执行者 | 内容 |
| --- | --- | --- |
| 扫描 | `MediaIndexingService.ScanAsync` | 只写文件属性（路径、文件名、目录、大小、时间、类型） |
| 回填 | `MediaMetadataBackfillService` | 像素尺寸与视频时长，后台分批补齐 |

扫描要点：

- 采用 **pending / done 标记法**完成「消失文件」对账：扫描前标记全部条目为 pending，
  遍历命中的标记为 done，收尾统一移除仍为 pending 的条目。开销 O(1)/条，避免 O(N) 差集。
- 移除扫描源时按前缀同步清理其下条目，避免留下无法访问却又可见的僵尸记录。
- 跳过**重解析点**（符号链接 / 联接）与隐藏、系统文件，规避目录环与越权读取。
- 路径入库前经 `PathGuard` 规范化，保证与索引时的前缀一致。

### 5.2 元数据回填

参数：每批 **200 条**、并发 **2**、批间让出 **1.5 秒**、单次运行最多 **25 批**。

三态设计的关键：**失败必须落为 `Failed`**。否则损坏文件会在每轮被反复捞取，
占用批次额度，导致回填永不收敛。

写回只覆盖 `width` / `height` / `duration_ms` 与状态列；收藏、评分、分类属用户数据，
由 `COALESCE` 保护。

**排他必须用 `Interlocked.CompareExchange` 而非布尔字段**：触发点有扫描回调与启动流程两处，
存在并发进入。改用 `SemaphoreSlim` 持有字段会触发 CA1001（在 `-warnaserror` 下是错误）。

回填与索引刻意解耦：不参与扫描的状态流转、不向用户暴露进度、失败不打断当前操作。
已在回填时直接返回而不排队——两个回填任务会各自取到同一批待处理条目（彼此的更新尚未提交），
重复探测同一批文件并在数据库写锁上互相等待，叠加的持续文件 IO 会让前台浏览表现为卡死。

### 5.3 分类规则

规则按 `priority` 降序、命中即止。用户正则属不可信输入，四道 ReDoS 防护：

1. 编译后构造时**强制 1 秒匹配超时**
2. 触发超时的规则**标记为 `IsDangerous` 并在本次匹配中跳过**
3. **整批匹配 30 秒总时限**
4. 待匹配文本**截断至 4096 字符**

> 初版方案设定截断 260 字符，实际放宽至 4096——260 不足以覆盖深层目录的完整路径。

批量重匹配由 `CategoryViewModel` 驱动：**分页读取 → 逐页 `MatchBatch` → 事务写回**，
避免一次性载入全部条目。

### 5.4 缩略图管线

请求尺寸语义统一为「**显示区最长边**」，处理顺序：

1. 先乘 `RasterizationScale` 换算物理像素
2. 再向上量化到 **17 档解码档位**（128–2560，相邻比值 ≤ 1.33）
3. 缓存键 `path|bucket`

- 图片：`BitmapDecoder` + `BitmapTransform`，缩小用 `Fant`、放大用 `Cubic`（上限 2 倍），
  遵循 EXIF 方向并色彩管理到 sRGB
- 视频：系统 `SingleItem` 缩略图，保留原始宽高比
- 解码重采样在线程池经信号量限流（并发 `CPU/2`，钳制 2–8），中间产物为 `byte[]`，
  **只在最后一跳回 UI 线程构造 `BitmapImage`**
- `ThumbnailPresenter` 维护「骨架屏 / 缩略图 / 失败占位」三态，`ImageOpened` 后淡入

> **绝对不要让位图尺寸参与任何驱动布局的属性**。位图按档位量化解码，宽高比相对原图有微小偏差；
> 一旦覆盖已有准确值，就会形成「解码 → 宽高比抖动 → 重排 → 回写显示尺寸 → 再解码」的环。
> 位图尺寸只能作兜底（预取与索引均无尺寸时），**优先级必须排最后**。

### 5.5 视频播放

基于 `MediaSource` / `MediaPlayer`，**不引入 FFmpeg**，零额外体积。

元数据读取走 `VideoProperties`（`StorageItemContentProperties`，STA 线程），
按旋转角度交换宽高存入 `width` / `height`，界面只读不再换算。

### 5.6 图片查看器与非破坏性编辑

- **显示旋转与落盘旋转分离**：显示旋转只改内存中的 `BitmapImage.Rotation`；
  落盘旋转经 `ImageEditService` 重编码，一律写入**新文件**（`_rot<N>.jpg` 递增后缀），原文件不动
- 编辑服务基于 ImageSharp，已实现裁剪、调色，**界面目前只暴露旋转落盘**
- 按 EXIF 方向自动摆正

### 5.7 删除

两种语义：

| 语义 | 行为 |
| --- | --- |
| 删除到回收站 | `SHFileOperation` + `FOF_ALLOWUNDO`（可还原），成功后同步移除索引记录 |
| 从索引移除 | 仅删数据库记录，不动磁盘文件 |

> **数据库为物理 `DELETE`，非软删除。** `deleted_utc` 列存在且查询时被过滤，
> 但**从未被写入**——初版方案规划的「批量软删除」未实施。保留列不影响正确性。

### 5.8 局域网 Web 服务

基于 `TcpListener` 自研 HTTP/1.1（见 [ADR-05](#adr-05-自研-http-服务)），逐连接独立任务，服务为**只读**。

| 端点 | 说明 |
| --- | --- |
| `GET /` | 浏览器端页面 |
| `GET /app.css`、`GET /app.js` | 前端资源 |
| `GET /api/health` | 健康检查 |
| `POST /api/login` | 登录，换取会话令牌 |
| `GET /api/items` | 分页列表，参数 `kind` / `q` / `offset` / `limit` |
| `GET /api/items/{id}` | 条目详情 |
| `GET /thumb/{id}` | 缩略图，最长边 320 |
| `GET /media/{id}` | 原始文件流，支持 Range（供视频拖动） |

安全约束：

- 非 `GET` / `HEAD` 一律 `405`
- 媒体与缩略图**只接受数据库主键**，绝不接受客户端传入的路径；落盘前再经 `PathGuard`
  校验位于已启用库目录内
- 对外 JSON **不含绝对路径**

安全机制：PBKDF2（SHA-256，10 万次迭代，16 字节随机盐，32 字节哈希），
格式 `迭代数.盐.哈希`，恒定时间比较；会话令牌 256 位 CSPRNG，仅存内存，8 小时过期，重启失效；
同一 IP 登录失败 5 次锁定 15 分钟；固定窗口限流 60 次 / 分钟。

## 8. 关键设计决策（ADR）

### ADR-01：.NET 8 + WASDK 2.4

**决策**：全项目统一 `net8.0`（LTS），WASDK 2.4.0。

**理由**：WASDK 2.0 不支持 .NET 9，初版方案的 .NET 9 计划不成立。

### ADR-02：显式平台，禁用 AnyCPU

**决策**：只保留 x64 与 ARM64，构建时校验并在 csproj 内将 `AnyCPU` 重定向到 x64。

**理由**：WinRT 互操作与 WASDK 均要求明确平台，AnyCPU 会在运行期暴露难以定位的失败。

### ADR-03：自包含引入 WASDK，修正 XAML 编译器路径属性

**决策**：`Microsoft.WindowsAppSDK` 以包引入而非运行时下载；XAML 编译器路径属性使用
**`PkgMicrosoft_WindowsAppSDK_WinUI`**。

**理由**：WASDK 2.x 中旧的 `PkgMicrosoft_WindowsAppSDK` 属性已失效，沿用会导致
MarkupCompilePass1 静默失败，症状是全项目爆 `CS0103`，极难归因。

### ADR-04：视频播放走系统解码器，不引入 FFmpegInteropX

**决策**：基于系统解码器，零额外体积。

**理由**：成本收益不成立——FFmpeg 编解码包体积以百 MB 计，而与 `MediaPlayerElement`、
窗口化、Surface 的兼容性问题反而更多。代价是格式支持取决于系统解码器。

> 代价是可接受的：绝大多数用户视频为 H.264 / HEVC。若后续确有 MKV 等特殊容器需求，
> 建议**按需下载 Windows 应用商店解码器**，或评估 FFmpegInteropX（MIT）的打包体积。

### ADR-05：自研 HTTP 服务

**决策**：基于 `TcpListener` 实现 HTTP/1.1，**不用 `HttpListener`**。

**理由**：`HttpListener` 需 `netsh http add urlacl` 预留 URL 或管理员权限，与「免安装、
免管理员、xcopy 部署」的目标冲突。自研约 300 行，只覆盖本项目所需的 GET/HEAD + 静态响应。

### ADR-06：PBKDF2 + 内存会话

**决策**：PBKDF2（SHA-256，10 万次迭代，16 字节盐）+ 恒定时间比较；会话令牌仅存内存。

**理由**：局域网服务面向不可信网络，密码不可明文或弱哈希存储；令牌不落盘则重启即失效，
无需管理吊销列表。

### ADR-07：索引两阶段 + 三态回填

**决策**：扫描只写文件属性；尺寸与时长由后台分批补齐，探测状态三态。

**理由**：让界面秒级可用。三态中「失败必须落为已失败」是收敛的必要条件。

### ADR-08：缩略图档位量化 + 只回传 `byte[]`

**决策**：请求尺寸先乘 `RasterizationScale` 再量化到 17 档；解码在线程池完成，
中间产物为 `byte[]`，只在最后一跳回 UI 线程构造 `BitmapImage`。

**理由**：档位量化避免同一图片因滚动产生大量不同尺寸的解码结果，直接提升缓存命中率；
线程亲和性切开可避免跨线程传递 `SoftwareBitmap` 的陷阱。

### ADR-09：分类重匹配分页批处理 + 事务

**决策**：分页读取 → 逐页匹配 → 事务写回。

**理由**：一次性载入全部条目在大库上会引发内存峰值与长事务锁。

### ADR-10：删除走回收站，数据库物理删除

**决策**：文件删除用 `SHFileOperation` + `FOF_ALLOWUNDO`；数据库为物理 `DELETE`。

**理由**：相册类应用的误删代价高，回收站是必要的兜底。数据库不做软删除是因为
索引可从文件系统重建，保留墓碑记录没有消费者。

### ADR-11：移除发现模式

**决策**：初版方案中的「发现模式」（与设备照片 / 通用文件夹集成、时间轴、地点相册）
**全链路移除**，不保留任何残余代码。

**理由**：该能力依赖 Windows 照片应用的封闭实现，且需授予 `broadFileSystemAccess`
与图片库权限——与「轻量替代、本地优先、最小权限」的定位冲突。

### ADR-12：随机排序用取模而非 `ORDER BY RANDOM()`

**决策**：列表随机排序用 `(id * @seed) % 1000003`；随机单条用主键定位 + 应用层生成的偏移量。

**理由**：`ORDER BY RANDOM()` 会对全表排序，数据量上万后开销无法接受。
取模方案保证**同种子分页稳定**——翻页时不会出现重复或遗漏。

### 10.2 已知缺陷

| 项 | 说明 |
| --- | --- |
| 缩略图缓存键不含文件标识 | 现按路径为键，文件被同名替换后会返回旧图。缓存键**必须带 `modified_utc` + `file_size`** |
