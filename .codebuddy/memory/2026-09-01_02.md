# 2026-09-01 工作日志（第 3 卷）

## 三次定位并修复：布局循环（界面完全无响应、点击无效）

### 决定性证据链
1. `diag.log` 显示 `LOADTOTAL|图库|1750|items=200` —— **加载只用 1.75 秒就完成了**，
   之后点击无任何新日志 → 不是加载慢，而是 UI 坏了。
2. CPU 10 秒涨 9.75 秒（97% 单核），同时 `diag.log` **0 字节增长** → 单线程死循环、无业务活动。
3. `crash.log` 出现 `LayoutCycleException: Layout cycle detected`（23:36:01，正是用户点击文件夹那一刻）。
4. 数据库校验排除 NaN 假设：`width <= 0` 与 `height <= 0` 均为 **0 条**，
   且 `FromDimensions` 有 `Math.Clamp(0.25, 4.0)` 钳制。

### 真凶：AspectRatio 取值优先级错误（既有设计缺陷，被回填引爆）
- 原优先级：**位图尺寸 > 预取 > 索引 > 1.0**，且 `OnThumbnailChanged` 在每张缩略图到位时
  都会 `OnPropertyChanged(nameof(AspectRatio))`。
- `Thumbnail` 是按显示区降采样解码的（档位 128~2560），**宽高比经档位量化后有微小偏差**
  （例：1000×563 = 1.7762，解码成 384×216 = 1.7778）。
- 反馈环：解码 → AspectRatio 抖动 → 面板重排 → `SetDisplaySize` 回写新显示尺寸 →
  超过容差 → 再次解码 → 缩略图又到位 → AspectRatio 又变 → **无限循环**。
- 为何此前不显、如今必发：回填让 `Item.Width/Height` 有值，AspectRatio 由「方图 1.0」
  变为「准确值」，此后每次解码都会与位图比例比较并抖动一次，环被稳定触发。
- 元凶注释：`DimensionText` 原文写「宽高比是相对值、用位图兜底无害」——**这个判断是错的**，
  已连同 AspectRatio 一并修正并写明理由，防止后人重新引入。

### 两处修复
1. `MediaItemViewModel.AspectRatio` 优先级改为 **预取 > 索引 > 位图(兜底) > 1.0**：
   一旦有准确尺寸，缩略图位图到达**不再改变** AspectRatio，环被打破；
   位图仍作兜底，避免两者皆无时退化成方图。
2. `GalleryViewModel` 撤 loading 覆盖层前 `await WaitForNextRenderFrameAsync()`：
   覆盖层与内容网格同处一个布局容器，同帧内既替换整页条目又折叠覆盖层，
   会使两者测量互相失效。（回填后预取耗时归零，两步撞进同一帧，故此前偶发、如今必发。）
   注：此项只缓解同帧冲突，**不是主因**，主因是上面的 AspectRatio 优先级。

### 方法论沉淀（重要）
- **「UI 无响应」判别式：CPU 单核 100% + 业务日志 0 增长 = 布局/渲染死循环**；
  CPU 高但日志持续增长 = 业务慢。两者排查方向完全不同。
- **`EnumWindows` 查不到窗口要警惕启动方式**：用 `Start-Process` 从 PowerShell 启动的 WinUI 实例
  可能创建不出窗口（实测 0 windows），此时基于它的 CPU 测量**全部无效**，不能据此下结论；
  用户手动双击启动的实例才是有效样本。
- **WinUI 应用的 `MainWindowHandle` 常为 0**，UIA `RootElement.FindAll(Children)` 也常拿不到
  空标题窗口；`EnumWindows` + `GetWindowThreadProcessId` 才是可靠的窗口枚举手段。
- **概率性缺陷被优化引爆是常态**：优化改变时序（预取归零、撤层提前），
  会把「偶发」变成「必发」。此时不要回滚优化，应去找被掩盖的根因。
- **`dotnet tool install -g dotnet-stack` 抓栈在本机失败**（exit 1），
  退而用「CPU 增量采样 + 业务日志增长 + crash.log」三件套定位，实测有效。
- 依赖 WinUI 类型（如 `BitmapImage`）的视图模型**无法在纯 net8.0 的 Core.Tests 中测试**，
  这类约束只能靠代码注释固化，不要浪费时间尝试。
